# ADR-022. Защищённое API чтения для BI, определения показателей и снимки закрытых месяцев

Статус: принято для реализации DEV-14 (04.10.2026). Что Power BI Service выполняет плановое обновление выбранным способом, подтверждает внешний gate EXT-08 (владелец BI, решение DEC-06). Локальные тесты и Power BI Desktop его не заменяют.

## Контекст

Аудит (A13):
- витрина `GET /api/v1/reports/mart/{набор}` защищена cookie сеанса BFF, а Power BI Service при плановом обновлении не имеет браузера и cookie;
- постоянный bearer-токен или личная cookie в Power BI недопустимы, прямой доступ к SQL — тоже;
- отчёты читают текущее состояние модулей: правка прайс-листа, имени клиента или внутренней часовой стоимости меняет цифры закрытого месяца;
- «сумма в прогоне» смешивала утверждённое с ещё не утверждённым, а уменьшение остатка по счёту легко принять за оплату.

## Решение

1. **Отдельное API `/api/v1/bi/v1`** (только GET), включается `Bi:Enabled`. Cookie-витрина остаётся на переходный период без изменений.
   - `GET /` — каталог: наборы, типизированные колонки, ключ, определения и глоссарий;
   - `GET /datasets/{набор}?from&to&pageSize&cursor` — страницы набора;
   - `GET /snapshots/{набор}?month=yyyy-MM[&revision]` — снимок закрытого месяца.
2. **Аутентификация — Entra-токен на своей схеме `BiBearer`.**
   - Подпись по ключам tenant, issuer (v2 и sts), audience (`Bi:Audience`), срок жизни (допуск 1 минута).
   - Схема не по умолчанию: её называет только политика `bi`. Bearer не открывает ни один cookie-эндпоинт, cookie не открывает BI.
   - Политика после проверки токена требует: claim `tid` равен `Bi:TenantId`; приложение-клиент (`azp`/`appid`) названо в `Bi:AllowedClients` (пустой список — никто); роль приложения `Crm.Bi.Read`/`Crm.Bi.Cost` или scope `Bi.Read`/`Bi.Cost`.
   - Включённый API без tenant, audience или клиента не запускается.
3. **Права на наборы.** `Crm.Bi.Read` — все наборы, кроме затрат. `Crm.Bi.Cost` — `microsoft-costs` и `margins` (так же, как `finance.cost.read` отделён от `finance.read`). Роли CRM и `UserId` в BI не участвуют.
   - Ни один набор не содержит предложений и проектов — данных, чей охват зависит от пользователя (ADR-018): у сервисной идентичности нет пользователя, и «все записи из-за UserId = null» исключены составом наборов.
   - Роли приложения не назначаются пользователям; синхронизация ролей CRM игнорирует назначения сервисных принципалов.
4. **Схема наборов версионирована** (`schemaVersion = 1`): колонки с именами и типами (`guid`, `string`, `int`, `decimal`, `date`, `bool`) отдаются в каталоге и в каждой странице. Новые колонки добавляются с новой версией, а прежняя читается в переходный период.
5. **Страницы и watermark.**
   - Строки упорядочены по ключу (первые колонки набора), страницы — keyset: курсор несёт момент начала обновления, период и ключ последней строки.
   - Каждая страница несёт `asOf` — момент начала обновления; последняя страница — `watermark` (тот же момент).
   - Инкрементального чтения нет: следующее обновление читает период заново. Строка, появившаяся левее курсора во время обновления, попадёт в следующее, а не потеряется. `pageSize` ограничен 5000, лимит запросов — на приложение-клиент (`Bi:RequestsPerMinute`, 120).
6. **Определения.** Глоссарий отдаётся с каталогом и дублируется в [runbook 14](../runbooks/14-power-bi-refresh.md): MRR, ARR, утверждённая и ожидающая сумма, выставлено, остаток к оплате, маржа и источник себестоимости.
   - Выставленное — содержимое утверждённых оснований (`approvedExVat`), ещё не утверждённое — отдельно (`pendingExVat`).
   - CRM знает `totalIncVat` и `outstanding` счёта по данным учётной системы. Колонки «оплачено» нет: остаток падает и при оплате, и при кредит-ноте, и CRM их не различает.
7. **Снимки закрытых месяцев в хранилище документов** (`reports/snapshots/<набор>/<месяц>/r001.json`), а не в новой схеме БД.
   - Отчётность схемы не имеет (правило docs/03), поэтому снимок — create-only объект с хешем: тот же способ, что для документов предложений (ADR-017) и журнала обслуживания (ADR-021).
   - Снимок делает ежедневная задача `reports-snapshot` для прошлого месяца (берёт только отсутствующие наборы) или Finance через `POST /api/v1/reports/snapshots/{месяц}` (`finance.cost.read`). Открытый месяц не снимается.
   - Исправление — новая ревизия (`revise`), прежняя остаётся читаемой. Чтение проверяет хеш.
   - `provenance`: `Captured` — снято не позже 5 дней после конца месяца; позже — `Reconstructed`: собрано из текущих данных и не выдаётся за состояние на конец месяца. Строка маржи несёт `hourlyCostUsed`.
   - Наборы со снимком: выручка по месяцам и клиентам, часы, затраты Microsoft, маржа, подписки, повторяющаяся выручка, счета. Остатки по счетам в снимке — на момент `asOf` снимка.
8. **Инфраструктура.** Параметры Bicep `biEnabled`, `biAudience`, `biAllowedClients` (переменные окружения конвейера `CRM_BI_*`) для crm-web; роли приложения `Crm.Bi.Read`/`Crm.Bi.Cost` описаны в `infra/entra/register-app.sh` (скрипт не запускался: изменение tenant требует допуска).

## Рассмотренные варианты

| Вариант | Почему не выбран |
|---|---|
| Токен BFF или cookie в Power BI | Истекает, привязан к человеку и браузеру, открывает всё API |
| Разрешить bearer на всём API | Ослабляет cookie-модель, CSRF и права ролей CRM |
| Прямое чтение SQL / Azure SQL как источник | Обходит права, границы модулей и record scope |
| Таблицы снимков в новой схеме `reporting` | Миграции, права, триггеры; объекты с хешем дают то же без схемы |
| Инкрементальное чтение по `changedSince` | У агрегатов нет журнала изменений; полное чтение периода идемпотентно |

## Последствия

- **Плановое обновление Power BI Service** с аутентификацией Entra — предмет EXT-08: какой коннектор и какая identity его выполняют, что происходит при ротации секрета и после истечения токена. До проверки способ — рекомендация, а не доказанная схема (runbook 14).
- Cookie-витрина `/api/v1/reports/mart` считается устаревшей и удаляется после перехода отчётов (в коде она не менялась); её определения прежние (в ней `totalExVat` включает неутверждённое).
- Снимки задним числом не воссоздают прошлое: для месяцев до DEV-14 они `Reconstructed` и годятся только как ориентир. Остатки по счетам на конец месяца без снимка того времени не восстановить.
- Хранилище документов зонально (ZRS), как и остальные операционные объекты (ADR-021): при потере региона снимки пропадают вместе с ним; владелец решает по региональному сценарию (EXT-04).
