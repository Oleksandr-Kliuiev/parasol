# ADR-018. Записевой охват: свои предложения и назначенные проекты

Статус: принято для реализации DEV-09 (04.10.2026). Матрица ниже — основа restricted-режима по SEC-AZ-03 и docs/02 §2. Бизнес-подтверждение матрицы (DEC-01) — внешний gate EXT-01; до него политика организации **не считается утверждённой**, и решение о включении в окружениях с реальными данными принимает владелец (runbook 11).

## Контекст

Аудит (A09): `mine`/`MineOnly` — фильтр, выбранный пользователем, а не проверка доступа. Любой с `sales.read` получал любое предложение (по id, списком, PDF) и мог выполнять с ним действия при `sales.write`; любой с `projects.read` видел все проекты; время можно было записать на любой проект по id — и ответ называл проект. При этом SEC-AZ-03 и docs/02 §2 обещают Sales «свои» предложения, а техникам — «назначенные» проекты.

## Решение

1. **Права охвата в карте ролей** (`Crm.Authorization/Permissions.cs`, единственное место «роль → право»): `sales.quotes.all` — каждое предложение; `projects.all` — каждый проект. Без такого права роль видит только свои/назначенные записи этого вида. Пользователь с несколькими ролями получает самый широкий охват (BR-ACC-03).
2. **Режим** `Authorization:RecordScope`: `Restricted` (по умолчанию, SEC-AZ-03) или `Open` (поведение до DEV-09). Задаётся параметром Bicep `recordScope` в `infra/env/*.bicepparam`; `Open` — только датированное и согласованное исключение на время сверки владельцев. При `Open` crm-web пишет предупреждение при каждом старте; режим виден в отчёте и в `/bff/user`.
3. **Общий контракт** `IRecordScope` (`Crm.SharedKernel`): `LimitedTo(everyRecordPermission)` — `null`, если вызывающий видит всё (режим Open, фоновые задачи — системный пользователь имеет все права, роль с правом «все»), иначе идентификатор пользователя (`Guid.Empty`, если CRM-пользователя нет, — тогда ничего не совпадает). Охват применяет **модуль-владелец** в каждом запросе к своим записям; ни один путь не опирается на фильтр, выбранный клиентом.
   - Sales: `QuoteService.InScope` — в списке и в единственном загрузчике по id (`LoadAsync`), через который идут все операции с предложением: карточка, PDF, правка, выпуск, согласование, отправка, принятие, отказ, отмена, новая версия, передача.
   - Projects: `ProjectAccess.InScope` — список, загрузка по id (все действия с этапами и задачами), удаление, `IProjectsApi.GetProjectAsync/GetProjectsAsync` (их использует учёт времени).
4. **Предложение принадлежит владельцу текущей версии.** Виден весь набор версий или ни одной; передача текущей версии переносит историю. Пользователь без `sales.quotes.all` может назначить владельцем только себя: создание или правка с другим владельцем — 403 `SAL_QUOTE_OWNER_NOT_ALLOWED`; пропущенный `ownerId` в правке сохраняет владельца (предложение не теряет владельца по недосмотру). Передача — отдельное действие `POST /quotes/{id}/transfer` (`sales.write`, `If-Match`, только текущая версия — иначе `SAL_QUOTE_NOT_CURRENT`, только активный пользователь — иначе `SAL_QUOTE_OWNER_UNKNOWN`), в любом статусе; изменение владельца пишется в журнал аудита. После передачи прежний владелец теряет доступ сразу; сохранённые ссылки отвечают «не найдено».
5. **Проект назначен** руководителю, участнику команды и исполнителю задачи. Команда — новая таблица `projects.ProjectMembers` (аудируемая, удаление мягкое — в журнале видно, кто и когда имел доступ), `POST /projects/{id}/members` и `DELETE /projects/{id}/members/{userId}` (`projects.write`, идемпотентно, в любом статусе проекта). Отсутствие назначения — нет доступа, а не доступ ко всему; смена руководителя меняет доступ сразу.
6. **Учёт времени**: проект записи должен быть в охвате пользователя, принадлежать той же организации и принимать часы (`TIM_PROJECT_NOT_AVAILABLE` / `_OTHER_ORGANIZATION` / `_CLOSED`). Запись, уже привязанная к проекту, исправляется без этой проверки — снятый с проекта техник может поправить вчерашние часы. Названия проектов в своих записях времени показываются как прежде (`GetProjectNamesAsync` называет то, на что уже указывает запись).
7. **Вне охвата — как не существует**: 404 с тем же кодом, что и для несуществующего id; списки фильтруются до лимита и подсчётов, поэтому ни id, ни количество не раскрывают чужие записи. Интерфейс показывает «не найдено».
8. **Отчёт dry-run** `GET /api/v1/admin/record-scope` (`audit.read`) и страница «Доступ к записям»: режим; для каждого вида записей — роли, видящие всё, и роли, ограниченные своими/назначенными; распределение записей по людям; записи без владельца/назначения (их увидят только роли с полным доступом); неактивные владельцы. Модули отдают свою часть через `IRecordScopeReporter` (как `ISearchProvider`).
9. **Интерфейс**: списки говорят «ваши предложения» / «ваши проекты», бесполезный фильтр «только мои» скрыт; передача предложения; раздел «Команда» проекта; при смене пользователя в браузере (другая вкладка, общий компьютер) и при выходе кэш запросов очищается; ответы API — `Cache-Control: no-store`.

## Матрица (предложение до EXT-01)

Охват: **все** — каждая запись вида; **свои** — предложения, текущей версией которых владеет пользователь; **назначенные** — проекты, где пользователь руководитель, участник команды или исполнитель задачи; «—» — нет права на вид или действие.

| Роль | КП: чтение | КП: изменение | Проекты: чтение | Проекты: изменение |
|---|---|---|---|---|
| Admin | все | все (административное исключение — полный набор прав) | все | все |
| Management | все | все + согласование скидок | все | все |
| Finance | все | — | все | — |
| Sales | свои | свои | все | все |
| ServiceLead | свои¹ | — | все | все |
| Technician | свои¹ | — | назначенные | —² |
| ReadOnly | свои¹ | — | все (без денег) | — |

¹ docs/02 §2: «—». В restricted-режиме такие роли видят только предложения, где их назначили ответственными (обычно ни одного); полностью закрыть вид для них — решение DEC-01.
² docs/02 §2: «RW (назначенные)»; в карте ролей у техника нет `projects.write` — изменение назначенных проектов техниками требует решения DEC-01.

Пути доступа и как они следуют охвату:

| Путь | Предложения | Проекты |
|---|---|---|
| Список, фильтры (`mine`, `ownerId`, `managerId`, организация, сделка, поиск) | охват до фильтров | охват до фильтров |
| По id, действия | 404 вне охвата | 404 вне охвата |
| PDF (DEV-08) | тот же загрузчик + `finance.read` | — |
| Глобальный поиск | провайдера нет | провайдера нет |
| История (журнал аудита записи) | только `audit.read` (Admin, Management, Finance — роли с полным охватом), даже владельцу | так же |
| Custom fields | вида «КП» нет | вида «проект» нет |
| Уведомления | видов о КП нет | видов о проектах нет |
| Экспорт, витрина Power BI | наборов КП нет | наборов проектов нет |
| Дашборд, отчёты | только сделки | часы — только в карточке/списке проекта |
| Учёт времени | — | проект записи — в охвате |
| Отчёт об охвате | `audit.read` | `audit.read` |

Не входит в restricted-режим SEC-AZ-03 (решение DEC-01; сейчас без записевого охвата): сделки и лиды (docs/02: Sales — RW все); биллинг-прогоны и отчёты «свои клиенты» для Sales (docs/02 §2) — сейчас по `billing.read`/`reports.read` видны все; описания начислений в основаниях содержат номер предложения и название проекта; договор, созданный из принятого предложения, видят роли с `contracts.read` (он сам — отдельная запись своего модуля).

## Последствия

- Sales больше не видит и не меняет чужие предложения, техник — проекты, на которых его нет; Finance и Management видят всё, как и раньше.
- Предложение без владельца и проект без назначений видят только роли с полным охватом — им никого не назначают «для обхода»; отчёт показывает их, владельцы назначаются перед включением режима (runbook 11).
- Первое развёртывание в окружение с данными: отчёт и сверка, при необходимости временно `Open` (runbook 11). Откат кода не нужен: `Open` возвращает прежнее поведение без изменения данных; таблица команды остаётся.
- Новый путь к предложениям или проектам (провайдер поиска, custom fields, история модуля, отчёт) обязан идти через охват модуля-владельца; регрессию ловят `RecordScopeTests` (интеграционные и модульные).
