# ADR-019. Серверные сессии и свежесть полномочий

Статус: принято для реализации DEV-10 (04.10.2026). Срок отзыва ≤ 5 минут — проектный ориентир DEC-05; замер в реальном tenant, разрешения Graph и поведение групп/PIM подтверждает внешний gate EXT-02. До него локальные тесты с поддельным временем и тестовым каталогом (WireMock Graph) **не считаются** проверкой Entra.

## Контекст

Аудит (A15):
- роли жили в cookie: claim `roles` из id_token при входе. Ежечасная ревалидация погашала refresh token для Graph `User.Read`, а этот access token ролей CRM не несёт, так что снятые Finance или Admin действовали до конца сессии (до 12 ч);
- ежечасная синхронизация пользователей видела только `accountEnabled`. Снятие назначения, выход из группы и истечение PIM она не замечала;
- выход удалял cookie только в браузере, и скопированная cookie оставалась действительной до истечения срока;
- без настроек Data Protection любой хост, включая production, молча работал со своим локальным набором ключей. Cookie одной реплики не читались другой, а сессии умирали вместе с репликой.

## Решение

1. **Источник назначений — корпоративное приложение CRM в Entra.** Задача `entra-role-sync` в crm-worker (`Integrations:MicrosoftGraph:RoleSyncCron`, по умолчанию каждые 2 минуты, через `SyncRunner`) читает:
   - `servicePrincipals?$filter=appId eq '<CrmAppId>'` — роли приложения;
   - `servicePrincipals/{id}/appRoleAssignedTo` — назначения пользователям и группам;
   - `groups/{id}/members/microsoft.graph.user` — **прямых** членов назначенных групп;
   - `users?$filter=accountEnabled eq false` — отключённые аккаунты.

   Результат совпадает с тем, что Entra кладёт в токен:
   - вложенные группы роли не дают;
   - активация PIM для группы — активное членство на её срок, после истечения роли нет;
   - отключённая роль (`isEnabled = false`) не считается;
   - отключённый аккаунт не держит ролей ещё до того, как ежечасная синхронизация пользователей пометит его неактивным.

   `User.Read` больше не считается проверкой ролей. В журнале интеграций остаются каждая ошибка, каждое изменение и раз в час запуск без изменений (`SyncRunner.quietFor`). Пауза системы `microsoft-graph` (runbook 05) останавливает и эту задачу.
2. **Подтверждённые роли хранятся на сервере.**
   - `identity.Users.Roles`, `RolesVersion`, `RolesVerifiedAt`. Последнее — подтверждение именно этого пользователя: токен входа или чтение каталога, изменившее его роли.
   - `identity.DirectoryRoleConfirmations` — одна строка на tenant: начало последнего применённого чтения каталога.

   Правила записи:
   - изменение ролей повышает версию и пишется в журнал аудита: что было, что стало, системный пользователь;
   - неизменные роли не пишутся, поэтому нет строки аудита на каждого пользователя каждые 2 минуты и не меняется ETag;
   - роли считаются подтверждёнными на момент `max(Users.RolesVerifiedAt, DirectoryRoleConfirmations.ConfirmedAt)`;
   - чтение, начатое до более позднего входа, не отменяет то, что подтвердил вход;
   - чтение старше уже применённого отбрасывается целиком. Перекрывающиеся запуски разводит маркер конкурентности: проигравший откатывается вместе со своими изменениями ролей.
3. **Серверная сессия.**
   - Вход создаёт строку `identity.UserSessions`, её id лежит в cookie (`crm_sid`). Выход закрывает её, и копию cookie отвергают все реплики.
   - На каждом запросе `OnValidatePrincipal` берёт состояние: сессия открыта, пользователь активен, роли, версия, время подтверждения. Источник — кэш реплики не старше 30 с (`Auth:SessionStateCacheSeconds`), иначе один запрос к базе.
   - Роли из cookie заменяются серверными, версия ролей хранится в claim `crm_rv`, cookie переписывается.
   - Claim `crm_roles_verified` выставляется из серверной записи на каждом запросе: значение из cookie никогда не читается авторизацией.
   - Охват записей DEV-09 считается из прав запроса, поэтому меняется вместе с ролями.

   **Срок отзыва:** до 2 минут ожидания запуска, плюс чтение Graph, плюс до 30 с кэша — около 2,5 минут при цели DEC-05 в 5 минут.
4. **Свежесть для привилегированных действий — fail-closed.** Подтверждение ролей не старше `Auth:PrivilegedFreshness` (5 минут) нужно:
   - изменяющим запросам, разрешённым только привилегированными правами (`Permissions.Privileged`: `billing.manage`, `billing.approve`, `billing.approve.second`, `time.unlock`, `sales.discount.approve`, `integrations.manage`, `customfields.manage`, `customers.delete`);
   - любому эндпоинту массового экспорта (`.ExportsData()`: витрина Power BI, экспорт организаций).

   Без свежего подтверждения ответ — `403 AUTH_REVERIFY_REQUIRED`. Интерфейс просит выйти и войти снова: новый токен — новое подтверждение. Проверку делает обработчик авторизации на сервере для каждого эндпоинта, а не интерфейс.
5. **Чтение при недоступном каталоге — ограниченный grace.** Сессия читает 8 часов после последнего подтверждения (`Auth:RoleGrace`), затем её отвергают (401) и нужен вход. Деактивированный пользователь получает 401 сразу после обновления кэша. Старая cookie его не активирует: активность ставит только синхронизация каталога.

   Ежечасная проверка refresh token ведёт себя так же:
   - ответ Entra «токен больше не выдаётся» (аккаунт отключён, пароль сброшен, сессии отозваны) завершает сессию;
   - если Entra не ответил (сеть, таймаут, 429, 5xx), проверка не считается пройденной, а откладывается на 5 минут, и запрос обслуживается в рамках grace. Привилегии по-прежнему решает подтверждение каталога. Раньше это давало 500 на каждый запрос каждой сессии старше часа;
   - неожиданная ошибка остаётся ошибкой запроса.
6. **Один набор ключей.** В production crm-web не запускается без `DataProtection:BlobUri` и `DataProtection:KeyVaultKeyUri` (Blob + ключ Key Vault, как в Bicep). Половина конфигурации не запускается нигде. Ротация ключей сессии не завершает: старые ключи остаются в наборе для расшифровки. Ротацию не используют вместо отзыва.
7. **Сохраняется:**
   - single-tenant регистрация, MFA и Conditional Access на входе, абсолютный срок 12 ч, скользящий 8 ч;
   - ежечасная проверка refresh token (отозванные в Entra сессии, сброс пароля);
   - запрет входа разработчика вне Development.

   Вход разработчика идёт тем же путём: сессия и роли, подтверждённые выбранной ролью. Синхронизации в Development нет, поэтому привилегированное действие требует входа не старше 5 минут.

## Рассмотренные варианты

- **Обновлять роли повторным получением id_token** по refresh token каждой сессии раз в несколько минут. Это N сессий × 12 погашений в час, ограничения Entra, а пока токен не получен, роли остаются старыми. Отвергнуто в пользу одного чтения каталога на tenant.
- **Короткая сессия** (5 минут) с повторным входом. Отвергнуто: усталость от MFA и потеря работы в формах.
- **Группы в токене.** Отвергнуто: переполнение (overage) при большом числе групп, и действует тоже только на входе.

## Последствия

- Снятая роль, выход из группы, истечение PIM или отключение аккаунта прекращают привилегии на всех репликах за ≤ 2,5 минуты без повторного входа (DEV-10-AC01…03).
- Если Graph не отвечает или не выдано разрешение, через 5 минут привилегированные действия и экспорт закрываются до успешного запуска или нового входа, а чтение продолжается не дольше 8 часов (AC04).
- **Требуется в tenant (EXT-02):** управляемой идентичности crm-worker нужны разрешения Graph Application `Application.Read.All` и `GroupMember.Read.All` (`User.Read.All` уже нужен для синхронизации пользователей). `Integrations:MicrosoftGraph:CrmAppId` = client id регистрации CRM (Bicep передаёт `entraClientId`). Без разрешений запуски падают, и привилегированные действия закрываются — fail-closed, см. runbook 12.
- **Миграция `SessionsAndConfirmedRoles` только добавляет:** колонки с безопасными значениями по умолчанию и две таблицы, предыдущий релиз работает на новой схеме. Cookie, выданные до DEV-10, не содержат `crm_sid` и один раз потребуют входа. Пользователи не удаляются.
- **Нет отдельной команды «завершить все сессии».** Срочный отзыв идёт через каталог (runbook 12). Глобальное завершение сессий отдельной командой — возможное развитие, ротацией ключей его не заменяют.
