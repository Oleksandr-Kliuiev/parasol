# ADR-015. Выпуск: один проверенный артефакт от CI до production

Статус: принято для реализации DEV-05 (04.10.2026). Фактические настройки GitHub/Azure (защита ветки, reviewers окружения `prod`, федерация OIDC, роли) — внешняя проверка EXT-11; этим решением и поручением ничего не развёртывалось.

## Контекст

Аудит (A05): `deploy.yml` запускался на каждый push в `main` параллельно с CI и собирал образы заново — в том числе для prod; образы ссылались на изменяемый тег; reviewers prod были только комментарием в YAML; smoke проверял лишь `/health/ready` 200; переменная PowerOffice по умолчанию давала `Demo` и prod; сканер пакетов при ошибке источника проходил как «чисто» (`| tee` без `pipefail`), `npm audit` не проверял сборочные зависимости. Проверка отката с расширенной схемой не выполнялась.

## Решение

1. **Одна цепочка.** CI (`ci.yml`) для PR и `main`. Для коммита, отправленного в `main`, последний job `release` вызывает `release.yml` с `needs: [backend, frontend, e2e, infrastructure, codeql]`: если любой обязательный job не успешен, `release` пропускается — публикации и развёртывания нет (AC01). Новый job CI архитектурный тест сразу требует либо добавить в `needs`, либо явно решить иначе. PR (в том числе из форков) до `release` не доходят и учётных данных не получают; `pull_request_target`/`workflow_run` запрещены тестом. Отменяются только устаревшие прогоны PR, прогоны `main` — нет (могут развёртывать).
2. **Собрать один раз.** `release.yml/publish` (окружение `test`, OIDC subject `environment:test`) собирает SPA и образы crm-web и crm-worker один раз, пушит в реестр test с тегом SHA и дальше пользуется **только digest**. Для каждого образа: SBOM (SPDX, syft), сканирование образа (grype, `fail-build` на High/Critical, ошибка сканера валит шаг), provenance-аттестация GitHub (`attest-build-provenance`, push в реестр). Release manifest (`tools/release/release.py manifest-create`): commit, ссылка на прогон, digests web/worker/migrator (migrator — тот же образ crm-web, `--migrate-only`), версии схемы (последняя миграция каждого контекста), разрывы схемы, хэши SBOM, результаты обязательных job'ов. Manifest и SBOM проверяются на шаблоны секретов и хранятся артефактом 90 дней.
3. **Test.** `release.yml/deploy-test` (concurrency без отмены): проверка manifest для этого SHA → проверка схемы против релиза, который работает в test → `tools/release/deploy.sh`: (а) задача миграций Container Apps (identity мигратора, внутри VNet) с образом crm-web **по digest**; сбой — выход до любых изменений ревизий и трафика (AC04); (б) Bicep с digests: новая ревизия crm-web под меткой `candidate` с 0 % трафика (стабильная держит 100 %), новая ревизия worker; (в) smoke кандидата, сверка, что каждый контейнер и задача миграций работают ровно с digest manifest; (г) трафик на кандидата, smoke публичного адреса (при сбое трафик возвращается на стабильную), запись развёртывания (`deployment-record`).
4. **Smoke** (`tools/release/smoke.sh`, без входа и без записи): `/health/live`, `/health/ready` = Healthy (SQL/Key Vault/Blob), SPA и её entry-скрипт с CSP и `nosniff`, HSTS вне localhost, API без сессии — 401, мутация без CSRF — 403, `/bff/user` — 401, `/health/integrations` и `/admin/jobs` — 401/403 или на вход, `/bff/login` ведёт в Entra с client_id окружения.
5. **Prod только продвижением.** `promote.yml` (ручной запуск, вход — полный SHA). Job `verify` без учётных данных окружения: формат SHA, успешный прогон CI на `main` для этого SHA, все обязательные job'ы и `release / publish`, `release / deploy-test` успешны, manifest этого SHA, запись test-развёртывания с теми же digests и пройденным smoke (`promotion-check`); иначе отказ (AC02). Job `deploy` — окружение `prod` (reviewers и политика веток — EXT-11): проверка схемы, проверка provenance-аттестации digests (`gh attestation verify`), `az acr import` из реестра test **по digest** (без пересборки; digest после копии сверяется), тот же `deploy.sh`. Записи test и prod содержат одинаковые digests (AC03). Вход workflow попадает в скрипты только через переменные окружения (тест).
6. **Откат.** Быстрый путь — трафик на предыдущую ревизию Container Apps, пока она активна. Иначе `promote.yml` с `rollback: true`: релиз, который уже работал в этом окружении, разворачивается его digests **без миграций** (схема остаётся новой, expand/contract). Миграции expand-only: архитектурный тест запрещает drop/rename/сужение/обязательную колонку без default; contract — отдельным релизом с ADR и записью в тесте.
7. **Разрывы схемы.** Изменение без смены колонок тоже может сломать прежний релиз: триггеры DEV-04 (`ProtectApprovedBilling`) отвергают запись EF Core без `HasTrigger` (ошибка 334). Это поймала проверка отката `tools/release/rollback-compat.sh`: E2E DEV-03 на схеме DEV-04 — 9 сценариев биллинга с HTTP 500, тогда как DEV-04 на текущей схеме — 54/54, DEV-02 на расширенной схеме DEV-03 — см. evidence DEV-05. Такие миграции регистрируются в `tools/release/schema-breaks.json` (тест требует запись для любой миграции с триггером). Manifest перечисляет разрывы релиза; Bicep помечает контейнеры тегом `crmRelease`; `schema-guard` перед развёртыванием сравнивает с релизом, который работает в окружении: откат ниже разрыва, который уже применён, отклоняется всегда (только администратор БД откатывает миграцию и разворачивает вручную); разрыв, которого нет у работающего релиза, ломает его между миграцией и переключением — нужен принятый maintenance window (`accept_schema_break`; в test принимается автоматически).
8. **Конфигурация окружений.** PowerOffice: `Demo` для test и `Production` для prod зафиксированы в `infra/env/*.bicepparam`, у параметра нет значения по умолчанию, workflow его не передают; приложение получает `Deployment__Environment` и не стартует при несоответствии (`PowerOfficeOptions.FitsDeployment`, `ValidateOnStart`): prod не может работать с Demo (и test с Production) даже при ошибке параметров.
9. **Сканеры fail-closed.** `dotnet list package --vulnerable --format json` разбирает `release.py vulnerable-dotnet`: High/Critical, неизвестная серьёзность, любые problems, отсутствие источника, меньше проектов, чем в solution, — отказ. `npm audit --json` со сборочными зависимостями: ошибка аудита, нулевой охват, `--omit=dev` — отказ. Образы — grype на release-артефакте.
10. **Цепочка поставки.** Все actions закреплены SHA коммита (тест; обновляет Dependabot), права workflow минимальны по job'ам, `id-token: write` только у job'ов, которым нужен Azure.

## Последствия

- В prod попадает только то, что прошло CI и test, тем же digest; ручная пересборка и «тот же тег» невозможны в штатном пути.
- Первое развёртывание DEV-04+ на окружение со старым релизом — разрыв схемы: в test принимается, в prod требует maintenance window (пауза worker и биллинга, runbook 01 §6a).
- Артефакты GitHub живут 90 дней: откат на более старый релиз без его manifest и записи развёртывания отклоняется (fail-closed); дольше хранить — решение владельца (EXT-11).
- Не реализовано и не заявляется: ZAP baseline, автоматический what-if в PR, автооткат по алерту 5xx, релизные теги — остаются задачами эксплуатации (DEV-17/21/23).
- Выполнение workflow в GitHub и Azure этим поручением не проверялось: нет удалённого репозитория и разрешения на развёртывание. Проверено локально: actionlint/shellcheck, юнит-тесты инструментов, архитектурные тесты, smoke против локального crm-web, проверка отката на временной БД, сборка Bicep.
