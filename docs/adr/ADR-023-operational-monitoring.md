# ADR-023. Мониторинг и сохраняемый разбор исключений

Дата: 04.10.2026. Статус: принято для реализации DEV-17; внешняя приёмка EXT-01 не выполнена.

## Контекст

Журнал последнего запуска не доказывает свежесть: failed/skipped может быть новее успешного запуска, а тихий успешный запуск не обязательно записывается в журнал. Ошибка требует назначения и комментария, переживающих обновление экрана. Общие диагностические сообщения могут содержать суммы из ответа поставщика.

## Решение

В `integration.SyncSuccesses` хранится одна монотонная отметка полного успеха на system/job. Она независима от retention журнала. Миграция переносит только доказуемые полные успехи; connection-test не используется для свежести. Failed, skipped и частичный успех не продвигают отметку. При паузе показывается отдельное состояние, прежний возраст сохраняется.

`integration.ExceptionTriages` хранит стабильный ключ сигнала, owner id, статус, комментарий и rowversion. Оператор меняет запись с If-Match; изменение и аудит записываются вместе. Категория, источник, тип и требуемое право сохраняются вместе с кейсом. Сигнал вычисляется из текущего состояния: Resolved разрешён только после восстановления. Исчезнувший, но незавершённый кейс остаётся доступен для итогового комментария; финансовые права продолжают действовать. Возвращение активного сигнала показывает Open вместо старого Resolved. Удаление старых resolved notes возможно только по утверждённой privacy retention policy; срока по умолчанию нет.

Модули предоставляют агрегированные сигналы через `IOperationalSignalSource` в SharedKernel. Они не ссылаются на интеграции; host собирает диагностику и проверяет RequiredPermission. В общей телеметрии только количество, возраст и ограниченные измерения system/job/module/component/category/source/kind. Финансовые суммы, идентификаторы клиентов и тексты ошибок поставщика туда не попадают. Нулевой счётчик выдаётся явно для восстановления алертов.

Ручной replay outbox подтверждает конкретные записи и причину. SQL session application lock сериализует заявки между web-репликами; заявка и аудит атомарны внутри каждого модуля. Между модулями общей транзакции нет: частичный сбой возвращает Requested / Unknown / NotRequested по элементам, после сетевого/частичного сбоя оператор перечитывает принятые заявки. Подтверждение включает Replays, поэтому повторное нажатие после нового сбоя worker не действует без свежего подтверждения. Outbound bulk retry атомарен для всей выборки в integration и сверяет ETag состояния каждой операции; устаревшая выборка получает 409 с результатами по элементам. Worker сохраняет прежнюю идемпотентность обработки.

`Crm.Health` и `Crm.Operations` публикуют SQL readiness и периодические снимки. Azure Monitor выбирает последний снимок, а не сумму повторных счётчиков. Stateful alerts задают severity, восстановление и группы operations/finance. Доставка отключена, пока конфигурация не содержит явное включение, владельца и адреса. Компиляция Bicep не доказывает работоспособность KQL или доставку; это протокол EXT-01 в runbook 15.

## Обратимость и ограничения

Миграция только добавляет таблицы и индексы, исходные SyncRuns не меняет. Откат приложения оставляет расширенную схему; Down с удалением истории разбора в эксплуатации не используется. Прежняя версия не продвигает SyncSuccesses: во время отката мониторинг нового выпуска не следует считать актуальным. Возврат новой версии потребует успешных синхронизаций.

Порог невыставленных позиций — начало текущего месяца Europe/Oslo; лицензии сверяются по существующей модели прошлого месяца в NOK. Это диагностические индикаторы для Finance, не автоматические финансовые решения. Большой объём диагностических запросов и индексы требуют измерения в DEV-16. Подтверждение владельцев, реакции, каналов и реальной доставки — EXT-01/DEC-09.
