# ADR-011. Идентичность начисления в основании и решения Finance

Статус: принято для реализации DEV-01 (03.10.2026). Расширяется в DEV-02 (ревизия и согласование) и DEV-03 (межпрогонный реестр начислений). Бизнес-правила DEC-02 владельцем ещё не утверждены; решение не меняет тарифы, НДС, округление и proration.

## Контекст

Аудит (A01) воспроизвёл двойное начисление: собранная строка 1 000, исправленная вручную на 900, после пересборки превращалась в две строки на 1 900. Причина — один флаг `ManuallyAdjusted` обозначал и самостоятельную ручную строку, и исправление строки источника; пересборка удаляла неотмеченные строки и добавляла все источники заново без сопоставления. Удалённая Finance строка возвращалась при следующем сборе, история решения не хранилась.

## Решение

1. **Ключ начисления (`SourceKey`).** Каждая собранная строка получает ключ, который не зависит от runId, времени сбора и случайных идентификаторов пересборки:

   | Источник | Ключ | Почему так |
   |---|---|---|
   | Строка договора | `contract:{SeriesId}:{с}:{по}` | Серия услуги сквозь версии (BR-CON-03) и дни, за которые выставляется строка. Две версии изменения в середине периода — два начисления; повторный сбор тех же дней — то же самое. |
   | Подтверждённое время (детально) | `time:{AllocationId}` | Allocation подтверждения; повторное подтверждение создаёт новые allocation и, значит, новое начисление. |
   | Время (сводно) | `time:{вид работ}:{ставка}` | Группа строк одного основания. |
   | Информационные часы | `info:{Covered|HourBank}` | Без денежного обязательства. |
   | Покупка пакета часов | `hourbank:{EntryId}` | Само движение покупки: две покупки одного пакета — два начисления, повторное чтение одной — одно. |
   | Отложенное начисление (предложение, этап проекта) | `pending:{PendingChargeId}` | Уникально по источнику (SourceType, SourceId, SourceLineId). |
   | Ручная строка | нет | Не связана ни с каким источником. |

   Коллектор отказывается от строки без ключа и от двух строк с одним ключом (это дефект источника, его нельзя «обойти» выставлением). В БД — уникальный индекс `(BasisId, SourceKey)` среди текущих строк.

2. **Значения источника и решения Finance.** Строка хранит эффективные значения (что выставляется) и значения источника при последнем сборе (`SourceQuantity`, `SourceUnitPrice`, `SourceDiscountPct`, `SourceDescription`) с канонической сигнатурой экономических полей (`SourceSignature`: группа, продукт, количество, цена, скидка, НДС; формат `0.####`, InvariantCulture, без текста). Решение (`Decision`) — `Override` (исправление) или `Exclusion` (исключение, tombstone) — принимается только с причиной и хранит автора, время и сигнатуру источника, против которой оно принято (`DecisionSignature`). Ручная строка (`Origin = Manual`) редактируется и удаляется без связи с источником.

3. **Пересборка.** Строки сопоставляются по ключу:
   - строка без решения принимает значения источника;
   - строка с решением сохраняет значения Finance; если сигнатура источника отличается от `DecisionSignature`, ставится `Conflict = SourceChanged`;
   - если источника больше нет: строка без решения удаляется, исправление получает `SourceRemoved`, исключение остаётся записью без конфликта (оба говорят «не выставлять»);
   - новые ключи добавляются как новые строки.
   Конфликт виден в UI и блокирует утверждение (`BIL_UNRESOLVED_CONFLICTS`). Finance либо оставляет решение с причиной (`keep`: `DecisionSignature := SourceSignature`, для исчезнувшего источника — принятое отсутствие), либо возвращается к источнику (`revert`). Возврат исключения снова включает строку. Исчезновение источника, принятое Finance, при повторном появлении источника снова даёт конфликт.

4. **Ревизия основания.** `BillingBasis.Revision` растёт при любом изменении строк (и не растёт при пересборке без изменений), поэтому ETag основания меняется при каждом решении. DEV-02 строит на этом ревизию прогона и согласование конкретного содержания.

5. **Плательщик и клиент услуги.** `SourceOrganizationId` — компания, которой оказана услуга; плательщик — организация основания. При консолидации дочерней компании (BR-BIL-12) строка переносится на основание материнской с сохранением исходного клиента.

## Переход со старых данных (expand)

- Миграция `ChargeIdentity` только добавляет колонки и индекс; суммы и ссылки не меняются. Строки, которые старая версия записала как ручные (`ManuallyAdjusted = 1` и нет `SourceRefs`), получают `Origin = Manual`.
- Собранная строка без ключа обрабатывается при следующем сборе открытого основания: обычная заменяется строкой с ключом, исправленная (`ManuallyAdjusted = 1`) остаётся рядом и получает `LegacyUnmatched` — ключ не угадывается, решение за Finance. Строка без `SourceRefs` с `ManuallyAdjusted = 1` никогда не приходила из источника (так старая версия пишет ручные строки, в том числе в окне отката) и принимается как ручная. Утверждённые и выгруженные основания не трогаются; их сверку выполняет реестр начислений DEV-03.
- `GET /api/v1/billing/legacy-lines` (billing.manage) — dry-run: сколько строк будет заменено, сколько ждёт решения и на какую сумму, сколько старых строк в закрытых основаниях.
- Колонка `ManuallyAdjusted` сохраняется для чтения старой версией (ручная или исправленная строка). Удаление — отдельный поздний шаг после окна отката.

## Конкуренция

Сбор, решения по строкам и утверждение изменяют строки основания и сам прогон в одной транзакции SaveChanges; `RowVersion` прогона и основания отклоняет вторую из параллельных команд (412), запросы с устаревшим `If-Match` — тоже. Уникальный ключ основания `{period}-{customer}-{run}` исключает второе основание клиента в прогоне; удалённое основание вернувшегося клиента восстанавливается, а не создаётся заново.

## Последствия

- Исправление собранной строки без причины отклоняется (`BIL_REASON_REQUIRED`); DELETE собранной строки — тоже, вместо него исключение с причиной.
- Исключённые строки не выставляются, не попадают в экспорт, выручку и сверку лицензий и не закрывают свои источники: часы и отложенные начисления исключённой строки остаются для следующего прогона.
- Сбор теперь убирает собранные строки клиента, у которого источников не осталось (раньше они оставались в основании, если там была хоть одна строка).
- Ограничение: уникальность начисления **между прогонами** (закрытый месяц, новый runId) этим решением не обеспечивается — это DEV-03.
