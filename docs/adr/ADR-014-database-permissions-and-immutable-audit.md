# ADR-014. Минимальные права приложения, неизменяемый аудит и защищённые финансовые данные в БД

Статус: принято для реализации DEV-04 (04.10.2026). Опирается на [ADR-012](ADR-012-revision-bound-approvals.md) (утверждённая ревизия) и [ADR-013](ADR-013-charge-register.md) (реестр начислений). Политика хранения персональных данных по категориям (DEC-03) владельцем не утверждена: разрушающий режим retention до её утверждения недоступен (EXT-07). Подробная матрица прав и процедуры — [runbook 08](../runbooks/08-database-permissions.md).

## Контекст

Аудит (A04) установил: crm-web и crm-worker работали под одной управляемой идентичностью, которую мигратор при каждом запуске добавлял в `db_datareader` и `db_datawriter`. Значит, любой из двух хостов (и любая уязвимость в нём) мог переписать или удалить журнал аудита, утверждённые основания и строки счетов, историю отправок и миграций. Секреты поставщиков (PowerOffice, Atera) получали оба хоста, хотя вызывает поставщиков только worker; Key Vault выдавал идентичности роли Secrets User и Certificate User на всё хранилище.

## Решение

1. **Роли БД вместо фиксированных.** Мигратор (владелец БД, единственный с DDL) после миграций создаёт роли и выдаёт права заново при каждом запуске (идемпотентно): `crm_runtime` — `SELECT, INSERT, UPDATE, DELETE` на схему каждого модуля и Hangfire, на `audit` только `SELECT, INSERT`, на историю миграций только чтение; `crm_web` и `crm_worker` — члены `crm_runtime`, у `crm_web` дополнительно запрещено менять outbox (его обрабатывает worker) и добавлять контрольные точки аудита; `crm_privacy` — только `EXECUTE` процедуры retention. Модули добавляют свои запреты через `IDatabasePermissionRules` (billing: удалять финансовые записи нельзя, журнал отправок — только добавление). Права проверяются до переключения идентичностей: идентичность не теряет доступ ради неполной роли.

2. **Отдельные идентичности.** crm-web — `id-crm-app-<env>` (роль `crm_web`), crm-worker — новая `id-crm-worker-<env>` (роль `crm_worker`). Мигратор делает каждую членом ровно своей роли и снимает `db_datareader`/`db_datawriter`/`db_owner`/`db_ddladmin`, выданные прежней версией. Конвейер развёртывания создаёт идентичность worker до миграций, чтобы её пользователь БД существовал раньше, чем Bicep переключит контейнер.

3. **Откат не расширяет права.** DDL-триггер базы `trg_ApplicationRolesStayNarrow` отклоняет добавление члена любой роли приложения в широкую фиксированную роль. Мигратор предыдущей версии при повторном запуске падает на этом (51031), а не возвращает `db_datawriter` молча. Снять защиту может только владелец БД сознательным `DROP TRIGGER … ON DATABASE`.

4. **Защита утверждённого в SQL.** Триггеры `billing` (`trg_BillingRuns_Protect`, `…Bases…`, `…Lines…`, `…Approvals…`, `trg_Charges_Protect`, `…ExportAttempts…`) действуют для любого пишущего, в том числе для идентичности со старым `db_datawriter`: у выпущенного прогона и утверждённого основания не меняются состав, суммы, плательщик, ключ, ревизия; основание не возвращается в черновик, выгруженное и отменённое (в выпущенном прогоне) — конечны, номер заказа после выгрузки не меняется; строки утверждённого основания не добавляются, не меняются и не удаляются (в том числе каскадом); акт согласования не удаляется и только один раз помечается недействительным; начисление создаётся `Reserved`, его идентичность неизменна, после резерва не меняются сумма и держатель, переходы — только по ADR-013; журнал отправок — только добавление. Транспорт остаётся приложению: `SendStartedAt`, `Failed`/`ReconciliationRequired`/`Exported`, номер заказа, попытки, сверка. Ошибки — `THROW 51001…51008` с кодами `BILLING_APPROVED_IMMUTABLE`, `BILLING_CHARGE_IMMUTABLE`, `BILLING_EXPORT_LOG_APPEND_ONLY`.

5. **EF Core.** Таблицы с триггерами объявлены через `HasTrigger`, поэтому EF не использует `OUTPUT` без `INTO` и сохраняет проверку `RowVersion` (тест конкуренции проходит через триггер). Аудит пишется перехватчиком в той же транзакции `SaveChanges`, что и бизнес-изменение: отказ триггера отменяет и запись аудита, отказ вставки аудита — и бизнес-изменение.

6. **Аудит только дополняется.** `UPDATE`/`DELETE` журнала запрещены ролям и триггером `trg_AuditEntries_AppendOnly` (удаление — никогда). Единственное изменение — retention: процедура `audit.ApplyRetention` (владелец `dbo`, цепочка владения; вызывает оператор `crm_privacy`) обнуляет только персональную часть старых записей (`UserId`, `UserName`, `IpAddress`, `Changes`) и оставляет факт действия (`At`, `Action`, `Module`, `EntityType`, `EntityId`, `CorrelationId`). По умолчанию — пробный прогон; разрушающий требует утверждённой политики модуля в `audit.RetentionPolicies` (пишет только администратор БД со ссылкой на решение DEC-03; приложение писать не может) и срока не короче политики. Аудит финансовых записей (`billing`, `contracts`, `time`, `sales`, `projects`, `catalog`, `licensing`) и сам аудит вне досягаемости retention: процедура отказывает (51020), политика для них не принимается ограничением. Каждый запуск сам становится записью аудита.

7. **Целостность и внешний якорь.** Ночная задача `audit-integrity` (worker) строит цепочку SHA-256 по фактам записей контрольными точками (`audit.IntegrityCheckpoints`), перепроверяет последнюю и по очереди одну из старых и пишет каждую новую точку в лог (`AUDIT_CHECKPOINT`, Log Analytics). Задача `audit-integrity-full` (вручную) перепроверяет все. В точку попадают только записи старше `Audit:Integrity:SettleTime` (5 минут) непрерывным диапазоном id, чтение — с `READCOMMITTEDLOCK`: идентификатор выдаётся до фиксации транзакции, и при RCSI (по умолчанию в Azure SQL) задача иначе могла бы пройти мимо записи, которая зафиксируется позже, и поднять ложную тревогу. Несовпадение — `AUDIT_INTEGRITY_MISMATCH` (Critical). Хэш в той же БД сам по себе не защищает от владельца БД: защитой служит сравнение с якорями в Log Analytics, который владелец БД переписать не может.

8. **Секреты поставщиков — только worker.** Ключи PowerOffice и Atera (и вебхуки Teams, Partner Center при подключении) получает только crm-worker: ссылки Key Vault в его контейнере разрешаются идентичностью worker, а роль Secrets User выдана ему на каждый такой секрет отдельно. crm-web не имеет ни переменных, ни доступа: его роли в Key Vault — чтение метаданных хранилища и Secrets User только на секрет своего сертификата входа; ролей Secrets User/Certificate User на всё хранилище нет ни у кого. Всё, что web делает с интеграциями, работает от сохранённых данных и выключателей (`Integrations:*:Enabled`): статус, сопоставления, импорт, проверка готовности биллинга. Проверка подключения ставится в очередь (`SyncRun` вида `connection-test` и событие в outbox) и выполняется worker; страница опрашивает результат.

## Последствия

- Приложение не может само изменить схему, переписать аудит, удалить финансовую запись или изменить утверждённое; все тесты интеграции выполняются под логином роли `crm_worker` без фиксированных ролей. Действия администратора БД (восстановление, ремонт данных) возможны только явным отключением триггера в транзакции — это видно в журнале SQL-аудита Azure и в цепочке аудита CRM.
- Абсолютной неизменяемости против администратора SQL нет и она не заявляется: владелец БД может отключить триггер или удалить DDL-триггер. Обнаружение — внешние якоря, SQL-аудит Azure и Defender for SQL; итоговая оценка угрозы привилегированного доступа — DEV-21.
- Новые таблицы модулей получают права автоматически через схему; таблицы, которые нельзя удалять или менять, модуль перечисляет в своём `IDatabasePermissionRules`. Это обязательно для inbox (DEV-07) и для таблиц приватности (DEV-11).
- Развёртывание этой версии требует внешних шагов в тенанте (выдать Graph-разрешения новой идентичности worker: `User.Read.All`, `Mail.Send` на общий ящик, `Sites.Selected`) — до них синхронизация пользователей, сводка и папки SharePoint из worker не работают. Порядок — runbook 01/02/08. Развёртывание этим поручением не выполнялось.
- Откат схемы (`Down`) снимает триггеры и процедуру, архивирует контрольные точки и политики в `*_rollback_<время>`; роли, запреты и DDL-триггер остаются.
