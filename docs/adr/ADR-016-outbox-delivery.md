# ADR-016. Доставка событий: аренда с токеном и квитанции обработчиков

Статус: принято для реализации DEV-07 (04.10.2026). Остаётся в рамках ADR-006 (Hangfire + transactional outbox в SQL); брокер сообщений не вводится.

## Контекст

Аудит (A07): после десяти ошибок сообщение outbox молча переставало выбираться; аренда на 2 минуты не продлевалась, а подтверждение (`ProcessedAt`) и снятие аренды писались без проверки владельца — исполнитель с истёкшей арендой мог пометить чужое сообщение или снять его аренду. Все обработчики события выполнялись в одной области: падение второго повторяло эффект первого. Защита от повтора держалась на проверках внутри обработчиков: `QuoteAcceptedHandler` проверял наличие договора без уникального индекса и не видел удалённые черновики; карточки Teams отправлялись прямо из обработчика при каждой доставке; события фаз проекта, доставленные не по порядку, возвращали или снимали начисление; `BasisExportedHandler` писал в два модуля двумя транзакциями. Повтор вручную был невозможен — только SQL.

## Решение

1. **Явные состояния** `OutboxMessages.Status`: `Pending` → `Processing` → `Processed`; `DeadLetter` (исчерпаны 10 попыток), `Quarantined` (payload не читается сразу; неизвестный тип — после 10 попыток, потому что следующий образ может его знать). `NextAttemptAt` с экспоненциальной задержкой (10 с · 2^(n−1), не больше часа, ±20 % jitter), `LastError` — для диагностики. Колонка со значением по умолчанию `Pending`: прежний образ продолжает вставлять события во время развёртывания; его аренда (`LockedUntil` без токена) и `ProcessedAt` уважаются.
2. **Аренда с токеном и CAS.** Захват — `UPDATE … WHERE` «свободно и пора» с новым `LeaseOwner`; любое дальнейшее изменение строки (отметка обработчика, итог, снятие аренды) — только `WHERE LeaseOwner = @token AND Status = 'Processing'`. Аренда продлевается каждую треть срока (`LeaseRenewal`); потеря аренды отменяет обработчики через токен отмены, их незафиксированная работа откатывается. Тот же приём — у исходящих операций (`OutboundOperations.LeaseOwner`) и очереди карточек Teams.
3. **Квитанция обработчика** (`InboxReceipts`, ключ `(MessageId, Handler)`) в схеме модуля обработчика. Каждый обработчик выполняется в собственной области и транзакции: обработчик модуля начинает транзакцию с вставки квитанции в свой контекст (ключ — блокировка: второй исполнитель ждёт и получает нарушение ключа), обработчик адаптера интеграции получает транзакцию и квитанцию при первом сохранении (через `AuditingInterceptor`). Транзакция фиксируется после возврата обработчика; повтор SQL-стратегии повторяет обработчик целиком. Найденная квитанция означает «уже сделано» — эффект не повторяется ни после падения до подтверждения, ни при двух исполнителях.
4. **Атомарность — граница модуля.** Обработчик меняет один модуль; попытка сохранить во втором — ошибка (`MessageHandlingContext.Guard`). Другой модуль реагирует на событие своим обработчиком: отметка часов «выставлено» перенесена из Billing в TimeTracking (`IBillingApi.GetInvoicedTimeEntryIdsAsync`), запись в чужой модуль через API (`ITimeTrackingApi.MarkInvoicedAsync`) удалена.
5. **Отметки обработчиков** (`DeliveredHandlers`): после успеха обработчика сообщение запоминает его имя; повтор выполняет только остальных. Это ускоряет повтор; корректность держится на квитанциях.
6. **Порядок и устаревшие события.** Обработчики, которые меняют состояние по событию с «отменой», проверяют текущее состояние источника: события объединения организаций пропускаются, если объединение отменено (`ICustomersApi.IsMergeUndoneAsync`); начисление фазы проекта следует текущему статусу фазы (`IProjectsApi.IsPhaseCompletedAsync`) и времени последнего решающего события (`PendingCharges.SourceChangedAt`). Один договор на принятое КП: уникальный фильтрованный индекс `Contracts.SourceQuoteId` (удалённые черновики учитываются), миграция останавливается при существующих дублях (51041) — их разбирает человек (runbook 09).
7. **Внешние эффекты.** Карточки Teams ставятся в очередь `notifications.ChannelPosts` в транзакции обработчика и отправляются задачей `channel-posts` с арендой; автоматический повтор POST в HTTP-клиенте отключён (одна попытка очереди — один POST). У вебхука нет ключа идемпотентности: при таймауте после приёма возможен дубль уведомления — только уведомления, не денег. Исходящие операции по-прежнему сверяются с внешней записью; неопределённый ответ при создании тикета Atera — задача сверки DEV-19.
8. **Replay.** Список недоставленных (`GET /api/v1/integrations/outbox`, `integrations.manage`) показывает тип, ошибку, попытки, завершённые обработчики и **имена** полей payload, без значений. Повтор (`POST …/outbox/replay`): не более 100 сообщений, причина 10–500 символов, подтверждённое количество должно совпасть с тем, что можно повторить сейчас, иначе 409. crm-web записывает `OutboxReplayRequests` и запись аудита (кто, причина, сообщения) в транзакции модуля; применяет запрос crm-worker (роль web не может менять outbox и квитанции, DEV-04). Повтор доставляет сохранённый payload без изменений; передать свой тип или JSON нельзя.
9. **Наблюдаемость и хранение.** Meter `Crm.Outbox`: `crm.outbox.delivered`, `failed_attempts`, `dead_lettered`, `quarantined`, `replayed`, gauge `crm.outbox.backlog` (модуль × состояние) — для DEV-17. Задача `outbox-retention` (ежедневно): доставленные сообщения старше 30 дней, квитанции старше 180 дней, если их сообщение не ждёт доставки ни в одном модуле; недоставленные не удаляются. Повреждённый payload логируется только позицией ошибки (`$.поле`), без текста исключения и значений.
10. **Миграции.** `OutboxDelivery` во всех 15 контекстах (порядок регистра): новые колонки и таблицы, затем перенос старых строк — доставленные → `Processed`, исчерпавшие попытки → `DeadLetter` без автоматического повтора. Только расширение схемы; прежний образ продолжает работать.

## Последствия

- Каждая доставка обработчику модуля стоит одной вставки квитанции и транзакции; блокировки держатся до конца обработчика — обработчики должны оставаться короткими и не открывать свои транзакции.
- Новый обработчик, пишущий в два модуля, падает в тестах и в работе — так и задумано; решение — второй обработчик в другом модуле.
- Ручной повтор теперь штатная операция администратора с аудитом, а не SQL.
- Не заявляется exactly-once для внешних систем: Teams — at-least-once с редким дублем; PowerOffice — поиск заказа по ссылке (ADR-013); Atera — DEV-19.
