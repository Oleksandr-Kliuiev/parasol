# Финансовая модель: обязательные инварианты

Общий контракт для DEV-01…04, DEV-07, DEV-13, DEV-19 и DEV-20. Названия новых сущностей примерные; конкретную схему описать в ADR при реализации. Не менять тарифы, VAT, валюты, proration и округление без отдельного подтверждённого правила.

## Различать четыре идентичности

| Понятие | Что идентифицирует | Что не должно менять идентичность |
|---|---|---|
| Экономическое начисление / charge | Обязанность за определённую услугу, источник и интервал | Новый runId, пересборка, повтор импорта или доставки события |
| Ревизия расчёта | Содержимое начислений, цен, скидок, ручных решений | Повторное чтение или техническая попытка отправки |
| Финансовый снимок / basis | Конкретный утверждённый набор строк плательщика | Повтор отправки и обновление transport status |
| Экспортная операция | Отправку одного снимка в конкретную систему/компанию | Retry, смена worker, повторная доставка outbox |

Существующий `{period}-{organizationId}-{runId}` может идентифицировать транспортную операцию, но не защищает от нового экономического начисления в другом run. Не заменять один случайный ключ другим и не использовать description/amount как уникальную идентичность.

Для контрактов идентичность включает устойчивую серию услуги и покрываемый интервал, а версия ContractLine — происхождение расчёта. Защитить от **перекрывающегося покрытия**, даже если интервалы представлены разными границами: одиночный unique index на даты этого не гарантирует. Допустимы канонические сегменты либо сериализованная проверка пересечений; ADR должен объяснить конкуренцию. При proration сохраняются исходный интервал и обоснование доли. Квартальный/годовой аванс не превращается в повторный месячный долг.

Для часов использовать идентичность подтверждённой allocation и её связи с entry/re-approval; для покупки пакета — отдельное движение покупки; для quote/phase/pending charge — исходное событие и item. Повтор импорта того же источника идемпотентен, две разные покупки не сливаются. Все источники перечислить в реестре провайдеров начислений с тестом каждого. Информационные строки иметь отдельно от платёжной обязанности.

Исходный клиент услуги и плательщик — разные поля. Групповой биллинг не теряет клиента и не меняет уникальность уже выставленного charge при перепривязке parent. В рамках текущего single-tenant продукта не вводить multi-tenant архитектуру; внешний accounting company scope учитывать, чтобы одинаковые external IDs разных подключений не смешивались.

## Пересборка и ручные изменения

Разделить самостоятельную ручную строку, override исходной строки и явное исключение источника (tombstone). У override хранить source key, исходный fingerprint/revision, новое значение, причину, автора и время. Пересборка сопоставляет источник по ключу, а не оставляет старую строку рядом с новой.

Если исходное значение не изменилось, override сохраняется один раз. Если источник изменился или исчез, показать конфликт и потребовать явное решение перед утверждением; не молча отменять override и не молча начислять дважды. После удаления override восстановить актуальный источник один раз. Самостоятельная ручная строка не подавляет чужую строку с похожим текстом.

Контрольный пример: исходные 1000 → override 900 → десять пересборок = одна строка 900. Отдельная ручная строка 2500 сохраняется однократно. Изменение source 1000 → 1100 создаёт видимый конфликт с override 900.

## Согласование конкретного содержания

У прогона монотонная revision и канонический digest финансового содержания. Digest — контроль содержимого, не замена авторизации и транзакции. Хранить фактический снимок, policy version и акт согласования с actor/time/revision. Нормализовать decimal и порядок строк; не вычислять hash из нестабильного порядка JSON.

Любая правка состава, суммы, плательщика, валюты, ставки, скидки или правила расчёта инвалидирует прежние согласования. Технический delivery status не меняет финансовую revision. Порог второго согласующего вычислять заново в транзакции по текущему содержимому. Сохранить исходную семантику: **любое основание клиента строго больше 200000 NOK без VAT**, если именно так настроено действующее правило; 200000 ровно не превышает порог. Не заменять его суммой всего run. Иные валюты/пороги требуют решения DEC-02.

Первый и второй согласующие — разные активные люди с нужными текущими правами; пустой actor и один человек с двумя ролями не обходят правило. Разрешённый порядок переходов задаётся явно, любой порядок не допускает самосогласование. Конкурентная mutation и approve проверяют ETag/revision внутри одной транзакции; устаревшая команда получает конфликт без частичной записи.

## Фиксация и отправка

При утверждении атомарно фиксируются финансовый снимок, согласования, резервы/ledger и событие намерения экспорта. Запись в SQL и вызов внешнего API нельзя считать одной атомарной транзакцией. Outbox доставляется как минимум один раз, каждый consumer защищён от повторного локального эффекта.

Предлагаемые состояния charge: Available → Reserved → Committed → ExportConfirmed. Неизвестный результат экспорта — ReconciliationRequired. Названия можно изменить, но переходы и ограничения должны быть явными. До отправки подтверждённо неиспользованный резерв можно освободить. После внешнего эффекта или неоднозначного timeout резерв не освобождать без сверки. Иначе другой run создаст дубль.

Экспорт отправляет неизменяемый снимок с прежним operation key и payload hash. При timeout после возможного создания заказа сначала искать его по поддерживаемому provider reference и сверять содержимое. Ни новый runId, ни повтор POST без доказанной provider идемпотентности не являются восстановлением. При невозможности уверенно сопоставить — ручное исключение с owner. Не обещать end-to-end exactly once при недокументированных гарантиях API.

Утверждённые суммы и строки защищаются в БД от UPDATE/DELETE runtime-пользователя, включая каскадные пути. Метаданные доставки можно обновлять в отдельно защищённой структуре. Триггеры/права должны учитывать EF generated SQL и OUTPUT, а не просто блокировать любое обновление таблицы.

Новые работы за закрытый период попадают в supplementary run только если не были выставлены. Исправление уже выставленного имеет исходный charge, причину и delta; кредитование не включать без Finance и проверенного PowerOffice API. CRM хранит происхождение начисления; PowerOffice остаётся системой бухгалтерского учёта и фактических оплат.

## Переход со старых данных

1. Expand: добавить совместимые таблицы/поля и явный feature switch, не стирая прежние суммы/ссылки. Прочитать фактические legacy записи, включая пустые external references.
2. Выполнить dry-run сопоставления по проверяемому источнику, интервалу, документу и сумме. Уровни confidence не дают права автоматически объединять неоднозначные начисления.
3. Сверить количество, денежные итоги по клиенту/периоду/валюте, согласования и внешние документы. Сохранить mapping и unresolved rows. Исторические записи без доказанного происхождения маркировать legacy unresolved, не придумывать source ID ради unique index.
4. Finance подтверждает спорные записи; блокируются affected charges, а не теряются данные. Добавлять уникальные ограничения только после успешной сверки.
5. Проверить старую и новую версии приложения на expanded схеме. Разрешать dual write лишь при атомарности и едином источнике истины; не поддерживать два расходящихся расчёта.
6. Включать новую отправку после технических проверок и допуска. Contract/drop старых полей — отдельный поздний шаг после окна отката и подтверждённой полноты backfill.

Rollback приложения не отменяет уже выставленный внешний документ. После начала записи в новую модель допускается только доказанно совместимый rollback или forward fix. Восстановление SQL требует внешней сверки, сохранённых ключей/idempotency mapping, PDF blobs и восстановления privacy suppression. Нельзя возвращать в работу старую копию очереди и автоматически повторять все записи.
