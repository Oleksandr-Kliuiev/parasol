# Правила исполнения

## Приоритет и границы

Текущие прямые инструкции владельца имеют приоритет. Затем применять корневой CLAUDE.md и этот пакет в его области. Устаревшие утверждения о гарантированной неизменяемости PDF, согласований и уникальности выставления не являются доказательствами: аудит выявил нарушения. Спецификации сохраняют силу там, где карточка явно не исправляет установленное противоречие. Изменение бизнес-правила фиксировать решением, а не незаметным изменением теста.

Пакет охватывает все A01…A16 и подготовку продукта к эксплуатации. Не расширять его до новой бухгалтерии, helpdesk вместо Atera или незаказанных AI-функций. Не назначать третьим лицам обязанности от имени пользователя; указанные роли — требуемые владельцы, конкретные люди ещё не подтверждены.

## Рабочий цикл

1. Проверить рабочую копию и инструкции; сохранить пользовательские изменения. На этой исходной точке нет коммитов — нельзя считать untracked файлы временными или удалять их. Рабочая ветка, если создаётся, использует `codex/` либо имя, явно заданное владельцем.
2. Выполнить `python3 docs/claude-opus/validate-package.py --next`. Прочитать PROGRESS и evidence незавершённой задачи. Выбирать по execution_order среди задач с проверенными зависимостями, а не только по номеру.
3. Поставить задачу `in_progress`, записать короткий план конкретного изменения. Крупную карточку разбить на небольшие части, сохранив исходные AC и один общий статус задачи.
4. Перечитать указанные исходники. Добавлять тесты на поведение и инварианты, не копирующие реализацию. Старые findings могут быть уже исправлены: сначала проверять текущую версию.
5. Реализовать изменения во всех затронутых слоях: домен, контракты, API, данные, права, UI и эксплуатация. Не оставлять заглушки за успешным ответом API. Технические имена из карточек — проектные предложения; эквивалентное более простое решение допустимо с объяснением и теми же гарантиями.
6. Выполнить применимые проверки VALIDATION. Каждому AC указать фактический способ, результат и артефакт. Для миграций проверить новую пустую БД и обновление копии старой схемы; для критических переходов — конкуренцию и отказ.
7. Просмотреть весь diff, включая косвенные изменения прав, округления и условий запросов. Обновить документацию и runbook одновременно с изменением поведения.
8. Сохранить `evidence/DEV-xx.md`, обновить статусы, повторно проверить пакет. Если нет внешнего блокера — перейти к следующей задаче. Не останавливаться после создания плана или частичного каркаса.

Не использовать `git add .`, reset/clean или массовую перезапись рабочей копии. Локальные коммиты возможны после проверки явного списка файлов и секретов; push и публикация не следуют автоматически из задания. Удалять только собственные временные контейнеры/файлы с точными идентификаторами. Реальные данные не копировать в evidence, логи, скриншоты, fixture или общедоступные сервисы.

## Состояния и доказательства

`backlog.json` — источник статуса задачи. `acceptance.csv` — результаты отдельных критериев. `external-gates.json` — внешние условия. PROGRESS содержит контекст продолжения, а не отдельную конкурирующую таблицу статусов.

| Статус | Когда применять |
|---|---|
| todo | Реализация ещё не начата |
| in_progress | Идёт реализация или локальная проверка |
| blocked | Нельзя завершить локальную часть без конкретного решения/ресурса; причина и следующий шаг в evidence |
| code_verified | Код реализован, локальные проверки пройдены; оставшиеся внешние проверки перечислены |
| accepted | Все AC имеют pass, evidence актуальны, gates карточки passed, зависимости accepted |

Зависимость `code_verified` разрешает реализацию следующей карточки. Для итоговой приёмки зависимости должны быть `accepted`. Технические части DEV-23 можно готовить заранее; выпуск требует полной приёмки всего объёма.

Результаты AC: `not_run`, `pass`, `fail`, `blocked`. `blocked` содержит точную зависимость от EXT или недостающего условия; не заменяет fail для воспроизведённого дефекта. Для `code_verified` локальные AC должны быть pass; ещё не выполненные внешние AC — blocked с явной ссылкой на EXT в evidence. Нельзя оставить not_run и назвать всю задачу проверенной. Составной AC с внешней частью получает blocked; локальные доказательства сохраняются в его строке evidence.

Исключение DEV-00: AC требует подтвердить существующий дефект. Ожидаемое падение регрессионного теста на исходной версии означает pass **критерия воспроизведения**, но не исправление продукта. В дальнейших карточках старые регрессии обязаны стать зелёными. При DEV-15 и других ранних задачах отдельно записывать известные красные тесты DEV-00; не маскировать их и не требовать преждевременного исправления чужой карточкой. Полный release gate остаётся красным до исправления. Новые неожиданные ошибки запрещают code_verified.

При изменении кода, от которого зависит ранее пройденный AC, сбросить его результат и связанный статус до новой проверки. Записывать SHA и состояние рабочей копии; при отсутствии коммита — manifest проверенных файлов. Контрольный скрипт проверяет согласованность записей, но не доказывает истинность записанного pass.

## Решения и внешние действия

Технические решения внутри объёма принимать самостоятельно, фиксируя важные компромиссы в ADR. Не добавлять обязательное согласование каждой правки. Спрашивать только то, без чего нельзя корректно выбрать бизнес-поведение или выполнить действие в реальной среде.

Если неизвестны роли, retention, корректировки, реальные реквизиты или SLA, продолжать механизмы и synthetic tests с явно отмеченной конфигурацией. Не включать неподтверждённое бизнес-правило в рабочую эксплуатацию. Для каждого внешнего шага подготовить: среда и аккаунт, точный сценарий, данные, ожидаемый побочный эффект, ограничения и обратимость. Учитывать уже данное разрешение; не запрашивать его повторно.

Наличие ключа в окружении не является разрешением отправлять реальные документы. Внешние обращения обычной разработки (официальная документация, согласованные реестры зависимостей) отделять от пользовательских данных и реальных бизнес-операций.

## Передача следующей сессии

Перед остановкой сохранить текущий DEV, завершённую часть, названия/результаты тестов, расположение logs, точный следующий шаг, открытые решения, созданные временные ресурсы. Не писать «всё готово», если осталось непроверенное. Следующая сессия сначала проверяет текущую рабочую копию, потом продолжает; аудит не запускается заново без причины.
