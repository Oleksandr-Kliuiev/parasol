# 06. Безопасность и защита персональных данных

Целевой уровень: **OWASP ASVS 4.0 Level 2**, Microsoft Zero Trust (verify explicitly, least privilege, assume breach).

## 1. Модель угроз (STRIDE, ключевое)

| Угроза | Пример | Контроль |
|---|---|---|
| Spoofing | Кража сессии, фишинг учётных данных | Только Entra ID + MFA (Conditional Access), phishing-resistant MFA для Admin/Finance, `__Host-` cookie HttpOnly/Secure/SameSite=Strict, CAE |
| Tampering | Изменение оснований счёта после утверждения | Доменная неизменяемость + триггер БД, аудит, двойное утверждение крупных сумм |
| Repudiation | «Я не утверждал этот прогон» | Неизменяемый журнал аудита с `oid`, IP, correlation ID |
| Information disclosure | Техник видит маржу; массовая выгрузка клиентов | Полевой RBAC на сервере, аудит экспорта, лимит строк, DLP-метки Purview на выгрузках (R2) |
| Denial of service | Исчерпание квоты Atera API | Собственные rate limiters, circuit breaker, изоляция очередей по системам |
| Elevation of privilege | Пользователь меняет свою роль | Роли только из Entra; в CRM нет UI назначения ролей; PIM для группы `CRM-Admin` |
| Компрометация ключей интеграций | Утечка API-ключа Atera (широкие права на RMM!) | Key Vault + Managed Identity, запрет вывода секретов в логи, ротация, алерт на аномальный объём вызовов |
| Подделка вебхуков | Ложные события от «Atera» | Секрет в пути + заголовок, дедупликация, вебхук только триггерит повторное чтение из API (данным вебхука не доверяем) |

## 2. Аутентификация
- **SEC-AUTH-01.** Единственный провайдер — Entra ID тенант Компании; регистрация single-tenant, `Assignment required = Yes`.
- **SEC-AUTH-02.** Conditional Access для приложения CRM: MFA обязательна; для ролей Admin/Finance — phishing-resistant методы (FIDO2 / Windows Hello for Business / passkey в Microsoft Authenticator); вход только с compliant или hybrid-joined устройств (рекомендация, **подтвердить**); блокировка входа из стран вне списка.
- **SEC-AUTH-03.** Гостевые (B2B) пользователи не допускаются, пока явно не назначены.
- **SEC-AUTH-04.** Сессия: скользящая 8 ч, абсолютная 12 ч; повторная проверка через refresh token каждые 60 мин; выход — локальный + Entra single sign-out. Сессия хранится на сервере (`identity.UserSessions`): выход закрывает её для всех реплик, и копия cookie не принимается (DEV-10). Ответ Entra при повторной проверке «токен не выдаётся» завершает сессию; если Entra недоступен, проверка откладывается на 5 минут, а не обрывает каждый запрос.
- **SEC-AUTH-07.** Роли берутся из серверного подтверждения каталога, а не из cookie (DEV-10, [ADR-019](adr/ADR-019-sessions-and-privilege-freshness.md)): синхронизация назначений приложения CRM каждые 2 минуты (прямые назначения и прямые члены групп, PIM, отключённые аккаунты и роли не считаются) или вход. Снятие роли действует на всех репликах за ~2,5 минуты (цель DEC-05 — ≤ 5 минут, замер — EXT-02). Привилегированные изменения (`Permissions.Privileged`) и массовый экспорт требуют подтверждения не старше 5 минут — иначе `403 AUTH_REVERIFY_REQUIRED` (fail-closed); чтение без подтверждения — не дольше 8 часов. Production не запускается без общего набора ключей Data Protection.
- **SEC-AUTH-05.** Учётные данные приложений — сертификаты (Key Vault, автопродление), не client secrets.
- **SEC-AUTH-06.** Сервисный аккаунт для Partner Center/GDAP: MFA, отдельная CA-политика (только с IP NAT Gateway CRM после первичного consent), без лицензии Exchange, мониторинг входов в Entra Sign-in logs.

## 3. Авторизация
- **SEC-AZ-01.** Роли → набор разрешений (permissions) определены в коде (`Crm.Authorization`), например: `customers.read`, `customers.write`, `finance.read`, `billing.approve`, `time.approve`, `admin.integrations`.
- **SEC-AZ-02.** Каждый эндпоинт помечен политикой; тест в CI проверяет, что нет эндпоинтов без политики (кроме `/bff/login`, `/health`, `/webhooks/*` с собственной проверкой).
- **SEC-AZ-03.** Проверки на уровне записи (DEV-09, [ADR-018](adr/ADR-018-record-scope.md)): Sales видит и меняет свои предложения (владелец текущей версии), Technician — назначенные проекты (руководитель, участник команды, исполнитель задачи); Admin, Management и Finance видят все предложения, все роли кроме Technician — все проекты (права `sales.quotes.all`, `projects.all`). Охват применяет модуль-владелец в каждом запросе (`IRecordScope`) — в списках до фильтров, при загрузке по id (вне охвата — 404, как для несуществующей записи), в документах и контрактах модулей; фильтры клиента (`mine`, `ownerId`, `managerId`) только сужают. Владельца предложения меняет передача (аудит); проект без назначений и предложение без владельца видят только роли с полным охватом. Режим `Authorization:RecordScope` (`Restricted` по умолчанию, `Open` — исключение окружения, runbook 11). Матрица — предложение до EXT-01 (DEC-01).
- **SEC-AZ-04.** Финансовые поля (себестоимость, маржа, суммы счетов, задолженность) удаляются из DTO сериализатором по атрибуту `[FinanceSensitive]`, если нет `finance.read`.
- **SEC-AZ-04a.** Документы с ценами (PDF предложения) не проходят через сериализатор DTO, поэтому право проверяется отдельно: без `finance.read` `GET /api/v1/sales/quotes/{id}/pdf` отвечает 403 `SAL_QUOTE_PRICES_HIDDEN`; права изменения предложений для скачивания не нужно (Finance скачивает). Сохранённые PDF (DEV-08) доступны только через этот путь: контейнер `documents` приватный, у хранилища выключены публичный доступ, публичная сеть и ключи доступа (нет SAS по ключу учётной записи), запись предложения не раскрывает ключ объекта; ответ — `Cache-Control: no-store`, `attachment`, `nosniff`. Скидку сверх предела роли согласовывает отдельное право `sales.discount.approve` (BR-SAL-05), и согласование фиксируется в записи предложения и в журнале аудита.
- **SEC-AZ-05.** Администрирование ролей: группы `CRM-*` в Entra; группа `CRM-Admin` — через Privileged Identity Management (активация на время, с обоснованием); ежеквартальный Access Review групп. Роли назначаются группам напрямую: вложенные группы ролей приложения не дают (так работает Entra, и так считает синхронизация ролей CRM). Окончание активации PIM снимает права в CRM за ~2,5 минуты (SEC-AUTH-07).

## 4. Защита приложения
- HTTPS only, HSTS (`max-age=31536000; includeSubDomains`), TLS 1.2+.
- Заголовки: строгая CSP (`default-src 'self'; frame-ancestors 'self' teams.microsoft.com *.teams.microsoft.com` — для вкладки Teams в R2), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`.
- CSRF: `SameSite=Strict` + заголовок `X-CSRF` на всех изменяющих запросах.
- Валидация входа на сервере (FluentValidation), параметризованные запросы (EF Core), экранирование вывода (React), санитизация HTML в заметках (DOMPurify на клиенте + HtmlSanitizer на сервере).
- Загрузка файлов: белый список типов, лимит 25 МБ, проверка сигнатуры, сканирование Microsoft Defender for Storage.
- Rate limiting API на пользователя (ASP.NET Core rate limiter): 300 запросов/мин; экспорт и витрина для Power BI — 10/час.
- Витрина для Power BI (FR-RPT-03) — обычный эндпоинт `/api/v1/reports/mart/{набор}` за тем же входом и теми же правами (`reports.mart`); прямой доступ к базе наружу не открывается, отдельных SQL-логинов нет.
- Зависимости: Dependabot/Renovate, `dotnet list package --vulnerable` и `npm audit` в CI, блокировка сборки при Critical.
- SAST: CodeQL; секреты в репозитории: GitHub secret scanning + push protection; DAST: OWASP ZAP baseline на `test` еженедельно.

## 5. Секреты и ключи

| Секрет | Хранение | Ротация | Доступ |
|---|---|---|---|
| Сертификаты приложений Entra | Key Vault (certificates) | Автоматически, 12 мес. | MI `crm-web`, `crm-worker` |
| Atera API key | Key Vault (secret) | 6 мес. + при увольнении администратора Atera | MI `crm-worker` (тикеты тоже создаёт worker через очередь исходящих операций) |
| PowerOffice Client Key, Subscription Key | Key Vault | 12 мес. / по требованию | MI `crm-worker` |
| Refresh token сервисного аккаунта Partner Center | Key Vault | Автоматически при использовании | MI `crm-worker` |
| Секрет вебхука Atera | Key Vault | 12 мес. | MI `crm-web` |
| Ключ Data Protection (обёртка) | Key Vault (key) | 90 дней | MI `crm-web` |
| Подключение к SQL | Без пароля — Entra-аутентификация Managed Identity, у каждого хоста своя: `id-crm-app` → роль `crm_web`, `id-crm-worker` → `crm_worker`, без `db_datawriter` и DDL ([runbook 08](runbooks/08-database-permissions.md)) | — | MI |

Key Vault: RBAC-модель, soft delete + purge protection, private endpoint, диагностические логи в Log Analytics; доступ людей — только через PIM. Роли, читающие значения секретов, выдаются на конкретный секрет, а не на хранилище: crm-web — только секрет своего сертификата, crm-worker — только секреты поставщиков (DEV-04-AC05, ADR-014).

## 6. Инфраструктура
- Azure SQL, Storage, Key Vault — без публичного доступа, только private endpoints.
- Azure SQL: TDE (service-managed key; customer-managed — при требовании), Entra-only authentication, Microsoft Defender for SQL, аудит в Log Analytics.
- Container Apps: минимальные образы (`mcr.microsoft.com/dotnet/aspnet:10.0-noble-chiseled`), запуск не от root, сканирование образов Defender for Containers.
- Microsoft Defender for Cloud: Secure Score ≥ 80 % для подписки CRM.
- Отдельные подписки Azure для `test` и `prod`; деплой в `prod` — только из CI через федеративные учётные данные (OIDC), без ручного доступа Contributor (break-glass через PIM).

## 7. Аудит и мониторинг безопасности
- **Журнал аудита CRM** (`audit.AuditEntry`): создание/изменение/удаление, слияние, экспорт, стирание по запросу субъекта (`Erase`: номер дела и поля, без значений), утверждения, изменение настроек интеграций, просмотр финансовых отчётов. Пользователям — только чтение. Роли приложения пишут его только `INSERT` в транзакции бизнес-изменения; `UPDATE`/`DELETE` запрещены правами и триггером. Единственное изменение — процедура retention под отдельной ролью: обнуляет персональную часть старых записей модулей с утверждённой политикой (DEC-03), аудит финансовых записей не трогает никогда. Цепочка SHA-256 по фактам записей с контрольными точками в Log Analytics обнаруживает изменение администратором БД (защиты от него хэш в той же БД не даёт — ADR-014, [runbook 08](runbooks/08-database-permissions.md)).
- Логи приложения не содержат: токены, секреты, тела писем, полные персональные данные (маскирование e-mail/телефонов в структурированных логах).
- Microsoft Sentinel (если используется Компанией) — подключение Entra Sign-in logs, аудит Key Vault/SQL и событий CRM (вход с новых стран, массовый экспорт, изменения в интеграциях).

## 8. GDPR и персональные данные

### 8.1 Категории данных
| Субъекты | Данные | Основание (ст. 6 GDPR) |
|---|---|---|
| Контакты клиентов | Имя, должность, e-mail, телефон, переписка (метаданные), участие во встречах, тикеты | Договор (6(1)(b)) / законный интерес (6(1)(f)) |
| Лиды | Имя, компания, контакты, источник | Законный интерес (B2B); согласие — для маркетинга |
| Конечные пользователи клиентов (из Atera: имя устройства, пользователь) | Имя пользователя, имя устройства | Договор с клиентом (Компания — **обработчик** от имени клиента) |
| Сотрудники Компании | Учётная запись, записи времени, действия в системе | Трудовой договор, законный интерес |

Специальные категории данных не обрабатываются; поле «заметки» сопровождается подсказкой не вносить такие данные.

### 8.2 Требования
- **SEC-GDPR-01.** Протокол обработки (ст. 30) обновляется с запуском CRM; DPIA проводится на Этапе 0 (обработка данных пользователей клиентов из RMM и тенантов).
- **SEC-GDPR-02.** Данные хранятся в Norway East (геобэкап — Norway West); субпроцессоры: Microsoft (DPA), Atera (DPA; данные хранятся у Atera — проверить регион), PowerOffice (Норвегия).
- **SEC-GDPR-03.** Экспорт данных субъекта (DEV-11, [ADR-020](adr/ADR-020-data-subject-requests-and-retention.md)):
  - Admin с правом `privacy.manage` открывает дело на контакт или лид, записывает способ проверки личности и выгружает JSON по модулям: карточка, роли у клиентов, лид и предложения, активности и сохранённые письма, тикеты-зеркало, внешние связи и зеркала, история изменений. У каждого раздела перечислено, что в выгрузку не вошло;
  - срок ответа — месяц от даты получения, просрочка видна;
  - SHA-256 выгрузки записывается в дело; экспорт требует свежего подтверждения ролей (ADR-019) и ограничен по частоте.

  Передача человеку — [runbook 13](runbooks/13-personal-data.md).
- **SEC-GDPR-04.** Стирание выполняется по просмотренному плану с подтверждением номером дела:
  - контакт получает `Anonymized-<hash id>` без контактных данных, роли у клиентов и активности удаляются, у тикетов-зеркала и внешних зеркал остаются только ключи, исходящие операции отзываются;
  - принятые предложения и их документы сохраняются до 31.12 пятого года (bokføringsloven);
  - юридическое удержание сохраняет одну запись с объяснением и обязательной датой окончания;
  - история изменений и снимки документов скрываются сразу, а физически их очищают процедуры оператора `crm_privacy`;
  - ключевой хеш адреса и внешние ссылки блокируют повторный импорт;
  - манифест вне базы повторно применяется после восстановления (DEV-11).
- **SEC-GDPR-05.** Сроки хранения ([04 § 8](04-data-model.md#8-сроки-хранения)) применяет ночная задача `privacy-retention` ограниченными пачками и с отчётом по классам.
  - По умолчанию она только считает. Удаляет только в режиме Apply и только классы со сроком, который DBA записал в `privacy.RetentionPolicies` по утверждённой матрице (DEC-03, EXT-07). Предложенные сроки не применяются.
  - События outbox о людях несут только id.
- **SEC-GDPR-06.** Письма из Outlook: в БД CRM — только метаданные; тело загружается из Graph с правами текущего пользователя и не кэшируется на сервере.
- **SEC-GDPR-06a.** Уведомления (S8) адресованы сотрудникам, а не клиентам: хранятся вид уведомления и параметры (номер договора, название клиента, суммы) — не переписка. Сводка уходит только на адрес сотрудника из Entra ID, с `saveToSentItems: false`, и содержит те же параметры; тексты, введённые пользователями, экранируются. Сотрудник может отключить письма или отдельные виды, а уведомления удаляются вместе со сроками хранения ([04 § 8](04-data-model.md#8-сроки-хранения)).
- **SEC-GDPR-06b.** Переписка и документы клиента остаются в Microsoft 365 (S10): вкладка «Почта» читает ящик вошедшего сотрудника его собственным делегированным токеном и ничего не сохраняет, пока человек не нажмёт «Сохранить в CRM» — тогда хранятся тема, отправитель, время и ссылка, но не тело письма. Файлы клиента лежат в SharePoint; CRM хранит только идентификатор папки и не проксирует содержимое, поэтому права на документы остаются правами SharePoint.
- **SEC-GDPR-07.** Данные для AI-функций (R3) не покидают EU Data Zone и не используются для обучения моделей.
- **SEC-GDPR-08.** Инцидент с персональными данными: runbook с уведомлением Datatilsynet ≤ 72 ч.

## 9. Резервное копирование и непрерывность
- Azure SQL: PITR 35 дней, LTR — ежемесячные копии 12 мес. и ежегодные 5 лет; geo-redundant backup storage.
- Blob: soft delete 30 дней, versioning.
- Ежеквартальный тест восстановления в изолированное окружение с проверкой целостности биллинговых данных.
- Недоступность CRM не останавливает бизнес: тикеты ведутся в Atera, счета — в PowerOffice; runbook описывает ручной биллинг на время аварии.
