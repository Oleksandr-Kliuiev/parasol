## Required findings

**F1 (P2) Time precision rule is not implementable as written.** Brief lines 80 and 83 require seven-digit UTC precision for half-open bounds and ordering, and line 142 adds an "exact sub-ms bounds" test. The stored sort column is millisecond resolution (`prisma/migrations/202610081100_stage2_m365_signin_windows/migration.sql:123`, occurredAt TIMESTAMP(3)), S2-B truncates to milliseconds on ingest (`packages/m365/signin-rows.ts:9-11,37`), and the canonical DTO text has a variable-length fraction (`connectors/microsoft365/dto-common.ts:57-70`), so it is not lexicographically sortable. Leaf, attempt and retention bounds are also millisecond. Consequence: keyset ordering, the keyset predicate, `total`, and the cursor last-key cannot agree on a sub-millisecond instant; an implementer either silently truncates (forbidden by line 80) or invents a derived key the brief never specifies. Correction: state one rule. Recommended: read-surface from/to accept at most three fraction digits and reject more with a validation error (no silent truncation), ordering and keyset use the stored column plus sourceId and contentHash, and line 142 is reworded to "sub-ms input rejected, ms bounds exact". If seven-digit semantics are kept, the brief must define the fixed-width tiebreak key derived from the DTO fraction and require it identically in ORDER BY, keyset predicate, bound filter, count and cursor.

**F2 (P2) Cursor size is unbounded against existing hard limits.** Lines 87–90 bind actor, workspace, client, permission evaluation, observation, connection, interval, limit, last key and fingerprint; line 116 only says the CLI flag "may need" a bound. Worst-case raw claims (five IDs up to 128 chars, sourceId up to 256, hash 64, fingerprint 64) exceed 1.7 KB after base64url plus MAC. The tool surface caps the whole parameters JSON at 2048 characters (`apps/api/src/http-boundary.ts:65`), the CLI caps every flag at 256 (`packages/ops/commands.ts:110`), and Stage 1 cursors are 400 (`http-boundary.ts:38`, `packages/tools/registry.ts:80`). Consequence: paging works in tests with short synthetic IDs and fails for long real IDs on the tools surface, contradicting line 96 and C4. Correction: encode only the last key and fingerprint raw and bind all other inputs through one SHA-256 digest inside the signed claims; fix one shared cursor maximum (for example 1024 chars) in the shared parameters module and apply it to the HTTP query, the tool parameter pattern and an explicit CLI exception; verify that the longest issuable cursor plus the other parameters stays under the 2048 body cap.

**F3 (P3) Fixed 30-second cleanup bound can make retention permanently unachievable.** Lines 128–129 mandate a 30 s statement timeout with full rollback and acknowledge no batching. The frozen routine processes every M365 connection of the client in one call (`prisma/migrations/202610081200_stage2_m365_cleanup_routine/migration.sql:37-104`), and each deleted membership or leaf fires row triggers with extra lookups (`202610081150…/migration.sql:155-159, 218-224`). With up to 100,000 rows per root (`connectors/microsoft365/contract.ts:56`), a backlog that once exceeds 30 s will exceed it every time, so payload stays on disk indefinitely while reads merely hide it. Correction: make the statement timeout an operator-configurable value within a sanctioned range (for example 30 s to 10 m, default 5 m) rather than a constant, keep the 5 s lock timeout, and document the failure mode and recourse in RUNBOOK. This is not a caller-supplied deletion predicate and needs no SQL change.
