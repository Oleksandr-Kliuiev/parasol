# Runbook 03. Восстановление базы на момент времени

Когда: данные испорчены ошибочной операцией (массовое удаление, неудачная миграция, неверный импорт), а не при падении сервиса — при недоступности Azure SQL см. § 5.

Роли: **Contributor** на группу ресурсов, доступ к Key Vault. RPO ≤ 1 ч, RTO ≤ 4 ч ([07 §2](../07-nfr-devops.md)).

## 1. Остановить запись
```bash
az containerapp revision set-mode -g rg-crm-prod -n crm-worker --mode single
az containerapp update -g rg-crm-prod -n crm-worker --min-replicas 0 --max-replicas 0
```
Worker остановлен: не идут синхронизации, outbox и биллинг-прогоны. Веб оставляем — пользователи видят данные, но предупредите их в Teams.

Квитанции обработчиков событий (`<схема>.InboxReceipts`, DEV-07) лежат в той же базе и восстанавливаются вместе с событиями и данными: недоставленные на момент копии события будут доставлены, уже обработанные — нет (runbook 09 §6). Внешние системы не откатываются — сверка заказов по ADR-013.

Документы предложений (DEV-08) хранятся вне БД, в контейнере `documents`: до запуска worker приостановите задачу `quote-document-orphans` и сверьте записи с объектами по runbook 10 §3.

Альтернатива, если испорчена одна интеграция, а не база: поставьте её на паузу (**runbook 05**) — восстановление не понадобится.

## 2. Определить точку восстановления
```bash
az sql db show -g rg-crm-prod -s sql-crm-prod -n crm --query "{earliest:earliestRestoreDate}"
```
Точку берут за минуту **до** вредной операции: время есть в журнале аудита (`/admin/audit`, фильтр по пользователю и действию) и в Application Insights.

## 3. Восстановить рядом, не поверх
```bash
az sql db restore -g rg-crm-prod -s sql-crm-prod -n crm \
  --dest-name crm-restore-$(date +%Y%m%d%H%M) --time "2026-09-24T09:15:00Z"
```
Восстановление всегда создаёт **новую** базу: боевая остаётся нетронутой, пока вы не решите переключиться.

## 4. Проверить копию
Подключитесь к `crm-restore-…` и сверьте: число организаций, последний биллинг-прогон и его основания, записи времени за текущий месяц. Сверку делает Finance, а не только дежурный.

Копия приносит с собой роли, права и триггеры защиты (ADR-014): пользователи `id-crm-app-<env>` и `id-crm-worker-<env>` в ней те же. Проверьте, что их членство не шире своей роли, а триггеры включены ([runbook 08 §1–2](08-database-permissions.md)):
```sql
SELECT OBJECT_NAME(parent_id) AS [Table], name, is_disabled FROM sys.triggers;
```
Копию данных в утверждённых основаниях **не правят** руками; если без этого нельзя — только администратор БД по [runbook 08 §6](08-database-permissions.md#6-действия-администратора-бд), затем полная проверка целостности аудита.

## 5. Переключение
1. Переименуйте базы (несколько секунд простоя):
   ```bash
   az sql db rename -g rg-crm-prod -s sql-crm-prod -n crm --new-name crm-broken-$(date +%Y%m%d)
   az sql db rename -g rg-crm-prod -s sql-crm-prod -n crm-restore-<метка> --new-name crm
   ```
2. Перезапустите приложения: `az containerapp revision restart …` для `crm-web`, затем верните worker (`--min-replicas 1`).
3. Проверьте `/health/ready` и `/health/integrations` (**runbook 05 §4**).
3a. **Стирания по запросам субъектов (DEV-11).** Если после точки восстановления людей стирали, API отвечает пользователям `503 PRIVACY_REPLAY_PENDING`, а синхронизации пропускаются, пока worker не применит манифесты удаления из хранилища документов заново. Задача `privacy-replay` запускается при старте worker и каждые 5 минут. Затем повторите процедуры оператора: `audit.ClearErasedPayloads`, `sales.ClearErasedDocuments` ([runbook 13 §5](13-personal-data.md#5-восстановление-базы-из-резервной-копии)). Хранилище документов назад не откатывайте: манифесты — единственный след стираний после точки восстановления.
4. Запустите задачу миграций (`caj-crm-migrate-<env>`): она заново применит права и сопоставит идентичности, если копия старше последнего развёртывания. Затем запустите `audit-integrity-full` (Admin → Задания): контрольные точки копии должны совпасть с её записями. Якоря `AUDIT_CHECKPOINT` в Log Analytics, записанные после точки восстановления, относятся к потерянной ветке (номера записей в копии будут выданы заново) — зафиксируйте точку восстановления и последний совпадающий якорь в отчёте об инциденте, чтобы сверка по [runbook 08 §5](08-database-permissions.md#5-целостность-аудита) не принимала это расхождение за подмену.

## 6. После
- Всё, что произошло между точкой восстановления и переключением, потеряно: счета и часы за этот промежуток заводят заново по журналу аудита сломанной базы (она сохранена как `crm-broken-…`).
- Если были выгрузки в PowerOffice после точки восстановления, сверьте заказы. Повторная отправка восстановленного основания сначала ищет заказ по ключу `{период}-{клиент}-{прогон}` и отмечает найденный; основание, отправка которого началась и осталась без ответа, ждёт сверки и второй раз не отправляется (ADR-013, runbook 04 §3a). Найти заказ по ссылке может не каждый ответ PowerOffice: до проверки на реальном API (DEV-19) сверяйте выгрузки после точки восстановления вручную, прежде чем включать worker.
- Сломанную базу храните 30 дней, затем удаляйте.
- Запишите инцидент: что удалили, кто, какой точкой восстановились, что доввели вручную.
