# Runbook 09. Недоставленные события: dead letter, карантин и повтор

Когда: в «Администрирование → Интеграции → Доставка событий» есть строки, растёт метрика `crm.outbox.dead_lettered` / `crm.outbox.quarantined`, или пользователь говорит, что после действия «ничего не произошло» (не появился черновик договора, начисление, отметка часов).

Роли: **Admin CRM** (право `integrations.manage`). Модель доставки — [ADR-016](../adr/ADR-016-outbox-delivery.md).

## 1. Что видно
Панель показывает по модулям, сколько событий ждёт доставки, сколько стали dead letter и сколько в карантине, и список недоставленных:
- **Dead letter** — обработчик падал 10 раз подряд (пауза между попытками растёт от 10 с до часа, всего около полутора часов). Сообщение больше не берётся само.
- **Карантин** — сохранённое сообщение невозможно прочитать (payload не соответствует типу события) или тип события неизвестен текущей версии (после 10 попыток).
- **Завершённые обработчики** — кто уже выполнил свою часть; при повторе они пропускаются.
- **Последняя ошибка** — текст ошибки каждого упавшего обработчика.
- **Поля** — только имена полей события. Значения payload не показываются и не пишутся в общие логи: в событиях бывают персональные данные.

Через API:
```bash
curl -s -H "X-CSRF: 1" "https://crm.<домен>.no/api/v1/integrations/outbox?status=DeadLetter" | jq '.items[] | {module, eventType, attempts, lastError, deliveredHandlers}'
```

## 2. Диагностика
1. По `lastError` и типу события определите, чей обработчик падает (имя класса перед двоеточием).
2. Подробности — в журнале crm-worker (Log Analytics) по идентификатору сообщения: `traces | where message has "<id>"`. Для карантина в журнале есть позиция ошибки (`$.поле`), но не значение.
3. Типичные причины: недоступна внешняя система (тогда сначала runbook 05, пауза), ошибка данных в модуле-получателе, сообщение старого формата после выпуска (карантин), ошибка в коде обработчика (нужен исправляющий релиз).

## 3. Повтор после исправления причины
Повторяйте **только после** устранения причины — иначе сообщение снова станет dead letter через 10 попыток.

В панели: отметьте сообщения (не более 100 за раз) → **«Повторить выбранные»** → проверьте количество и типы в диалоге → укажите причину (что исправлено, не менее 10 символов) → подтвердите. Через API:
```bash
curl -X POST https://crm.<домен>.no/api/v1/integrations/outbox/replay \
  -H "X-CSRF: 1" -H "Content-Type: application/json" \
  -d '{"messages":[{"module":"contracts","id":"<id>"}],"reason":"Исправлен справочник SLA, релиз 2026.10.4","expected":1}'
```

Что происходит:
- crm-web записывает запрос и запись аудита (кто, когда, причина, какие сообщения); `expected` должно совпасть с числом сообщений, которые можно повторить **сейчас** — если кто-то уже повторил или сообщение доставлено, ответ 409 `OUTBOX_REPLAY_STALE`, обновите список;
- crm-worker в течение нескольких секунд возвращает сообщения в очередь (`Replays` +1, попытки с нуля) и доставляет **сохранённый payload без изменений** только обработчикам, которые ещё не завершены;
- обработчик, который уже сделал свою работу (квитанция в его модуле), ничего не повторяет.

Повторить «отредактированное» сообщение нельзя по замыслу: если payload неверен, правильный путь — исправить данные в модуле-источнике (событие возникнет заново) или релиз, который умеет читать старый формат.

## 4. Карантин неизвестного типа после выпуска
Сообщение записал более новый образ, а обработал старый (или наоборот, тип удалён). После выпуска версии, знающей тип, повторите сообщения из карантина как в § 3. Если тип удалён намеренно — сообщение остаётся в карантине как свидетельство; удалять строки outbox вручную нельзя.

## 5. Миграция DEV-07 остановилась с ошибкой 51041
`CONTRACT_QUOTE_DUPLICATES`: в БД есть несколько договоров, созданных из одного принятого КП (результат гонки до DEV-07). Миграция ничего не меняет и останавливается: дубль мог уже выставляться в счетах.
```sql
SELECT SourceQuoteId, Id, Number, Status, IsDeleted, CreatedAt
FROM contracts.Contracts
WHERE SourceQuoteId IN (SELECT SourceQuoteId FROM contracts.Contracts WHERE SourceQuoteId IS NOT NULL
                        GROUP BY SourceQuoteId HAVING COUNT(*) > 1)
ORDER BY SourceQuoteId, CreatedAt;
```
Finance и владелец договоров решают, какой договор настоящий; лишний — отменяется в CRM штатно, а связь с КП у него снимает администратор БД (`UPDATE contracts.Contracts SET SourceQuoteId = NULL WHERE Id = …`, с записью в журнал инцидента). Затем развёртывание повторяется.

## 6. После восстановления БД из резервной копии
Квитанции обработчиков хранятся в той же базе, что и события и бизнес-данные, поэтому восстанавливаются согласованно: события, которые на момент копии не были доставлены, будут доставлены, а уже обработанные — нет. Внешние системы не откатываются: см. runbook 03 и сверку заказов (ADR-013).

## 7. Хранение
Задача `outbox-retention` (03:15 по Осло) удаляет доставленные сообщения старше 30 дней, квитанции старше 180 дней (если их событие не ждёт доставки ни в одном модуле) и применённые запросы повтора старше 180 дней. Dead letter и карантин не удаляются автоматически.
