# 15 — Мониторинг и разбор исключений (DEV-17)

## Владельцы и включение

Рабочее место: **Администрирование → Интеграции → Мониторинг**. Доступ — `integrations.manage`; финансовые сигналы дополнительно требуют `finance.read`, себестоимость — `finance.cost.read`. Ответственный выбирается из активных пользователей CRM; назначение, статус и комментарий сохраняются с аудитом. Конкурирующее изменение возвращает 412: перечитать данные перед повтором.

EXT-01 / DEC-09 ещё не принят. Конкретные люди, резервный исполнитель, часы поддержки, сроки реакции и разрешённые получатели должны быть подтверждены PO + operations + Finance. Не подставлять вымышленные адреса. В `infra/main.bicep` параметры `monitoringOperationsOwner`, `monitoringFinanceOwner`, `monitoringOperationsEmails`, `monitoringFinanceEmails` заполняются для конкретной среды; `monitoringNotificationsEnabled` по умолчанию false. Доставка включается только при наличии имени владельца, хотя бы одного адреса и явного включения. `monitoringRunbookUrl` должен указывать на доступную оператору опубликованную копию этого runbook. До заполнения адресатов возможен только просмотр состояния.

До внешней приёмки закрепить принятые значения всех переопределяемых `monitoring*` параметров в `infra/env/<env>.bicepparam`: владельцы, адресаты, включение, URL runbook, пороги и свежесть. Обычный release использует этот файл. Значения, переданные только одноразовым `--parameters`, следующий release сбросит к значениям из файла или defaults; такое временное включение не является устойчивой настройкой. Конкретные адреса и имена добавляются только после подтверждения EXT-01.

Первая реакция: открыть конкретный сигнал, назначить ответственного, установить «В работе», записать причину и следующий шаг. Не помещать в комментарии суммы, токены, клиентские документы или данные контактных лиц. Сначала устранить причину; повторять операции только после сверки внешнего эффекта. При невозможности восстановления — передать подтверждённому резервному исполнителю; его имя и срок эскалации заполняются в протоколе EXT-01, а не считаются уже назначенными.

## Свежесть и паузы

`integration.SyncSuccesses` хранит последнее полное успешное завершение каждого потока. Failed, Skipped, частичный успех (`Failed > 0`), отмена и проверка соединения не освежают данные. Успешный quiet run обновляет отметку, даже если запись о запуске не попала в журнал. Retention журнала не удаляет отметку. Миграция переносит последние полные успехи из старого журнала; если доказательства успеха нет, показывается «Ещё не было успешного обновления».

Atera `atera-tickets` и `atera-tickets-recent`: 15 мин с последнего полного успеха. Оба задания должны запускаться с интервалом не более 10 мин; defaults — открытые тикеты `*/10 * * * *`, полный проход недавних тикетов `5-59/10 * * * *`, со сдвигом на 5 мин. При EXT-01 проверить существующие переопределения `TicketSyncCron` / `RecentTicketSyncCron`, длительность и квоты: прежний ежечасный recent-проход не обеспечивает 15-минутную свежесть. PowerOffice `poweroffice-invoices`: 90 мин — это свежесть снимка invoices/outstanding, а не доказательство полноты банковских платежей. Остальные потоки: `Monitoring:FreshnessMinutes` (начальное значение 1440), переопределение `Monitoring:Freshness:<job>` через `monitoringFreshness`, ожидаемые ещё не запускавшиеся потоки — `Monitoring:Streams:[{System,Job}]`. Порог PDF — `Monitoring:DocumentPreparingMinutes`, начальное значение 15.

Намеренная пауза показывается отдельной категорией. При паузе/disabled свежесть не становится Fresh; предупреждение о просроченной sync подавляется, возраст последнего успеха остаётся видим. При maintenance подавляются задержка очереди, outbound и sync; heartbeat, SQL, dead letters и потеря телеметрии продолжают контролироваться. Восстановление источника не влияет на readiness CRM — независимые функции продолжают работать.

## Повторные операции

Выбрать конкретные сообщения/операции (не более 100), проверить список с идентификаторами, указать причину 10–500 символов и подтвердить состав. Сервер повторно проверяет каждую запись и подтверждённое поколение состояния (outbound ETag / число replay outbox); результат содержит статус по каждому элементу. Повторное одновременное нажатие сериализуется в SQL. Устаревшая выборка возвращает 409 и статусы Available/Unavailable; обновить список и подтвердить новый состав. Для outbox запросы записываются с аудитом по модулям, применяет их worker, уже выполненные обработчики защищены inbox receipts. При частичном сбое между модулями ответ OUTBOX_REPLAY_PARTIAL перечисляет Requested / Unknown / NotRequested. Unknown означает, что результат commit нельзя подтвердить. Перечитать список: принятые запросы видны как Replay requested; не считать сетевой сбой доказательством отсутствия запроса. То же старое подтверждение после быстрого повторного сбоя worker отклоняется; нужен новый просмотр состава.

Завершить разбор можно после устранения причины. Исчезнувший сигнал с незавершённым разбором остаётся на экране с отметкой «Восстановлено»; сохранить итоговый комментарий и статус «Решено». Показаны до 200 последних таких кейсов с общим числом; старые доступны по ключу через triage API. При повторном появлении причины старое «Решено» показывается как «Открыто», чтобы новый сбой не пропал из сохранённого фильтра. Запись и аудит предыдущего разбора сохраняются; финансовые права проверяются и для исчезнувших сигналов. Retention `integration.exception-triage` удаляет только старые resolved notes по отдельно принятой политике DEV-11/EXT-07; без такой политики ничего автоматически не удаляется.

<a id="financial"></a>
## Финансовые исключения

- `Unbilled`: невыставленные PendingCharges с ChargeableFrom до начала текущего месяца (Europe/Oslo). Проверить прогон и причины задержки; мониторинг не создаёт начислений.
- `ReconciliationRequired`: основания с неизвестным результатом внешнего экспорта. Сначала сверка PowerOffice, затем решение по runbook 02/03; слепой retry недопустим.
- `LegacyUnresolved`: неоднозначные старые начисления, решение Finance / EXT-01.
- `BillingConflict`: активные конфликты строк неотменённых/неэкспортированных оснований. Разобрать источник до согласования.
- `EstimatedQuantity` (`billing:estimated`, DEV-19): открытые (не экспортированные и не отменённые) основания с `BIL_STALE_QUANTITY`, `BIL_NO_DEVICE_SNAPSHOT` или `BIL_INCOMPLETE_HOURS` — количество взято из устаревшего чтения, из живого списка устройств или при неполном импорте часов. Только счётчик; можно ли выставлять такие основания, решает бухгалтерия. Сигнал гаснет после экспорта/отмены основания или повторного сбора со свежими данными. Порог — `Billing:StaleQuantityDays` (3).
- `LicenseDiscrepancy`: число клиентов, у которых NOK-себестоимость лицензий за предыдущий календарный месяц превышает выручку лицензий CRM по существующей модели reconciliation. Это индикатор для сверки, не бухгалтерское заключение; другие валюты не складываются с NOK. Детали — в финансовом отчёте под `finance.cost.read`.

Метрики, алерты и общий экран содержат только количества и возраст, без сумм и клиентских идентификаторов. При устранении причины contributor выдаёт 0, позволяя алерту восстановиться.

<a id="mapping"></a>
## Сопоставления

Проверить внешние записи без ExternalLink и активные CSP-подписки без клиента или продукта. В «Сопоставлениях» выбрать доказуемое соответствие; не объединять клиентов по догадке. После сопоставления обновить экран и проверить уменьшение счётчика.

<a id="documents"></a>
## Подготовка документов

`DocumentPreparing` — PDF остаётся Preparing дольше настроенного порога. Проверить worker, доступ к document store и runbook 10. Не менять сохранённый снимок и не пересоздавать уже выпущенный файл. После успешного сохранения PDF сигнал должен уйти. Глобальный счётчик доступен только с `sales.quotes.all`; реквизиты предложений в мониторинг не входят.

<a id="directory"></a>
## Подтверждение ролей Entra

`DirectoryConfirmationStale`: когда Microsoft Graph и CRM app id настроены, подтверждение ролей нужного tenant отсутствует или старше 10 минут (`Monitoring:DirectoryConfirmationMinutes`). Проверить `entra-role-sync`, Graph permissions и credential; успешная sync другого потока не считается подтверждением ролей. Подробности — runbook 12. Права не расширять для обхода отказа; проверить новое подтверждение каталога после восстановления.

## Подавление и восстановление

Правила Azure Monitor stateful (`autoMitigate`, resolve через 10 мин). Повторяющиеся оценки одного открытого алерта не отправляют письмо каждую минуту; после восстановления — recovery. Независимые dimension не объединяются: system/job/module/component/category, без customer/id labels. Workbook показывает последние значения; повторные снимки не суммируются. При пропавшей телеметрии отсутствие строки не считается здоровьем: отдельно срабатывают host/collector alerts.

## Протокол EXT-01 для мониторинга

Заполнить до реального учения: разрешённая test-среда и resource IDs; версия/manifest; operations owner, finance owner, резервный исполнитель; адреса и часы поддержки; сроки реакции и эскалации; URL runbook. Утверждение DEC-01/02/08 также входит в общий EXT-01 и не заменяется этим учением.

1. Скомпилировать Bicep; развернуть только в явно разрешённой test-среде. Проверить action groups, владельцев, адреса и валидность KQL. Компиляция не доказывает доставку.
2. На синтетических данных создать один failed sync / dead-letter; записать время. Убедиться, что CRM readiness и чтение клиентов продолжают работать.
3. Проверить видимость сигнала, назначить владельца, сохранить статус/комментарий. Зафиксировать получение Fired выбранным реальным адресатом и correlation с сигналом, без персональных данных в evidence.
4. Оставить проблему на несколько периодов оценки: подтвердить отсутствие повторных уведомлений о том же открытом алерте.
5. Исправить синтетическую причину, выполнить подтверждённый replay или успешную sync. Проверить lastSucceededAt/счётчик, исчезновение активного сигнала и доставку Resolved.
6. Повторить для финансовой action group с синтетическим расхождением без суммы в алерте. Проверить 403 для роли без мониторинга и серверное отсутствие недоступных финансовых сигналов.
7. Кратко прекратить экспорт телеметрии в test: проверить missing-telemetry alert. Вернуть экспорт и проверить recovery.
8. Сохранить дату, версию, фактические задержки, разрешённые ссылки на Fired/Resolved и подписи владельцев. Только после этого внешняя часть AC05 может получить pass.

Локальные SQL/WireMock/UI тесты не закрывают пункты доставки, облачного KQL и бизнес-подтверждения. До выполнения протокола EXT-01 остаётся blocked.
