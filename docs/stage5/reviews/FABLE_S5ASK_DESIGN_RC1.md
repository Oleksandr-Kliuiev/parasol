## Required findings (correct in the contract before ASK-A)

**R1 — 02_CONTRACTS.md:14 and 04_PLAN_AND_ACCEPTANCE.md:18,30: "route-local parser/limit before JSON parse; unchanged global parsers" is not achievable under current wiring.**
Failure: Nest's global `express.json` runs for every path before any Ask middleware or guard. An Ask body of 16KiB to 100KiB is fully JSON-parsed before Ask code sees it. A body over 100KiB yields Nest's own 413 "request entity too large", not an Ask code. A malformed body containing question text yields Nest's 400 whose message echoes a body excerpt. Verified on Node 25:
```
Unexpected token 's', ..."uestion": secret-mar"... is not valid JSON
```
This contradicts 02:19 "no body echo", 03:55 "error paths never echo body/question" and the Q1 "preparse16KiB" gate. An implementer cannot satisfy the text with "new parser middleware limited to Ask route".
Closure: name the admitted mechanism. Recommended: create the Nest app with `bodyParser: false` in both fixture and db branches, then add an Ask-only raw reader enforcing 16KiB, UTF-8 and syntax with fixed Ask responses and no message, and re-register the identical default json/urlencoded parsers for every non-Ask path. Declare this as the one shared-source delta in `apps/api/src/main.ts` per 04:24, with regression tests proving unchanged parser behaviour for existing endpoints in OFF and MOCK. Also state the Ask status and code for an oversize body and for a non-JSON content type (recommend 413 ASK_TOO_LARGE and 400 ASK_REQUEST_INVALID).

**R2 — 02_CONTRACTS.md:19-25: error response DTO and diagnostic carrier unspecified.**
Failure: statuses and codes are fixed, but no body shape, header or cache directive is given, and "diagnostics contain only server-generated correlation UUID" never says where it travels. Accepted precedents differ: S4-C sends `{statusCode, code, synthetic:true}` with no-store (`apps/api/src/db/poweroffice.ts:48-51`); tools send a correlation header (`apps/api/src/db/tools.ts:33`). Guard 401 and OFF 404 are Nest default bodies. Q1 "exact body" cannot be gated and the browser has nothing exact to validate.
Closure: define `AskErrorV1 {contractVersion:'AskErrorV1', code:<allowlist>, correlationId:<UUID>}` or declare the header, require `Cache-Control: no-store` and `application/json`, and list which responses remain Nest defaults the browser handles by status only.

**R3 — 02_CONTRACTS.md:11 vs 03_SECURITY_AND_STATE.md:9-11: denial semantics contradictory, reason code unnamed.**
Failure: 02:11 "Path client matches SCOPE_ID_PATTERN" reads as 400 ASK_REQUEST_INVALID, while 03:9 requires malformed, nonexistent and forbidden IDs to be indistinguishable (403 plus one workspace denial). "Fixed reason" is not fixed. Stage 1 uses INVALID_SCOPE_ID versus SCOPE_DENIED (`apps/api/src/db/auth.ts:56`); Stage 3/4 use SCOPE_DENIED versus PERMISSION_DENIED for a member lacking the permission (`packages/actions/authority.ts:108-111`). Phase ordering is only partially stated at 03:8.
Closure: state that a malformed path client is 403 ASK_SCOPE_DENIED with one `ask.scope_denied` denial, never 400. Fix the reason code(s), recommending SCOPE_DENIED for non-member/malformed/nonexistent and PERMISSION_DENIED for a member without context:read, matching Stage 3/4. Write the exact order: size/syntax, guard 401, body semantic 400, phase-1 fence re-auth 401, membership/permission 403 audited, then read.

**R4 — 02_CONTRACTS.md:81-97: intent and compiler predicate table missing; INSUFFICIENT vs ASK_PLANNER_INVALID ambiguous.**
Failure: WHY_URGENT, SOURCE_STATE or ENTITY with no focus selected is both "incompatible focus → 503" (02:92) and "missing required facts → 200 INSUFFICIENT" (02:93). The journey "Почему это срочно?" without a focus must be a 200. Claim codes are named without predicates or cardinality (one OBSERVATION_RECORDED claim with up to 8 refs versus one per ref). ENTITY "one CONFIRMED matching entity link" (02:64-65) never defines "matching"; the accepted console rule is same entityId and same entityKind, first in id order (`apps/operator/src/entities.ts:28-31`). Q4/Q8 cannot be gated and the browser's "valid for that code's exact predicate" (02:108) has nothing to check against.
Closure: add an exact table. Per intent: required focus (absent → 200 INSUFFICIENT, no claims), allowed ref kinds (violation → 503 ASK_PLANNER_INVALID), refs that must equal focus, UNSUPPORTED requires empty refs. Per claim code: predicate and ref cardinality, with SOURCE_URGENT meaning focus severity in HIGH/CRITICAL and SOURCE_NOT_URGENT_IN_READ otherwise, ENTITY_* from the entity fact state, and one RECORDED claim per intent citing the planner's valid refs. Matching link: same entityId, same entityKind as the entity row, status CONFIRMED, system Atera or Huntress, first in existing id order.
