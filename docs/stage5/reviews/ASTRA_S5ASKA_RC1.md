## Required findings

**R1 — The private DB phase does not actually return within its two-second bound.** `packages/ask/authority.ts:54–72`, especially the fixed per-statement timeout at line 62 and awaiting the transaction promise at line 70. Real confined PostgreSQL 17.11 reproduction: hold `ApiToken` and `Actor` separately, start private authentication, release the token lock after approximately 1.15 seconds and leave the actor lock held. At 2.2 seconds authentication is still unsettled, one owner is held and the Actor query is still waiting. `ASK_DEADLINE` arrives at 3.199 seconds, when the second statement's own two-second timeout expires. A separate run measured 3.209 seconds. Prisma's transaction timeout does not provide the advertised public phase bound while a query is executing; the unchanged statement timeout starts afresh for each statement. This violates 03's authentication/DB phase `min(2s, original remaining)` bounds and Q6.

Expected closure: enforce an absolute deadline for each DB phase and timely failure to its caller, while retaining the same owner until the actual outstanding query and transaction cleanup settle. A timeout race alone must not free capacity. Add this sequential-lock regression for authentication and applicable fenced phases; observe PostgreSQL work/locks and owner counts at public timeout and at drain/recovery. Preserve the original eight-second deadline and stop subsequent work after the phase terminates. Evidence: `independent-physical-phase.log`, `independent-hostile-3.log`, test `physical PG phase bound` in `source/review-hostile.test.ts`.

**R2 — An in-progress source workflow starts new reads after HTTP disconnect.** `packages/ask/read.ts:184–193` and its awaited helper queries; `packages/ask/authority.ts:150–151` checks the run only around the entire reader. Real HTTP reproduction: block the Observation page query, disconnect its client, confirm the owner is still held, and then release Observation while separately blocking Entity. A new Entity query starts and waits after the run is terminal. The flow therefore continues fetching graph/resource data after disconnect; retaining the owner does not satisfy the separate prohibition on new reads after terminal state. Similar per-await checks are absent inside private authentication and fenced helpers. This violates 03's before/after-await and no-new-read rules and Q6; the packaged disconnect test checks audit/admission counts but does not observe these subsequent queries.

Expected closure: propagate/check terminal and deadline state at the actual asynchronous read boundaries, including authentication/admission/source/finalization, without abandoning rollback or other required cleanup. Add a real HTTP/PG barrier asserting no later graph/resource read, charge, new audit or new phase begins after terminal state, while the existing work still drains before exactly-once release. Evidence: `independent-hostile-3.log`, event `read-after-disconnect` (`newEntityRead:true`, `heldOwners:1`).
