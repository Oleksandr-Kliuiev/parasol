## Подтверждённая проблема и реализация

**До.** `DatabaseMigrator.GrantAppIdentityAsync` при каждом запуске добавлял единственную идентичность web и worker (`id-crm-app`) в `db_datareader` и `db_datawriter`; защиты аудита и утверждённых финансовых данных в БД не было (ADR и docs/06 обещали «триггер» и «SQL-пользователя без DELETE»). Интеграционные тесты работали под `sa`, поэтому ни одно ограничение прав не проверялось. Обе Container Apps получали ключи PowerOffice/Atera, а идентичность имела Secrets User и Certificate User на весь Key Vault. Веб сам вызывал поставщика для проверки подключения.

Подтверждение дефекта: первый прогон интеграционных тестов под логином без `db_datawriter` (роль `crm_worker`) — 115/117; упали ровно два теста, которые как администратор БД переписывали выгруженное основание и вставляли «довнедрённые» данные (`BILLING_APPROVED_IMMUTABLE`), т. е. раньше это могла сделать сама идентичность приложения. Эти два теста переведены на явное подключение администратора (`AdminSqlWithoutBillingTriggersAsync`).

**После** ([ADR-014](../../adr/ADR-014-database-permissions-and-immutable-audit.md), [runbook 08](../../runbooks/08-database-permissions.md)):

- `DatabasePermissions` (BuildingBlocks): роли `crm_runtime` ⊃ `crm_web`/`crm_worker`, `crm_privacy`; права по схемам модулей, аудит только `SELECT/INSERT`, история миграций только чтение, у web запрет менять outbox; правила модулей (`IDatabasePermissionRules`): billing — без удаления финансовых записей, журнал отправок только добавляется; audit — политики хранения и контрольные точки не пишутся приложением, `EXECUTE` процедуры retention только `crm_privacy`. Мигратор применяет права после миграций, **проверяет** их на каждой схеме и только потом сопоставляет идентичности (Web→`crm_web`, Worker→`crm_worker`, Privacy→`crm_privacy`; прежняя App — только если отдельных нет) со снятием `db_datareader`/`db_datawriter`/`db_owner`/`db_ddladmin`/… DDL-триггер `trg_ApplicationRolesStayNarrow` не даёт вернуть идентичности приложения широкую роль (51031).
- Триггеры billing (миграция `ProtectApprovedBilling`, SQL записан в миграции дословно, текущие определения — `BillingTriggers`) для прогонов, оснований, строк, актов согласования, начислений и журнала отправок; маппинг EF с `HasTrigger`. Транспорт выгрузки и номер заказа остаются доступны приложению.
- Аудит (миграция `AppendOnlyAudit`): триггер только-добавление, таблица утверждённых политик `audit.RetentionPolicies` (ограничение запрещает финансовые модули), процедура `audit.ApplyRetention` (по умолчанию пробная; разрушающая — только по утверждённой политике и сроку; обнуляет персональную часть, факт остаётся; финансовые модули — отказ 51020; запуск пишется в аудит), таблица `audit.IntegrityCheckpoints`.
- `AuditIntegrityJob` (worker, 04:40) — цепочка SHA-256 по фактам записей, перепроверка последней и одной старой точки, лог `AUDIT_CHECKPOINT` (якорь в Log Analytics), `AUDIT_INTEGRITY_MISMATCH` (Critical); `audit-integrity-full` — полная проверка вручную. Записи моложе 5 минут ждут следующего запуска, чтение с `READCOMMITTEDLOCK` (иначе при RCSI задача могла бы пройти мимо незафиксированной записи — найдено при самопроверке).
- Секреты: идентичность `id-crm-worker-<env>` (Bicep, конвейер создаёт её до миграций и передаёт обе идентичности задаче миграций); ссылки Key Vault только у worker; Secrets User — на каждый секрет поставщика отдельно (worker) и только на секрет сертификата входа (web, после bootstrap); у web вместо Secrets/Certificate User на хранилище — Key Vault Reader (метаданные). `IIntegrationAdapter.IsEnabled` и готовность биллинга (`IBillingTargetSystem.IsConfigured`) следуют выключателю `Enabled`; вызовы поставщика требуют ключей и выполняются в worker. Проверка подключения: `POST /integrations/{system}/test` записывает `SyncRun` `connection-test` и событие outbox (`OutboxMessage.For`), worker выполняет проверку (`IntegrationConnectionTestHandler`), `GET /integrations/{system}/test/{id}` (оба — `integrations.manage`; создание — без If-Match, CSRF как у всех мутаций); страница опрашивает ответ и через минуту без ответа говорит об этом. `/health/integrations` не учитывает проверки подключения.
- UI: кнопка «Проверить подключение» показывает «Проверяется…», результат — уведомлением; названия задач аудита; nb/en/ru синхронизированы.
- Тесты работают под логином `crm_worker` без фиксированных ролей (фикстура: мигратор как администратор, затем приложение под ролью); классы, играющие администратора БД, — в `DatabaseAdministrationCollection` без параллелизма. E2E: веб без ключей PowerOffice, ключи только у worker.

## Данные и обратимость

Миграции `AppendOnlyAudit` (audit) и `ProtectApprovedBilling` (billing) — отдельные, после исторических; триггеры не трогают существующие строки. Проверено на копии прежней схемы с данными DEV-02/DEV-03 (8 прогонов, 9 оснований, 23 строки, 18 начислений, 3 записи аудита; [протокол](DEV-04/migration-upgrade.txt), скрипты рядом, исходные данные — [DEV-03/mig-legacy-billing.sql](DEV-03/mig-legacy-billing.sql)):

1. Применение миграций и мигратора дважды (идемпотентно): контрольные суммы всех таблиц до и после совпадают; 7 триггеров таблиц и DDL-триггер включены; права роли на 15 схем, запреты и `EXECUTE` для `crm_privacy` — как в матрице runbook 08.
2. Поведение ролей на старых данных (каждая проба откатывается): черновик и повтор «Ошибка → Утверждено» разрешены, выгруженные/утверждённые/закрытые записи защищены, legacy-начисление можно подтвердить решением Finance, оператор приватности видит только процедуру.
3. Откат схемы (`ChargeRegister`, audit `Initial`): триггеры и процедура сняты, контрольные точки и политики сохранены в `*_rollback_<время>`, данные те же; роли, запреты и DDL-триггер остаются — логин worker после отката без `db_datawriter`, старое `ALTER ROLE db_datawriter ADD MEMBER` по-прежнему 51031 («откат не возвращает широкие права»).
4. Повторное применение после отката и мигратор — успешно, защита снова действует.

Переход идентичностей: конвейер создаёт `id-crm-worker-<env>` и задаёт задаче миграций обе идентичности до первого запуска новой версии; Bicep затем переключает контейнеры. **Внешние шаги (не выполнялись)**: выдать `id-crm-worker-<env>` Graph `User.Read.All`, `Mail.Send` на `crm@`, `Sites.Selected` до развёртывания, затем снять лишнее у `id-crm-app-<env>` (runbook 08 §2).
