## Подтверждённая проблема и реализация

**До** (выдержки из предыдущего релиза — [baseline-defects.txt](DEV-07/baseline-defects.txt)):

- выбор сообщений `ProcessedAt == null && Attempts < 10`: после десяти ошибок сообщение молча исчезало из обработки, состояния и списка не было, повтор — только SQL;
- захват ставил `LockedUntil` без владельца, аренда не продлевалась, итог писался `Where(m => m.Id == id)` — исполнитель с истёкшей арендой перезаписывал `ProcessedAt/Attempts/LockedUntil` сообщения, которое уже держал другой;
- все обработчики события — в одной области: падение одного повторяло эффекты остальных. Тест DEV-02 прямо фиксировал это: повторная доставка ставила **вторую** исходящую операцию;
- `QuoteAcceptedHandler`: проверка без уникального индекса и без удалённых черновиков; карточки Teams уходили POST'ом из обработчика при каждой доставке, отказ вебхука проглатывался; `BasisExportedHandler` писал в Billing и TimeTracking двумя транзакциями; события фаз проекта не по порядку возвращали или снимали начисление; исходящие операции — аренда без токена, итог через `SaveChanges` поверх чужого, таймаут HttpClient уходил как отмена и оставлял операцию под арендой. Полный обзор 25 обработчиков выполнен перед изменениями.

**После** — модель [ADR-016](../../adr/ADR-016-outbox-delivery.md):

- Состояния `Pending/Processing/Processed/DeadLetter/Quarantined`, `NextAttemptAt` (10 с·2^(n−1), ≤ 1 ч, ±20 %), `LastError`, `DeliveredHandlers`, `Replays`; 10 попыток → dead letter; нечитаемый payload → карантин сразу; неизвестный тип → повтор, после 10 попыток карантин. Недоступная БД во время обработчика не тратит попытки (сообщение возвращается, раунд прерывается); таймаут внешнего вызова внутри обработчика — обычная ошибка.
- Аренда с токеном `LeaseOwner`, захват и каждое изменение строки — compare-and-set; продление каждые ⅓ срока (`LeaseRenewal`), потеря аренды отменяет обработчики, их транзакция откатывается; остановка worker возвращает сообщение без попытки.
- Квитанции `InboxReceipts (MessageId, Handler)` в схеме модуля обработчика: обработчик модуля начинает транзакцию квитанцией (`MessageHandlingContext.ClaimAsync`, сначала чтение, ключ — для гонки), обработчик адаптера — при первом сохранении (`AuditingInterceptor`); фиксация после возврата обработчика под SQL-стратегией повторов. Обработчик меняет один модуль — иначе ошибка.
- Обработчики: уникальный фильтрованный индекс `Contracts.SourceQuoteId` + проверка с удалёнными; отметка часов перенесена в TimeTracking (`IBillingApi.GetInvoicedTimeEntryIdsAsync`, `ITimeTrackingApi.MarkInvoicedAsync` удалён); начисления фаз — текущий статус фазы (`IProjectsApi.IsPhaseCompletedAsync`) и время решающего события (`PendingCharges.SourceChangedAt`); шесть обработчиков объединения пропускают отменённое объединение (`ICustomersApi.IsMergeUndoneAsync`); Teams — очередь `notifications.ChannelPosts` + задача `channel-posts` с арендой, отказ вебхука — ошибка с повтором, автоматический повтор POST в HttpClient отключён; `OutboundQueue` больше не падает на двух ожидающих операциях одной сущности.
- Исходящие операции: токен и CAS, продление аренды, таймаут HttpClient — неудачная попытка; повтор и отмена через API пишутся в аудит, отмена отклоняется, пока операцию держит прогон (`INT_OUTBOUND_RUNNING`).
- Закрыт дефект, записанный в DEV-15: два основания одного прогона, завершившие выгрузку одновременно, сталкивались на версии строки прогона, и второе падало уже после создания заказа (прогон мог остаться «выгружается»). `BillingApi.UpdateRunStatusAsync` при конфликте перечитывает прогон и выводит статус заново (он производен от оснований). Воспроизведено детерминированно: без повтора — `DbUpdateConcurrencyException` ([протокол](DEV-07/run-status-race.txt)).
- API (`integrations.manage`, CSRF глобально): `GET /api/v1/integrations/outbox` — счётчики по модулям и недоставленные без значений payload (только имена полей); `POST …/outbox/replay` — ≤ 100, причина 10–500, `expected` = число повторимых сейчас (иначе 409 `OUTBOX_REPLAY_STALE`); запрос и аудит в транзакции модуля, применяет worker одной транзакцией с условным захватом запроса. Конкурентный контроль — условие состояния и подтверждённое количество (ETag у списка нет).
- Права БД: `crm_web` — DENY INSERT/UPDATE/DELETE на `InboxReceipts`, DENY UPDATE/DELETE на `OutboxReplayRequests` (INSERT разрешён); outbox — как в DEV-04 (UPDATE/DELETE запрещены).
- UI: панель «Доставка событий» на странице «Интеграции» (выбор, «Повторить выбранные», диалог с количеством, типами и обязательной причиной), nb/en/ru, названия задач `channel-posts`/`outbox-retention`, коды ошибок.
- Метрики `Crm.Outbox` (DEV-17), задача хранения `outbox-retention`, документация: ADR-016, [runbook 09](../../runbooks/09-event-delivery.md), docs/03 §5.1, docs/07, runbook 03/04, CLAUDE.md.

Изменённые и новые файлы: `src/BuildingBlocks/Crm.Infrastructure/{Outbox/OutboxProcessor.cs, Outbox/LeaseRenewal.cs, Outbox/OutboxRetentionJob.cs, Persistence/OutboxMessage.cs, Persistence/OutboxMigrationSql.cs, Persistence/AuditingInterceptor.cs, Persistence/ModuleDbContext.cs, Persistence/DatabasePermissions.cs, Persistence/AuditEntry.cs, DependencyInjection/ModuleRegistration.cs}`, `src/Hosts/Crm.Web/{Http/OutboxEndpoints.cs, Program.cs}`, `src/Hosts/Crm.Worker/Program.cs`, модули Billing (контракт, `PendingCharge`, `BillingApi`, `ProjectPhaseChargeHandler`), Contracts (`QuoteAcceptedHandler`, `ReminderFeatures`, `ContractsDbContext`), Customers (контракт, `CustomersApi`), Projects (контракт, `ProjectsApi`), TimeTracking (контракт, `TimeImportService`, csproj), Notifications (`ChannelPost`, `TeamsHandlers`, контекст, модуль), Sales/Activities/Licensing/Service (обработчики объединения), Integrations.Core (`Outbound.cs`, `MappingEndpoints.cs`, `MergeLinkHandlers.cs`, контекст), Graph (`GraphTeams.cs`, модуль), миграции `*_OutboxDelivery` ×15 и снимки, web (`DeliveryPanel.tsx` и тест, `api.ts`, `types.ts`, `IntegrationsPage.tsx`, локали), тесты (`OutboxDeliveryTests`, `DeliveryProbes` — новые; `CrmWebFactory`, `DatabasePermissionTests`, `OutlookApiTests`, `BillingApprovalApiTests`, `ChargeRegisterApiTests`; юнит `OutboxDeliveryTests`).

Изменения существующих тестов: имитация «падение до подтверждения» и «восстановление из копии» теперь задаёт полное состояние сообщения (`Processing` + истёкшая аренда; при восстановлении — и квитанции, которых в копии не было), а не только `ProcessedAt = null` — при явных состояниях старый способ не доставлял сообщение повторно. ## Данные и обратимость

- Миграции `OutboxDelivery` в 15 контекстах (порядок регистра, Audit первым): колонки `Status` (default `Pending`), `NextAttemptAt`, `LeaseOwner`, `DeadLetteredAt`, `DeliveredHandlers`, `Replays` (default 0); таблицы `InboxReceipts`, `OutboxReplayRequests`; индексы. Contracts — уникальный фильтрованный индекс `SourceQuoteId` с предварительной проверкой дублей (THROW 51041 и runbook 09 §5 — ничего не сливается автоматически, дубль мог выставляться в счетах). Billing — `PendingCharges.SourceChangedAt` (NULL у существующих: для них действует проверка текущего статуса фазы). Notifications — `ChannelPosts`. Integration — `OutboundOperations.LeaseOwner`. Только расширение схемы (архитектурный тест проходит), разрывов нет.
- Перенос старых строк: доставленные → `Processed`, исчерпавшие 10 попыток → `DeadLetter` без сброса попыток (без автоматического повтора); трогает только строки в состоянии по умолчанию, повторный запуск ничего не меняет — проверено тестом.
- Старый релиз на новой схеме: E2E DEV-06 — 54/54. Во время развёртывания старый и новый образ уважают аренду друг друга (`LockedUntil`), подтверждение старого (`ProcessedAt`) новый считает доставкой; старый обработчик КП не создаст дубль (индекс); старые обработчики Teams до переключения шлют напрямую — как раньше.
- Откат — предыдущий релиз без миграций (штатный путь DEV-05). `Down` удаляет новые колонки и таблицы вместе с состояниями и квитанциями — только вручную, со знанием, что повторная доставка после этого не защищена квитанциями.
- Внешние эффекты, которые откат не отменит: отправленные карточки Teams, заказы PowerOffice (сверка по ADR-013), тикеты Atera.
- Нагрузка: одна вставка квитанции и транзакция на обработчик; счётчики очереди — раз в минуту на модуль; хранение — раз в сутки.

## Самопроверка и остаточные риски

Самопроверка (не независимое review): diff, миграции, гонки двух исполнителей, падение до подтверждения, потеря и продление аренды, недоступная БД, повреждённые данные, права, логи. Найдено и исправлено в ходе самопроверки: снятие аренды через `CASE` по `Status` в том же `UPDATE` читало старое значение (SQL Server вычисляет SET по значениям до изменения) — заменено явным флагом; таймаут HttpClient внутри обработчика выглядел как недоступная БД и навсегда откладывал бы сообщение — отдельное правило для обработчиков; хранение пыталось удалять в audit-схеме, где роль только вставляет; применение заявки на повтор было не атомарным и могло примениться дважды — одна транзакция с условным захватом заявки; синхронное исключение обработчика оборачивалось reflection — `DoNotWrapExceptions`; повторные доставки шумели ошибками EF — сначала чтение квитанции; отмена исходящей операции могла пройти под работающим прогоном — условное обновление.

Остаточные риски и передача:
- Teams: у вебхука нет ключа идемпотентности — при таймауте после приёма возможен дубль уведомления (только уведомление; повторная доставка события дубля не создаёт).
- Atera: тикет создан, а запись результата в CRM не удалась — повтор операции может создать второй тикет; это сверка при неопределённом исходе, задача DEV-19 (EXT-03).
- Обработчики держат транзакцию до конца работы: текущие короткие; новый обработчик не должен делать долгих внешних вызовов внутри (правило в CLAUDE.md и ADR-016).
- Обработчики объединения в Sales/Activities/Licensing/Service по-прежнему не возвращают записи при отмене объединения (существующее поведение продукта, не изменялось; новое — только пропуск уже отменённого объединения).
- Диалог повтора в E2E под axe не проверяется: API E2E не может создать dead letter; поведение диалога — vitest, страница с панелью — axe в обеих темах.
- Алерты на метрики — DEV-17.
