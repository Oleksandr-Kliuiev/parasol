## Подтверждённая проблема и реализация

**До.** Воспроизведено на `4a108ac` во временном worktree ([baseline-defect.txt](DEV-10/baseline-defect.txt), [тест](DEV-10/Dev10BaselineTests.cs.txt)):
- после снятия Finance в Entra та же cookie утверждает прогон (404 — «авторизован, прогона нет»), и `/bff/user` по-прежнему показывает `Crm.Finance`;
- cookie на реплике с собственным набором ключей — 401, то есть сессии не переживают реплику;
- после выхода копия cookie отвечает 200 на `/bff/user` и продолжает утверждать;
- настройка ключей в Production без `BlobUri`/`KeyVaultKeyUri` не отказывает и берёт локальное хранилище машины.

По коду: ежечасная ревалидация (`ValidatePrincipalAsync`) погашает refresh token для `User.Read` и обновляет только `crm_last_validated`, роли остаются из id_token входа. Синхронизация пользователей смотрит только `accountEnabled`.

**После** — модель [ADR-019](../../adr/ADR-019-sessions-and-privilege-freshness.md):

- **Источник назначений** — задача `entra-role-sync` (`EntraRoleSync.cs`), каждые 2 минуты через `SyncRunner`. Она читает:
  - `servicePrincipals?$filter=appId eq …` — роли приложения, отключённые не считаются;
  - `appRoleAssignedTo`;
  - **прямых** членов назначенных групп — как в токене Entra, вложенные группы роли не дают, PIM-активация есть членство на её срок;
  - отключённые аккаунты (`accountEnabled eq false`) — ролей не держат ещё до ежечасной синхронизации пользователей.

  Без `TenantId`/`CrmAppId` задача пишет в журнал, что пропущена.
- **Подтверждённые роли** (`Crm.Identity`):
  - `Users.Roles/RolesVersion/RolesVerifiedAt`; `ConfirmRoles` при входе, `ApplyDirectoryRoles` при синхронизации;
  - `DirectoryRoleConfirmations` — одна строка на tenant, монотонная, `ConfirmedAt` — маркер конкурентности.

  Правила:
  - пользователь пишется и аудируется только при изменении ролей;
  - чтение старше входа пользователя для него ничего не меняет;
  - чтение старше применённого отбрасывается целиком (`RoleSyncResult.Superseded`).
- **Сессии.** `UserSessions`, id в cookie (`crm_sid`), `ISessionDirectory` отвечает одним запросом. `SessionStateCache` хранит ответ 30 с и не больше 10 000 записей. Переполненный свежими записями кэш отвечает из базы, не запоминая.

  `OnValidatePrincipal`:
  - нет `crm_uid`/`crm_sid`, сессия закрыта, пользователь неактивен или подтверждение старше 8 ч — cookie отвергается;
  - роли cookie заменяются серверными, в `crm_rv` пишется версия, cookie переписывается;
  - `crm_roles_verified` всегда берётся из серверной записи.

  Выход закрывает сессию и забывает её в кэше реплики.
- **Свежесть.** `PermissionAuthorizationHandler` проверяет подтверждение не старше `Auth:PrivilegedFreshness` (5 мин) в двух случаях:
  - изменяющий запрос, разрешённый только правами из `Permissions.Privileged`: биллинг (manage/approve/approve.second), `time.unlock`, `sales.discount.approve`, `integrations.manage`, `customfields.manage`, `customers.delete`;
  - эндпоинт с `.ExportsData()` — витрина Power BI, экспорт организаций.

  Нет подтверждения — отказ без исключения (fail-closed). `CrmAuthorizationResultHandler` отвечает `403 application/problem+json` с кодом `AUTH_REVERIFY_REQUIRED`.
- **Ключи.** `DataProtectionSetup.Problem`: в Production без пары `BlobUri` + `KeyVaultKeyUri` хост не стартует, половина пары не стартует нигде.
- **Ежечасная проверка refresh token.** Отказ Entra «токен не выдаётся» завершает сессию, как и раньше. Недоступный Entra (сеть, таймаут, 429, 5xx) откладывает проверку на 5 минут, и запрос обслуживается в рамках grace. Раньше это было 500 на каждый запрос каждой сессии старше часа. Неожиданная ошибка остаётся ошибкой.
- **SyncRunner.** Добавлен `quietFor`: неудачи и изменения пишутся всегда, неизменный или пропущенный запуск частой задачи — раз в час. Иначе 720 строк в сутки вытеснили бы из «последних 50 запусков» все остальные системы.
- **Worker и инфраструктура.**
  - `GraphOptions.CrmAppId`/`RoleSyncCron`, HttpClient со стандартной устойчивостью, recurring job;
  - Bicep передаёт worker `Integrations__MicrosoftGraph__CrmAppId = entraClientId`;
  - `register-app.sh` выдаёт идентичности worker `User.Read.All`, `Application.Read.All`, `GroupMember.Read.All`, находя id разрешений по имени.
- **SPA.**
  - Ответ 401 на запрос `/api/` отправляет на вход и возвращает на ту же страницу; ответ `/bff/user` разбирает сам AuthGate.
  - `AUTH_REVERIFY_REQUIRED` показывается текстом: выйти, войти, повторить.
  - Добавлено название задачи `entra-role-sync`.
  - Всё в nb, en и ru.

**Находки самопроверки, исправленные до коммита:**
1. Первая версия синхронизации обновляла каждого пользователя каждые 2 минуты: строка аудита на человека за запуск (~20 тыс. в сутки при 30 пользователях), смена ETag и конфликты конкурентности с входом. Заменено подтверждением на tenant и записью только изменений (мутация M3).
2. `transitiveMembers` давал роль членам вложенных групп. Entra такую роль не выдаёт, так что CRM дала бы больше прав, чем сам токен. Заменено прямыми членами (мутация M1).
3. Отключённый аккаунт сохранял назначения и права до часа. Теперь он теряет роли на следующем запуске (мутация M2).
4. Журнал синхронизаций переполнялся запусками каждые 2 минуты — `quietFor`.
5. Кэш мог расти выше 10 000 записей при одних свежих записях — граница стала строгой.
6. Тесты сессий делили один tenant, и общая строка подтверждения с разными ручными часами делала их зависимыми от порядка. Теперь у каждого теста свой tenant.
7. Найдено тестом абсолютного срока, существовало до DEV-10: при недоступном Entra ежечасная проверка refresh token роняла каждый запрос (500). Теперь проверка откладывается (мутация M8).

## Данные и обратимость

- **Миграция** `Crm.Identity/20261004083007_SessionsAndConfirmedRoles` только расширяет схему:
  - `Users.Roles nvarchar(256) NOT NULL DEFAULT ''`, `RolesVersion int NOT NULL DEFAULT 0`, `RolesVerifiedAt datetimeoffset NULL`;
  - новые `UserSessions` и `DirectoryRoleConfirmations`.

  Пользователи не удаляются и не меняются. Релиз DEV-09 работает на новой схеме: E2E 55/55.
- **Первый запуск после выпуска.** Существующие cookie не содержат `crm_sid`, поэтому каждый пользователь входит один раз (проверено). Роли у существующих пользователей пусты до входа или первой синхронизации, и этого никто не замечает: сессии без `crm_sid` всё равно входят заново, и вход подтверждает роли.
- **Откат кода до DEV-09** — штатный путь DEV-05. Старая версия снова читает роли из cookie. Cookie новой версии содержат роли последнего обновления, так что старая версия примет их до истечения срока — прежнее поведение. Таблицы остаются неиспользуемыми. `Down` удаляет сессии и подтверждения — только вручную.
- **Внешние эффекты** только в tenant и только после EXT-02: администратор выдаёт идентичности worker разрешения Graph. Без них синхронизация падает, и привилегированные действия через 5 минут требуют входа (fail-closed, runbook 12). Перед развёртыванием это обязательное действие владельца tenant.
- **Нагрузка:**
  - сессия — один запрос на сессию в 30 с на реплику (PK пользователя, индекс `UserSessions(UserId)`, PK tenant);
  - синхронизация — 3 запроса Graph плюс по одному на назначенную группу каждые 2 минуты, одна запись tenant и изменённые пользователи;
  - журнал синхронизаций — до 24 строк в сутки.
