# Сценарии приёмки: Technician (техник)

Статус документа: **шаблон сценариев, не результат**. Исполнители, даты, оценки и подписи не заполнены и вносятся только в [протокол](../protocol-template.md) настоящими участниками UAT в среде `test` (EXT-10).

## 1. Назначение

Проверить, что техник без подсказок вносит часы так, что они правильно классифицируются для биллинга, видит свои проекты и клиентов, и **не видит денег и чужих записей**.

## 2. Предусловия

- Среда `test`, вход через Entra; тестовая учётная запись с ролью `Crm.Technician` (список тестовых ролей: [runbook 17 §4.2](../../../../runbooks/17-vulnerability-intake.md), создание и отзыв ролей: [runbook 12](../../../../runbooks/12-roles-and-sessions.md)).
- Для шага одобрения часов и негативных проверок - отдельная учётная запись `Crm.ServiceLead` (сценарий SL-1). Одобряет другой человек, не техник.
- Синтетический клиент с активным договором и, для шага «пакет часов», с активным пакетом часов (Hour bank); проект, в команде которого учётная запись техника; второй проект того же клиента, где техника **нет**. Данные готовит Admin/Finance заранее.
- Запись в Atera выключена (`Integrations:Atera:WriteEnabled` = false): шаг с тикетом проверяет честное сообщение, а не создание реального тикета.

## 3. Нужные данные

| Что | Примечание |
|---|---|
| Клиент A: договор на обслуживание (часы покрыты договором) | чтобы проверить классификацию «Covered by contract» |
| Клиент B: пакет часов с известным остатком | классификация «Hour bank»; остаток записать до и после |
| Клиент C: без покрытия | классификация «By rate» |
| Номер тикета Atera (произвольный тестовый) | необязателен (подсказка «Atera ticket number, if the work belongs to one») |
| Проект P1 (техник в команде), проект P2 (нет) | охват проектов (DEV-09) |

## 4. Сценарии

### TEC-1. Свои часы за неделю

| № | Действие | Ожидаемый результат |
|---|---|---|
| TEC-1.1 | Меню «My timesheet» (`/time`). | Страница «Your hours this week»; навигация «Previous week / This week / Next week». |

## 5. Денежные правила, которые проверяются

Техник денег не видит, поэтому проверяется **классификация**, из которой Finance потом считает сумму:

- Часы делятся на «Covered by contract», «Hour bank», «By rate», «Not billable» (аллокации, а не отдельные записи); расчёт позже сверяет Finance (FIN-2/FIN-3).
- Правило сверки примера приёмки: 3 ч x 1 250 NOK = 3 750 NOK (часть основания 15 000 NOK). Техник вносит ровно 3 часа в тестовом клиенте; видимости суммы у него быть не должно.
- Одобренные ServiceLead часы получают статус «Approved»; только одобренные попадают в прогон. Техник статус не меняет.
- Работа вне часов поддержки отмечается «Outside support hours» (учёт выходных и праздничных дней - `BusinessTime`, тарифный движок).

## 6. Негативные проверки

По карте `ByRole` в `Permissions.cs`: у Technician есть `customers.read`, `contacts.write`, `catalog.read`, `contracts.read`, `sales.read`, `licensing.read`, `activities.read/write`, `service.read/write`, `time.own`, `projects.read`, `users.read`.

| № | Проверка | Должно быть по коду | Примечание |
|---|---|---|---|
| TEC-N1 | Меню «Billing», «Invoices», «Dashboard», «Margins» | Не отображаются; прямой URL - нет доступа / 403 (нет `billing.read`, `reports.read`, `finance.read`) | |
| TEC-N2 | Деньги на экранах: договор, предложение, клиентская карточка «Invoices» | Суммы удалены сервером (`[SensitiveData]`), а не только спрятаны в интерфейсе | Проверить через ответ экрана; исполнитель UAT не открывает инструменты разработчика без согласия |
| TEC-N3 | Правка фаз и задач проекта P1 | По коду - **невозможна** (только `projects.read`) | Расхождение №6 в [role-matrix-mismatches.md](../../DEV-21/role-matrix-mismatches.md): docs/02 говорит «RW (назначенные)». Решение владельца продукта; не считать ни одно поведение ошибкой до его решения |
| TEC-N4 | Чужие часы | Видны только свои записи в «My timesheet»; раздела «Time entries» (`/time/entries`) нет (нет `time.read`) | |
| TEC-N5 | Предложения (`/quotes`) | Видны только те, где техник - владелец текущей версии; чужие - 404 | Расхождение №1: у роли есть `sales.read`, документ говорит «—». Решение DEC-01 к подтверждению |
| TEC-N6 | Значения пользовательских полей клиента | По коду читаются (право `customers.read`) | Расхождение №8: документ - «недоступны». К подтверждению |
| TEC-N7 | Администрирование: «Users», «Audit log», «Integrations», «Record access» | Не видны; прямой URL - нет доступа | |
| TEC-N8 | Отозванная роль | После снятия роли в Entra экран «No access»/401 в течение ≈ 5 минут | [runbook 12](../../../../runbooks/12-roles-and-sessions.md); выполняет Admin/владелец tenant |

## 7. Доступность и клавиатура

1. Недельная сетка и диалог «Register hours» полностью с клавиатуры: поля, выпадающий «Work type», флажки, «Save»/«Cancel».
2. Сообщение об ошибке пустого поля объявляется и связано с полем.
3. Диалог возвращает фокус на кнопку, открывшую его.
4. Двойное нажатие «Register hours» создаёт одну запись.
5. Мобильный размер (≈360 px): техник часто вносит часы с телефона - таблица недели читается, цели нажатия не менее 24 x 24 px.
6. Масштаб 200 % и тёмная тема: контраст бейджей статусов достаточный.
7. Реальный скринридер и устройства - вручную (EXT-10).
