# DEV-22. Приёмка по ролям и параллельный месячный биллинг: материалы

Задача: [tasks/DEV-22.md](../../tasks/DEV-22.md). Внешние gate: **EXT-09**, **EXT-10** ([external-gates.json](../../external-gates.json)).

## Статус

Здесь лежат **шаблоны и процедуры**, подготовленные до UAT и пилота. В них нет ни одного исполнителя, даты, результата, подписи или базового значения: все такие поля пустые и заполняются настоящими людьми в среде `test`. Наличие этих файлов не закрывает ни один критерий DEV-22-AC01..AC05. Пока пилотный месяц не завершён, задача остаётся `code_verified` / ожидает внешнего gate (DEV-22-AC06).

Сервисные средства реализованы в коде и на экране «Pilot reconciliation» (`/billing/runs/{id}/pilot`, кнопка на странице прогона, видна только с правом `billing.reconcile`): `GET /api/v1/billing/runs/{id}/trace` и `trace.xlsx`, `POST /api/v1/billing/runs/{id}/pilot/compare`, `POST .../pilot/signoff`, `GET .../pilot`, `GET /api/v1/billing/pilot-readiness`, `GET /api/v1/billing/pilot/kpi`. Они проверены тестами на синтетических данных и **не прогонялись в реальной среде пилота**; полное описание и ограничения - [runbook 18](../../../runbooks/18-pilot-billing.md), раздел «Средства DEV-22 в CRM». Перед использованием проверить по коду и `evidence/DEV-22.md`.

Ограничения средств, которые нужно знать при приёмке:

- `MissingInFile` считается для каждого плательщика прогона, которого нет в файле независимого расчёта: файл должен охватывать всех клиентов пилота, иначе остальные плательщики объясняются как исключения.
- Заказ в PowerOffice несёт только код продукта; MVA берётся из продукта в PowerOffice. След CRM показывает ставку MVA строки, но в заказ она не передаётся, поэтому MVA сверяется с документом PowerOffice отдельно (EXT-03).
- Проверка готовности отвечает только из crm-web; факты crm-worker (ключи провайдеров, его конфигурация) ей неизвестны и показываются как «Unknown».
- KPI `notMeasured` (время до первого успешного сценария по пользователю, упущенные продления, возраст устранённых исключений, входы по ролям) данные не дают; см. [kpi-baseline.md](kpi-baseline.md).

## Порядок использования

1. Владелец UAT (PO) назначает исполнителей и наблюдателей (EXT-10), владелец Finance - сверку (EXT-09/EXT-10). Имена не вносятся в этот каталог без решения компании о хранении.
2. Admin готовит среду `test` и тестовые учётные записи по ролям ([runbook 17 §4.2](../../../runbooks/17-vulnerability-intake.md), [runbook 12](../../../runbooks/12-roles-and-sessions.md)) и синтетические данные по таблицам «Нужные данные» в сценариях.
3. Обучение по [training-plan.md](training-plan.md); первый самостоятельный сценарий замеряется по протоколу.
4. Роли проходят сценарии, результаты и замечания - в копиях [protocol-template.md](protocol-template.md).
5. Параллельный месячный пилот - по [runbook 18](../../../runbooks/18-pilot-billing.md); KPI - по [kpi-baseline.md](kpi-baseline.md).
6. Итоги (способ проверки, фактический результат, ссылка на протокол, commit или manifest) вносятся в `evidence/DEV-22.md` по [шаблону](../TEMPLATE.md), `backlog.json`, `PROGRESS.md` и `external-gates.json` - людьми, после реального исполнения.

## Известные ограничения

- Матрица ролей docs/02 §2 расходится с кодом (`Permissions.cs`) в нескольких строках; сценарии описывают поведение кода и отсылают к [role-matrix-mismatches.md](../DEV-21/role-matrix-mismatches.md). Решения DEC-01/EXT-01 не приняты; ни одно из этих расхождений сценарии не объявляют ошибкой.
- «Sales: только свои клиенты» (биллинг, отчёты) в коде не применяется; в сценарии Sales это помечено как решение к подтверждению.
- Автоматические e2e/интеграционные тесты перечислены в каждом сценарии, чтобы UAT сосредоточился на том, чего автоматика не проверяет: независимый ручной расчёт сумм, понятность для реальных людей, скринридер и реальные устройства.
- Реальные данные клиентов в сценариях не используются; копия производственных данных для пилота требует отдельного разрешения (runbook 18 §1.8).
