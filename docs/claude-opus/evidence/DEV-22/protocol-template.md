# Протокол приёмки по роли (шаблон)

**Это пустой шаблон.** Копия заполняется для каждой роли отдельно (Sales, Technician, ServiceLead, Finance, Management, Admin) настоящим исполнителем во время UAT в среде `test` (EXT-10, DEV-22-AC01).

Правила заполнения:

1. Каждое поле ниже остаётся **пустым**, пока исполнитель или ответственный не внесёт значение сам. Автор шаблона, разработчик и ассистент не вписывают имена, даты, результаты, слова «пройдено» и подписи.
2. Результат шага - только одно из значений: `OK`, `Fail`, `Blocked`, `N/A` (с причиной в замечании). Пустая клетка означает «не проверялось».
3. Исполнитель в протоколе идентифицируется так, как решит владелец UAT (ФИО или код); репозиторий не хранит персональные данные сотрудников сверх нужного для подписи - **решение о том, хранится ли протокол в репозитории или в папке компании, принимает владелец UAT (PO)**. Если протокол с ФИО хранится вне репозитория, в evidence кладётся ссылка/хэш файла.
4. Подсказка разработчика во время сценария делает этот сценарий непройденным для целей UAT: он повторяется другим исполнителем или тем же после обучения без подсказки; хронометраж «время до первого самостоятельного успешного сценария» засчитывается только по сценарию без подсказок.
5. Автоматические e2e-тесты и сценарии на тренировочных данных не заменяют этот протокол.

## 3. Суммы (только для ролей, которые считают деньги: Finance, при необходимости Sales)

Ожидаемая сумма записывается **до** просмотра результата CRM (исполнитель рассчитывает по исходным данным).

Сравнение с CRM можно выполнить на экране «Pilot reconciliation» (`/billing/runs/{id}/pilot`, право `billing.reconcile`, CSV `orgnr;period;currency;group;productCode;quantity;amountExVat;externalRef`); в протокол записываются идентификатор и SHA-256 сравнения, а не сами суммы клиентов, если протокол хранится вне компании. Программа сравнивает суммы без MVA; MVA исполнитель сверяет с документом PowerOffice отдельно (заказ несёт только код продукта). Плательщик прогона, которого нет в файле, программа покажет как `MissingInFile`.

| Клиент / источник / период | Ожидаемая сумма без MVA (расчёт исполнителя) | Сумма в CRM | Разница | Объяснение разницы | Ссылка на замечание |
|---|---|---|---|---|---|

## 5. Блокирующие замечания

Блокирующее: сценарий нельзя пройти; деньги посчитаны неверно; видны данные, которых у роли быть не должно; потеряны или задвоены данные; действие необратимо и непонятно; пользователь без подсказки не может продолжить.

| ID | Сценарий/шаг | Описание | Серьёзность (Blocker / Major / Minor) | Ответственный (роль, не человек) | Срок закрытия | Дата закрытия | Доказательство закрытия (commit/manifest/тест, повтор шага) | Закрыто и перепроверено (да/нет) |
|---|---|---|---|---|---|---|---|---|
| F-01 | | | | | | | | |

Правило закрытия DEV-22-AC01: все `Blocker` закрыты и перепроверены исполнителем; `Major` закрыты либо приняты владельцем продукта письменно с причиной; `Minor` - в журнале.

## 6. Журнал замечаний (формат записи)

Один блок на замечание; ведётся по ходу сценария, а не по памяти после.

```
ID:            F-<номер по порядку внутри роли>
Найдено:       <дата, время> исполнителем <идентификатор>
Роль/учётка:   <роль приложения>
Сценарий/шаг:  <например FIN-3.5>
Ожидалось:     <из файла сценария>
Получено:      <факт, текст сообщения как на экране, язык интерфейса>
Шаги повтора:  <1..n; данные только синтетические>
Вложения:      <скриншот без персональных данных; ссылка, не сам файл с токенами>
Серьёзность:   Blocker | Major | Minor
Класс:         Defect | Missing-requirement | Matrix-question (docs/02 vs код) | Training | Data | Environment
Владелец:      <роль>
Срок:          <дата>
Статус:        new | confirmed | fixed | retested | closed | rejected (с причиной) | accepted-by-PO (с причиной)
Закрытие:      <commit/manifest, дата, кто перепроверил>
```

Если замечание касается матрицы ролей (класс `Matrix-question`), ссылка на строку в [role-matrix-mismatches.md](../DEV-21/role-matrix-mismatches.md); решение принимает владелец продукта (DEC-01/EXT-01), а не исполнитель.
