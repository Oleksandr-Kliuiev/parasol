## Required changes (P1, P2)

**1. P1. The authority-fence trigger silently no-ops under the fence's own RLS.** `docs/stage3/03_DATA_AND_CONCURRENCY.md:21-24` requires ENABLE+FORCE RLS on all action tables with the fence policy "verified workspace only" (that is, `atlas_app_workspace()`). Lines 35-40 make the Actor/ClientMembership/ApiToken/Connection triggers call a narrow SECURITY DEFINER function that updates only the fence row. Trigger: an owner session revokes a token (`UPDATE "ApiToken" SET "revokedAt"`), which is the normal path since the runtime has no auth-row write. Owner sessions set no `app.workspace_id`, and the definer is not the table owner, so the fence policy evaluates to NULL and the definer's UPDATE matches zero rows and succeeds. Impact: the revocation becomes visible without ever taking the fence lock, so a reservation holding the fence can read stale authority and the stated serialization guarantee (line 40, acceptance B3) is void. The same defect hits "Workspace creation installs it" (line 19) under FORCE RLS. Fix: specify (a) a dedicated fence policy for the definer role (`TO <definer> USING (true) WITH CHECK (true)`), runtime policy stays workspace-scoped; (b) the trigger derives the workspace from NEW/OLD, never from session settings; (c) the trigger RAISEs unless exactly one fence row was updated (`GET DIAGNOSTICS ROW_COUNT = 1`), so a missing row or a filtered row fails the authority mutation closed; (d) whether FORCE applies to the fence and mock tables at all, since the baseline deliberately does not FORCE (migration 202610071200 comment) and owner/seed/test setup relies on that.

**2. P1. The approver cannot see what they approve.** `01_SPEC.md:26-27` says title/description are shown only through the protected preview file, and `02_CONTRACTS.md:7,22` tie that file to `action-preview`, which needs `actions:request`. `02_CONTRACTS.md:36` makes `action-approve` supply the expected hash of the stored request, and line 52 strips title/body from `action-get`. An approver holding only approve+read therefore approves a hash blind, which contradicts "immutable intent-bound approval" as a human control. Fix: add an explicit approver-side protected preview (for example `action-get --preview-file <path>` for approve+read on that request) rendered from the stored canonical body, not re-derived, with the stored hash, same 0600 new-file rules. State that `action-approve --hash` must equal that stored hash.

**3. P2. Verification "one active at a time" has no lease, deadline owner or stale-release rule.** `04_EXECUTION_AND_PORT.md:34-36` increments a persisted count (≤3) and forbids a second active verification, and `03:13-15` lists only a count and timestamps on ActionAttempt. Trigger: the process crashes between incrementing the count and publishing a result. Impact: either the in-flight marker never clears (request stuck below budget forever) or nothing marks it in-flight and two verifications race, which line 35 forbids. Fix: add verification lease fields (nonce, startedAt, deadlineAt) and an explicit rule: `action-recover` may release a lease after deadline plus grace with the count consumed, a result arriving under a stale nonce is discarded and audited, and only the current nonce may publish.

**4. P2. "Separately protected" token digests in client-scoped action rows are unspecified.** `02:27` and `03:8-12,31-33` store requester and signer token digests in ActionRequest/ActionApproval and reread them to drive the `app.token_hash` lookup. The baseline (migration 202610071600) only ever exposes a digest to a transaction that already holds it; copying digests into rows readable under ordinary client scope widens that, and column-level SELECT revocation would break the recheck itself. Fix: choose and state one of: (a) store ApiToken row ID only and add an additive lookup policy on ApiToken (`workspaceId = atlas_app_workspace() AND actorId = atlas_app_actor()`) so the recheck reads revokedAt/expiresAt by row ID under the named actor; or (b) keep digests and specify the concrete protection (which role can SELECT that column, and that it never leaves the fenced transaction). Option (a) also removes the "digest" canary from C7.

**5. P2. Explicit REVOKED approval decision has no owner or command.** `03:12` and `03:50` define a REVOKED decision and a revocation transaction, `06` B4/C6 test revocation races, but `02:7-9` lists no `action-revoke`. Trigger: implementer must guess whether REVOKED is an approver-initiated command or the lazily recorded state when a guarded operation finds the signer's token/membership gone (`02:38-39`). Fix: define it. Recommended: both, with `action-revoke` limited to the original signer (approve+read, same membership) and REVOKED also recorded lazily with a safe code when authority loss is detected.

**6. P2. Adjacent changes to roles.sql and the runtime self-check are required but unspecified.** `prisma/roles.sql:48-51,129-158` requires exactly four roles and manages exactly one routine; `packages/graph/runtime-role.ts` fails startup unless `cleanupRoutines === 1` and the definer holds exactly `DEFINER_TABLE_PRIVILEGES`/`DEFINER_COLUMN_PRIVILEGES`. `03:38-39` adds a second SECURITY DEFINER function with "public EXECUTE revoked" but does not say who owns it. Trigger: if the existing cleanup definer owns it, its new UPDATE(version) on the fence fails `cleanupOwnerViolations`; if a new role owns it, roles.sql creation, validation and the self-check facts have no entry. Fix: specify the owner role (recommend a new NOLOGIN NOBYPASSRLS fence definer), its exact grants (SELECT and UPDATE(version) on the fence only, nothing else), the roles.sql delta, and the new self-check facts (fence trigger function exists exactly once, owner confined, runtime holds only UPDATE(workspaceId) on the fence, the four auth/Connection triggers present and enabled). Note that trigger functions need no runtime EXECUTE grant at fire time, so PUBLIC revoke is sufficient.

## Recommended changes (P3)

7. **Error vocabulary gaps** (`02:54-57`). ACTION_NOT_DUE is never defined. Say which code a PostgreSQL deadlock or serialization abort maps to (`03:44-45`), which code cancel-after-reservation returns (`04:46`), the generic authentication refusal code, and the verification-lease conflict code from finding 3.
8. **Preview-file path policy** (`02:51`, C7). Specify the flag, O_CREAT|O_EXCL|O_WRONLY at 0600, absolute path, refuse existing path or symlink, how "outside the repository" is decided, and exactly what the file contains (title, description, marker, hash only, or the full canonical JSON including customer key and token row ID). Recommend content-only plus hash.
9. **Checkpoint split contradiction** (`05:14-15` vs `02:22`). S3-A delivers a "fenced" preview and request, while fence migrations default to S3-B. Decide now: fence table, install and lock in S3-A; mutation triggers and definer in S3-B.
10. **Lock order vs Connection** (`03:42`). Do not row-lock Connection inside action transactions. `packages/connections/m365-disable.ts:30` takes Connection FOR NO KEY UPDATE and would then take the fence through the new trigger; an action transaction taking fence then Connection FOR SHARE creates an avoidable deadlock cycle. State that a plain read after the fence lock is sufficient under READ COMMITTED.
11. **UUIDv8 wording** (`02:21`). "First 128 bits" is then overwritten by version and variant bits, so 122 hash bits survive. Say so, and define the lone-surrogate and NFC steps as applied before hashing.
12. **Manifest nit.** `hashAlgorithm` says "sorted" without the key; the Stage 2 manifests say "sorted by path". Align the text.

## Residual risks (accepted for MOCK scope)

- MOCK success proves none of the live ambiguity semantics (timeouts, 429, partial creates, upstream idempotency); the package states this correctly.
- Fence safety depends on triggers firing; an owner with ALTER TABLE can disable them. Out of scope, but worth a self-check fact.
- OUTCOME_UNKNOWN can remain unresolved forever by design; no retention or erasure exists for ticket content.
- A permanently rotated requester token kills an approved request at reservation (canonical input binds the token row). Intended, but state it so it is not reported as a bug.

Checkpoints, acceptance matrix, deterministic idempotency, requester/approver separation, DB-clock-after-lock, audit atomicity, legacy Approval inertness and the no-network trap are otherwise consistent and implementable once findings 1 to 6 are closed in a re-frozen package.
