# M28 — локальный пробный проход и свежая задача после связи заявки

Локально принято 17 октября 2026, от M27 (`a66a672`). Публикации и развёртывания нет.

## Работа сотрудника

[Инструкция локальной демонстрации](../testing/LOCAL-DEMO.md) запускает настоящие
CRM Web/Worker и Atlas на 40 тестовых клиентах, 400 устройствах и трёх ролях.
`npm run demo:local` принимает новый абсолютный каталог и 1–120 минут (по умолчанию 30).
Таймер начинается после готовности. Рабочие провайдеры и внешние отправки выключены.
В терминале и `demo.json` есть только локальный URL, ссылки тестовых ролей и срок.

Команда использует общий проверенный lifecycle composition: новые БД, loopback bindings,
ограниченные SQL/PostgreSQL роли, отдельные документы/ключи/сертификат. Ctrl+C или таймер
закрывает свои процессы, проверяет принадлежность контейнеров и удаляет private runtime.
Существующий каталог не переиспользуется. Demo-report всегда diagnostic / accepted:false;
он не подменяет строгую автоматическую приёмку. Нормальный composition сохранил 9/9.

Полный проход инструкции обнаружил реальную помеху M27: после привязки заявки её ETag
обновлялся, а родительский список оставлял старую Activity. Следующее завершение задачи
получало защитный 412. Данные сохранялись, но требовалось лишнее восстановление контекста.
Теперь успешное сохранение связи помечает её текущий scope. Окно остаётся открытым для
учёта часов; после закрытия сохраняется исходная кнопка до возврата фокуса, затем родитель
перечитывает полную Activity. «Мои задачи», выбранная запись и общая лента скрывают старые
действия на время чтения. Следующий явный complete использует уже показанную свежую версию.

ETag связи не подставляется в старые поля задачи. Нет автоматического повтора complete,
изменения прав или ослабления M20. Отказ сохранения связи не запускает родительский refresh.
Фокус после обновления — на существующем Refresh my tasks / Refresh activity / Log activity.
Смена сотрудника/прав/клиента и поздние ответы сохраняют прежнюю изоляцию scope.

## Изменённые части

- `tools/demo`: строгие CLI arguments, безопасный public descriptor, ограниченное ожидание
  остановки и unit-проверки. Новый npm script; demo tests входят в существующий CI command.
- `tools/composition/run.mjs`: отдельный onReady lifecycle для демо; обязательная новая
  сборка и запрет совмещения с приёмочным browser-набором. Общие setup/cleanup сохранены.
- CRM frontend `TaskTicketButton` / `TaskTicketContent`: уведомление о собственной успешной
  записи после закрытия; `MyTasksPanel` / `ActivityTimeline` / `ActivityTimelineItem`:
  полное чтение Activity и стабильный focus target. Backend и схемы не менялись.
- `TaskTicketRefresh.test.tsx`, actual composition ticket/time scenario и инструкция.
  Mapping unit helper ожидает доступную кнопку после закрытия chooser, сохраняя assertions.

В каждом браузере Admin назначает отдельное активное наблюдение Technician. Получатель
читает источник из My Day, связывает сохранённую заявку, вручную вводит 0.25 собственных
часов, закрывает окно, получает свежую полную задачу и завершает именно её версию.
Task исчезает из открытых, исходное наблюдение Atlas остаётся OPEN. Никакой BFF response
не подменяется. Нормальный composition также сохраняет мобильные/keyboard/Axe проверки
в обеих темах. Снимки итогового прохода осмотрены.

Два отдельных lifecycle-прогона предшествовали UI-исправлению: все 31 root/tool inputs
после него совпадают. Итоговый общий запуск и трёхбраузерный guide используют уже новый
UI; 2698 принятых input hashes совпадают до/после. Все семь owned fixtures очищены,
включая два отклонённых guide-прогона. История диагностик сохранена в свидетельстве.

Backend 850 и Atlas 1421 inputs не менялись: принятые M26 939/94/208 и строгие Atlas
711/789/90 используются по точному совпадению. Эти наборы не перезапускались; более широкий
CRM browser 78/78 относится к M26. Исходные checkout, Git history и changed-source secret
scan проверяются перед локальным checkpoint. Рабочие аккаунты и VPS не затрагивались.

## Что остаётся

В инструкции есть таблица замечаний и ручного замера времени для сотрудников.
Автоматический проход доказывает работоспособность пути, а не человеческую экономию.
Отзывы, реальный baseline привычного процесса и отдельные внешние ворота остаются
неподтверждёнными; общий продуктовый goal активен.
