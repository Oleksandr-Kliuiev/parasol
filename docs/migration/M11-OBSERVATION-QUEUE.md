# M11 — полная очередь наблюдений клиента

Локальное продолжение M10 на ветке `feat/observation-queue` от `bbaf67f`.
Публикация, развёртывание и подключение рабочих credentials не выполняются.
Общая цель продукта и оставшиеся пробелы перечислены в [готовности продукта](../PRODUCT_READINESS.md).

## Интерфейс

В техническом блоке клиента появилась третья вкладка **Очередь и история наблюдений**.
Предупреждение о первых 100 активных наблюдениях M10 позволяет открыть её напрямую.
Очередь читает страницы по 25 записей. «Следующая», «Предыдущая», «Первая» и «Обновить
очередь» заменяют текущую страницу, а не складывают её с предыдущей.

Фильтры важности, срочности HIGH/CRITICAL и состояния применяются на сервере ко всему
выбранному набору. По умолчанию это OPEN/ACKNOWLEDGED; отдельно доступны RESOLVED/SUPPRESSED.
Поиск по описанию, ID и подтверждённому устройству ограничен текущей страницей и подписан
соответственно. Смена фильтров сбрасывает продолжение страницы и текстовый поиск.
Refresh начинает первую страницу с прежними серверными фильтрами.

Показаны текущий общий итог выбранного набора, распределение важности, число загруженных
строк, время чтения и состояния источников. Atlas использует keyset pagination, поэтому
новые события и изменения состояний могут менять totals между страницами. Это не
неизменяемый снимок; новая срочная запись перед текущим cursor видна после Refresh.

При чтении старые строки скрываются. Ошибки и отменённые/поздние ответы не возвращают
прежнюю страницу. Отказ Atlas в доступе или изменение связи вызывает повторную проверку
основного технического блока, чтобы прежние устройства нельзя было открыть соседней вкладкой.
Неверный/просроченный cursor предлагает начать первую страницу. Fixture mode показывает
явное отсутствие поддержки полной очереди; его фиксированная демо-страница не выдаётся
за серверно отфильтрованную историю. Все подписи доступны на nb/en/ru.

## API и защита

`GET /api/v1/parasol/customers/{CustomerId}/observations`

| Параметр | Значения |
| --- | --- |
| `severity` | ALL, URGENT, INFO, LOW, MEDIUM, HIGH, CRITICAL; по умолчанию ALL |
| `status` | ACTIVE, OPEN, ACKNOWLEDGED, RESOLVED, SUPPRESSED; по умолчанию ACTIVE |
| `cursor` | Непрозрачное продолжение BFF, отсутствует для первой страницы |

Неподдерживаемые фильтры получают безопасную ошибку 400. Нужны сессия сотрудника,
`parasol.atlas.read`, проверенная связь клиента и его индивидуальные Atlas credentials.
Reader сначала читает overview для текущего реестра устройств/источников, затем фиксированный
Atlas `/clients/{mappedClient}/observations?limit=25&status=...&severity=...&cursor=...`.
Обе операции вместе ограничены 10 секундами; overview — 2 МиБ, страница — 1 МиБ,
JSON depth 32. Redirects, cookies, автоматические повторы и исходные тексты ошибок отключены.

Сохраняются проверки scope каждого наблюдения, связи устройства, важности/срочности,
дат, ID, дубликатов и закрытая проекция M10. Страница должна соответствовать выбранным
состояниям/важности; totals и counts относятся ко всему выбранному набору, включая
последнюю или пустую позднюю страницу. После обоих чтений повторно проверяются пара
workspace/client и ID связи. При unlink/rebind старый результат отбрасывается целиком.

Atlas cursor не передаётся браузеру. BFF защищает его существующим IDataProtector,
привязывает к сотруднику, CustomerId, workspace/client, LinkId и фильтрам, ограничивает
15 минутами. Подмена, другой сотрудник/клиент/фильтры и истечение срока получают
INVALID_CURSOR до обращения к Atlas. Подлинное продолжение того же сотрудника/клиента/фильтров
при изменённой связи получает IDENTITY_CHANGED, чтобы убрать и родительскую сводку.
Повторный cursor источника также не принимается.
Atlas 400 для продолжения превращается в безопасный INVALID_CURSOR без чтения его тела.
Ответ API имеет `Cache-Control: no-store`. В БД CRM очередь и cursor не сохраняются.

Новых зависимостей, таблиц, миграций или команд изменения состояния Atlas нет.
Reader очереди и защита курсора зарегистрированы только в веб-хосте, после настройки
Data Protection. Фоновый Worker не получает зависимости от браузерных ключей.
Имена людей, исходные payload, внешние event/connection IDs и финансовые значения
не попадают в DTO. Shared frontend-контракт и отображение строк используются M10 и M11.

| Production SPA build и бюджет | Пройдены; initial bundle 291,4 КБ gzip при бюджете 300 КБ |
| Root tooling, импортированная история, `git diff --check`, Gitleaks | Пройдены |

SQL regression и новая очередь проверялись отдельными целевыми прогонами; не заявляется
повтор всего CRM SQL-набора. Итоговые перечисленные наборы без failures/skips.
Основные сценарии: cursor binding/expiry/tamper, фильтры истории, источник с чужим scope,
пустая последняя страница, изменение связи во время чтения, отмена/поздний ответ, отзыв
доступа, навигация за первые 100 записей, узкий экран и обе темы.

Независимая проверка выявила смену связи до Next: исправлено различение старой identity
и испорченного cursor. Frontend-тест обнаружил гонку быстрого refetch, при которой
React Query мог не отрисовать промежуточное fetching-состояние. Явное скрытие до завершения
проверки и ключ сотрудник/ревизия гарантируют сброс всей прежней очереди. Проверены
быстрый и отложенный ответы новой карточки.

Первый браузерный запуск обнаружил регистрацию cursor-сервиса в общем модуле, из-за которой
Worker не запускался без IDataProtectionProvider. Регистрация перенесена в Web;
сборки Web/Worker, SQL и архитектурные проверки повторены после исправления.
Итоговый браузерный прогон подтвердил фактический запуск обоих хостов. Проверки Axe
прошли в светлой/тёмной теме на экране 390 px без отключения контраста; обе мобильные
карточки осмотрены визуально. Переход на шестую страницу и серверный фильтр LOW
проверяют доступ к записи за пределами первой сотни.

В браузерных тестах контролируются только технические ответы BFF; CRM API, вход Development,
клиентская карточка и SQL настоящие. SQL integration вызывает настоящий BFF и локальный
WireMock Atlas. Это не проверка двух совместно работающих приложений с PostgreSQL;
такой локальный сценарий остаётся отдельными пилотными воротами. Реальные провайдеры,
Entra и VPS не менялись, полные наборы Atlas не перезапускались, поскольку его код не изменён.
