## Что видит сотрудник после M42

- **Вкладка клиента «Sikkerhetskopi»** (NN «Tryggingskopi», EN «Backup»; под «Mer», пока её не открыли). Сохранённая копия
  CloudAlly и время её чтения («CloudAlly lest 15:05»; незаконченное или опоздавшее чтение — предупреждением, как у
  оповещений). Плитка на службу — «E-post», «OneDrive», «SharePoint», «Teams og grupper»: сколько в копии и что не так
  («1 feilet · 1 ikke i kopi») или «Alt i orden». Строка лицензий из Partner Center: «2 lisensierte brukere har ikke e-posten
  i sikkerhetskopien: 4 lisensierte, 2 i kopi (Partner Center, 21.10.2026)», а без данных Partner Center — прямо, что
  проверить нельзя. Аккаунт CloudAlly с датацентром; аккаунт вне EU помечен «Utenfor EU».
- **«Tjenester i CloudAlly»** — задачи (служба аккаунта): сколько пользователей или сайтов, сколько требуют внимания,
  последняя копия, «På pause» / «Kjører»; «Kopier nå», «Fortsett» и в меню «Sett på pause …».
- **«Brukere og områder»** — ящики, OneDrive, сайты и команды; сначала то, что требует внимания (не удалось, старше
  предела, на паузе, не в копии), затем по имени. Фильтры «Trenger tiltak» и по службе, поиск по имени и адресу. У
  неудачной копии — слова CloudAlly и ссылка на его страницу помощи. В меню строки: «Ta sikkerhetskopi nå», «Ta med i kopi»
  (пользователь, которого CloudAlly знает, но не копирует) и «Gjenopprett …».
- **Мастер восстановления** «Gjenopprett …»: куда — «Last ned som PST» (почта) или ZIP (файлы), «Til en annen konto i
  samme domene» (для SharePoint — «Som et nytt område»), «Tilbake på samme sted»; затем день (не позже сегодняшнего;
  берётся копия на конец дня), флажок «Ta med slettede elementer» и прямая фраза, что отдельное письмо или файл
  восстанавливаются в CloudAlly. «Fortsett» открывает обычное подтверждение действия M39.1 с предпросмотром.
- **Пробелы покрытия о копиях** в `/alerts` (источник «Parasoll»): «E-post: sikkerhetskopien i CloudAlly feilet for 1 av 2
  (Fjord IT AS)», «… ingen sikkerhetskopi i CloudAlly på over 26 timer …», «… står på pause …», «2 lisensierte Microsoft
  365-brukere har ikke e-posten i sikkerhetskopi (…)». Панель пробела ведёт на вкладку клиента («Åpne kundens
  sikkerhetskopi»). В «Dekningskontroller» — четыре новых правила; у правила «старше» предел «Timer siden siste kopi»
  (2–168, по умолчанию 26).
- **Связь аккаунта с клиентом** — на экране «Сопоставления» (`/admin/mappings?system=cloudally&type=Customer`): у CloudAlly
  нет оргномера, поэтому сам ничего не связывается; подсказки — по имени и домену адреса аккаунта. Без связи вкладка
  говорит «Ingen CloudAlly-konto er koblet til denne kunden» и ведёт к сопоставлению тех, у кого есть право.

## CloudAlly API: что подтверждено справочником

Источник — собственный справочник CloudAlly: `https://api.cloudally.com/documentation` (Swagger UI) загружает OpenAPI 3.1 из
`/v3/api-docs/AuthenticationV2` и `/v3/api-docs/ManagementV2`; плюс справочный центр support.cloudally.com. Единственный
публичный клиент — Ruby-гем `jancotanis/cloudally` (только чтение v1). С рабочим ключом ничего не проверялось.

- **Хост один для всех регионов** — `https://api.cloudally.com` (единственный сервер в справочнике; региональные имена не
  разрешаются, сам хост — в AWS us-east-1). Регион — свойство аккаунта (`EU`, `EU_FRANKFURT`, `EU_PARIS`, `EU_STOCKHOLM`,
  `EU_ZURICH`, `LONDON`, …). «Регион EU» в CRM поэтому — ожидаемый датацентр аккаунтов (`Backup:Region`, по умолчанию `EU`):
  аккаунт вне его вкладка помечает.
- **Вход партнёра:** `POST /v2/auth/partner`, заголовки `client-id` и `client-secret` (ключ приложения из портала,
  Integrations → API; секрет показывается один раз), тело `{email, password}` пользователя портала → `accessToken`,
  `expiresIn`, `refreshToken`, `refreshTokenExpiresIn`. Обновление — `POST /v2/auth/refresh` с теми же заголовками и
  `{refreshToken}`. Отдельного объекта «API-пользователь» в API нет: токен всегда привязан к пользователю портала, поэтому
  «отдельный API-пользователь» — это партнёрский пользователь, заведённый для Parasoll (в v2 — с ролью `custom` и только
  нужными правами: запуск, пауза, восстановление, экспорт копий).
- **Партнёрские (reseller) вызовы v2**, которые читает и вызывает CRM:

| Что | Вызов |
| --- | --- |
| Аккаунты клиентов партнёра | `GET /v2/resellers/accounts?page&pageSize` |
| Все задачи всех аккаунтов | `GET /v2/resellers/accounts/backup-tasks` |
| Статус каждой копируемой сущности | `GET /v2/resellers/accounts/backup-statuses` (страницы и `nextPageToken`) |
| Задача с её сущностями (в том числе `NOTACTIVE`) | `GET /v2/resellers/accounts/{account}/backup-tasks/{task}` |
| Счета по аккаунтам | `GET /v2/resellers/bills` |
| Копировать сейчас: задачу / сущность | `POST …/backup-tasks/{task}/backupNow`, `…/entities/{entity}/backupNow` |
| Пауза, возобновление задачи | `POST …/backup-tasks/{task}/pause`, `…/activate` |
| Включить сущность в копию | `POST …/backup-tasks/{task}/entities/{entity}/activate` |
| Восстановление, экспорт | `POST /v2/resellers/accounts/{account}/recovery/restore`, `…/recovery/export` |
| Отключить аккаунт (подписка отменяется, аккаунт удаляется) | `DELETE /v2/resellers/accounts/{account}` + `client-id`/`client-secret` |

  Голого `/v2/resellers` в справочнике нет (список реселлеров — только у дистрибьютора, `/v2/distributors/resellers`);
  партнёр работает через `/v2/resellers/accounts/…`. Последняя попытка позже последнего успеха — по словам справочника,
  признак неудачной копии.
- **Чего API не умеет**, и что поэтому остаётся в консоли: поиск и просмотр отдельных писем и файлов в копии (их id не
  отдаются, так что восстанавливаются только ящик, OneDrive или сайт целиком), ссылка на скачивание экспорта, подключение
  тенанта и создание задачи (OAuth в интерфейсе CloudAlly), настройки задачи (расписание, автодобавление новых ящиков —
  по умолчанию выключено), журналы. Лимиты запросов не опубликованы.

## Как устроено

### Интеграция `Crm.Integrations.CloudAlly` (часть 2)

- `CloudAllyTokenProvider` по образцу `PowerOfficeTokenProvider`: токен кешируется и общий; истёк — refresh-токеном, отказ —
  новым входом. `expiresIn` в справочнике без единиц, поэтому читается как Unix-время в мс или с, иначе секунды от сейчас;
  минута запаса, не дольше недели. `CloudAllyAuthHandler` ставит Bearer и `client-id`/`client-secret` (их шлёт и клиент
  CloudAlly; справочник объявляет их только у части вызовов) и на 401/403 один раз берёт новый токен.
- `CloudAllyClient`: без перенаправлений (`ProviderHttp.NoRedirects`), повтор только чтений (запись — только на 429),
  ограничитель 120 запросов в минуту, страницы по `totalPages` и токену; страница, которую нельзя прочитать, или
  бесконечный список роняют всё чтение. Даты принимаются во всех формах справочника (`yyyyMMddHHmmss` числом и текстом,
  ISO, Unix-время), `yyyyMMddHHmmss` — как UTC.
- Ключи (`ClientId`, `ClientSecret`, `Email`, `Password`) — только в закрытой конфигурации Worker
  (`deploy/hostinger/README.md`); Web получает переключатели (`Enabled`, `WriteEnabled`, `DryRun`, `WriteAllowedCustomerIds`,
  `EnabledActions`).
- Задания: `cloudally-accounts` (ежечасно, аккаунты во внешние записи для сопоставления), `cloudally-backups` (раз в два
  часа: задачи связанных аккаунтов, сущности каждой задачи, статусы — к сущностям по задаче и имени, так как id сущности в
  статусе нет; одно полное чтение → `IBackupApi.ApplySnapshotAsync` → `ICoverageCheck.CheckAsync("cloudally", …)`),
  `cloudally-bills` (ночью, строки счетов дня). Все три — на `/connections` и в `FreshnessLimits`.
- Чтение охватывает все связанные организации и все организации с сохранёнными копиями: аккаунт, который CloudAlly больше
  не перечисляет или чью связь сняли, забывается со всеми задачами и сущностями при следующем полном чтении.
- Служба по источнику: `MS365` и `O365*` — почта, `ONEDRIVE`, `SHAREPOINT(_MULTI)`, `MSTEAMS`/`MS365GROUP*`/`MS365TEAM_*` —
  Teams и группы, остальное — «Annet».

### Модуль `Crm.Backup` (схема `backup`, часть 1)

- `backup.Accounts`, `Tasks`, `Entities` — зеркало последнего полного чтения (миграция `CloudAllyBackups`, только в контексте
  модуля); `BillLines` — строки счетов дня с ключом `{system}:{account}:{day}:{type}:{source}:{service}` (повтор дня
  заменяет, прошлые дни — история). Пишут только чтения; записи под app lock `backup:{system}` одной единицей работы.
- `BackupStates.Of` — одно правило состояния для вкладки, фильтров и правил: в стороне (`IN_ANOTHER`, `ARCHIVED`, …) →
  не в копии (`NOTACTIVE`) → пауза (задачи или сущности) → не удалось (ошибка CloudAlly; или последняя попытка позже успеха
  больше чем на минуту, если копия сейчас не идёт) → старше предела (или ни одной копии, а CRM знает сущность дольше
  предела) → ждёт первой копии → в порядке. В SQL то же правило — выражением ранга (`BackupQueries`).
- Чтения вкладки (`service.read`): `GET /api/v1/backup/organizations/{id}` (время чтения через `ISyncCompletenessSource`,
  аккаунты, счётчики по службам, задачи, проверка лицензий) и `GET …/entities?service&state&q&cursor&limit` (keyset:
  ранг состояния, имя, id).
- Предел «старше» — настройка правила в модуле Service; вкладка читает его через новый контракт `ICoverageLimits`.

### Правила покрытия

Регистрирует модуль Backup (`ICoverageRule`), проверяет и хранит Service после каждого полного чтения CloudAlly. Пробел — на
задачу (службу аккаунта) или на клиента, не на ящик: отозванное согласие тенанта — одно оповещение на службу, а не на
каждого пользователя; кто именно — во вкладке.

| Правило | Когда | Важность |
| --- | --- | --- |
| `cloudally.backup-failed` | у задачи есть сущность с ошибкой или с попыткой позже успеха | критично, если не удалось у всех, иначе предупреждение |
| `cloudally.backup-late` | последняя успешная копия старше предела (26 ч), а ошибки нет — копия не запускалась | критично, если старше у всех |
| `cloudally.backup-paused` | задача или часть её сущностей на паузе | предупреждение |
| `cloudally.user-not-backed-up` | лицензий с ящиком (Partner Center) больше, чем ящиков в копии почты | предупреждение |

Лицензии — `ILicensingApi.GetLicenseReadingsAsync` (новый метод: последнее чтение каждого SKU за две недели, а не только SKU
каталога). Партнёр-центр считает лицензии по SKU, не по людям, поэтому правило — счёт: сумма назначенных лицензий из списка
`Backup:MailboxSkus` (Business Basic/Standard/Premium, E1/E3/E5, F3, Exchange Plan 1/2/Kiosk/Essentials, с вариантами по
началу имени) против числа разных ящиков в копии. Клиент без чтения Partner Center не проверяется — пробела нет, а вкладка
прямо говорит, что проверить нельзя. Настройки четырёх правил добавлены данными миграции Service `BackupCoverageRules` (схема
Service не менялась).

### Действия (путь M39.1)

Все — `IVendorActionHandler` с `CloudAllyActionGate`; права `service.write`/`service.read`; все виды выключены, пока их не
перечислит `Integrations:CloudAlly:EnabledActions`; allow-list — по id аккаунта CloudAlly. Каждое действие сначала читает
задачу живьём: что уже так — «Пропущено», чего нет — «Отклонено»; после отправки задача читается снова и сразу сохраняется
(`IBackupApi.ApplyTaskAsync`), поэтому вкладка показывает итог без ожидания следующего полного чтения.

| Вид | Цель | Уровень | Повтор без ответа |
| --- | --- | --- | --- |
| `backup.run` | задача или сущность | Standard | да (идущая копия не запрашивается дважды) |
| `backup.activate` | сущность `NOTACTIVE` | Standard (эффект: CloudAlly начнёт брать за неё плату) | да |
| `backup.pause` / `backup.resume` | задача | Disruptive (причина) / Standard | да |
| `account.deactivate` | аккаунт | Destructive | да (аккаунт сначала ищется) |
| `restore.export` | сущность почты, OneDrive, сайта | Disruptive | нет → «Неясно» |
| `restore.other` | то же; другой аккаунт того же домена, для сайта — новый сайт | Disruptive | нет |
| `restore.in-place` | то же | Destructive | нет |

Экспорт и восстановление в другой аккаунт отдают данные одного человека другому, поэтому спрашивают причину. Дата
отправляется как конец выбранного дня `yyyyMMdd235959`. Почта экспортируется в PST (`downloadToPst`), файлы — ZIP;
`inPlace` ставится только для OneDrive и SharePoint. Ответ `needRedirect` (CloudAlly хочет вход в тенант клиента) — итог
«Неясно» (`VND_RESTORE_SIGN_IN`), адрес перенаправления CRM не открывает. `restoreOption` не задаётся: CloudAlly решает
конфликты по умолчанию.

### Персональные данные

- Ссылки панели пробела закрывали панель сами, а закрытие шло назад по истории и отменяло переход (первый полный прогон,
  все три браузера).
- Мастер восстановления в WebKit оставался `aria-hidden` (см. UX-проход); тест проверяет, что мастер открывается с фокусом
  на первом способе.
- Чтение задачи после «копировать сейчас» стирало ошибку и время попытки сущностей; связь, снятая с клиента, оставляла его
  копии в базе; число сущностей задачи считало неактивные (найдено ревью кода, покрыто SQL-тестами).
- Старые тесты, которые задела M42: `alerts-a11y.spec` искал единственный переключатель «Raise alerts», а M42 добавила
  четыре правила (теперь — переключатель в разделе правила Atera); `alert-task.spec` открывал панель адресом возврата
  входа и скрывал страницу, которую вход ждёт (вход теперь на очереди, панель — следующим переходом).
- Вне M42: гонка в `tickets.spec.ts` (M39) под Firefox — см. риски.

### UX-проход (user-task-walkthrough, ux-copy, design-critique, accessibility-review)

Задачи техника: всё ли в порядке с копией клиента; кто не копируется и почему; «копировать сейчас» после исправления причины;
включить нового сотрудника; восстановить ящик, OneDrive или сайт на дату; отреагировать на пробел покрытия; отключить аккаунт
ушедшего клиента. Найдено и исправлено:
- Связанный, но ещё не прочитанный аккаунт вкладка называла «не связан» (ноль из непрочитанного источника): теперь вкладка
  читает связи клиента и говорит «En CloudAlly-konto er koblet …; sikkerhetskopiene vises etter neste lesing av CloudAlly».
- После «копировать сейчас» строка пользователя не показывала, что копия идёт: чтение задачи после действия сохраняет
  «Kjører», и строка показывает его до следующего чтения.
- Негде было проследить, что просили у CloudAlly для клиента (восстановление идёт часами): панель «Handlinger i CloudAlly» —
  пять последних действий с итогом, кто и когда, с переходом к карточке действия.
- С выключенными действиями кнопки просто отсутствовали: при праве записи вкладка говорит, что изменения в CloudAlly в этой
  установке выключены.
- Тексты (ux-copy): одно действие — одни слова везде (кнопка, пункт меню, заголовок и кнопка подтверждения: «Sikkerhetskopier
  nå» / «Ta tryggingskopi no» / «Back up now»; то же для «Ta med i sikkerhetskopien» и видов восстановления); «For gammel» →
  «Forsinket» / «Forseinka» / «Overdue»; заголовок пробела без двойного «for» («E-post: 1 av 2 uten sikkerhetskopi i CloudAlly
  på over 26 timer»); «нет данных Partner Center» говорит, что сделать; одинаковые кнопки задач различаются именем задачи в
  доступном имени («Back up now: Mail», WCAG 2.5.3).
- Мастер восстановления в WebKit открывался скрытым от вспомогательных технологий: WebKit при фокусе на поле даты шлёт
  `focus`, но не `focusin`, tabster не видел, что фокус вошёл в диалог, не включал его модальность и ставил на сам диалог
  `aria-hidden` (VoiceOver в Safari его бы не прочитал). Теперь мастер спрашивает сначала способ, потом день, и открывается
  на первом способе; e2e проверяет фокус. Тот же дефект есть у старых диалогов, которые открываются на поле даты, — см. риски.
- Ссылки панели пробела («Åpne kundens sikkerhetskopi», клиент, устройство) сами закрывали панель, а закрытие возвращало
  историю назад и отменяло переход по ссылке (панель, открытая из строки очереди). Теперь ссылка просто уводит со страницы, а
  `?alert=` уходит вместе с адресом.
- design-critique: на телефоне датацентр аккаунта переносился отдельной строкой «· data center EU» — разделитель начинал
  строку; теперь он держится за имя неразрывным пробелом. Остальное по снимкам всех состояний в двух темах: проблемы видны
  первыми (красная и янтарная подпись плитки, сортировка строк, «Trenger tiltak» со счётчиком), вкладка собрана из тех же
  `Panel`, `FigureGrid`, `RecordRow` и `FilterChips`, что «Drift», мастер ставит адрес «в другой аккаунт» сразу под выбором.
- accessibility-review: новых нарушений WCAG 2.2 AA нет (axe и замеры аудита — контраст, цели ≥ 24 px, края полей, фокус,
  перенос на 320 px); цвет нигде не единственный признак — подписи «1 feilet», «På pause» словами; ошибки мастера названы
  текстом. Кнопки меню строк — 24–32 px, как в остальных списках CRM: уровень AA (2.5.8), но не 44 px AAA.

Рассмотрено и оставлено: вкладка — под «Mer» (шесть ежедневных разделов UX-2026 В4); к копиям обычно ведёт оповещение, его
панель открывает вкладку, а открытая вкладка встаёт в ряд. Строка о копиях во вкладке «Drift» — после слияния с M41, которая
меняет ту же вкладку. Строка свежести очереди называет только источники оповещений (Atera; с M41 и Huntress), хотя пробелы о
копиях зависят от чтения CloudAlly: так же было с пробелами M40 о молчащих агентах; свежесть CloudAlly видна во вкладке, куда
ведёт панель пробела, и на `/connections`.

## Риски и следующие шаги

- **Рабочий аккаунт не проверен** (по аналогии с EXT-03 для Atera): вход партнёра с отдельным пользователем и его ролью
  `custom`, нужен ли `client-id`/`client-secret` на каждом вызове, единицы `expiresIn`, срок жизни refresh-токена, влияние
  2FA/SSO и ограничений IP аккаунта (если включены — адрес VPS нужно доверить в CloudAlly).
- **Форматы, которые справочник не называет:** `lastBackupDate`/`lastBackupAttemptDate` (текст), часовой пояс
  `yyyyMMddHHmmss` (принят UTC), формат `date` восстановления (отправляется `yyyyMMdd235959`), значения
  `backupStatus[].status`. Проверить на первом чтении.
- **Соответствие источников службам** выведено из имён (`MS365` — Exchange и т. д.); «все активные статусы» могут не
  включать сущности на паузе — тогда у них нет времени попытки, а состояние всё равно «пауза».
- **Восстановление:** в другой аккаунт — только тот же домен (по справочному центру); без `restoreOption` CloudAlly решает
  конфликты сам; id задания восстановления не возвращается, итог виден только в CloudAlly; ссылка на экспорт приходит
  письмом. Первое восстановление — на тестовом клиенте (`WriteAllowedCustomerIds`).
- **Отключение аккаунта** удаляет копии; есть ли у API семидневная отсрочка, как у интерфейса, — не подтверждено.
- **Лимиты запросов** не опубликованы: по умолчанию 120 в минуту и задача в два часа; чтение задачи с сущностями — запрос
  на задачу связанного аккаунта.
- **Резидентность данных:** API (и с ним адреса и статусы пользователей EU-аккаунтов) идёт через AWS us-east-1; это
  обработка самого CloudAlly, но для договора о данных стоит знать.
- **Проверка лицензий — счёт, а не люди:** у пользователя с двумя «ящичными» SKU лицензии посчитаются дважды; общие ящики без
  лицензии в копии уменьшают недостачу. Список `Backup:MailboxSkus` сверить с SKU клиентов.
- **Счета** хранятся (`backup.BillLines`), но не показываются: сверка с договором и `PerBackupSeat` — M43.
- **Слияние с M41:** общие места — локали, `ConnectionCatalog.cs`, `FreshnessLimits.cs`, `external-apis.mjs`,
  `playwright.config.ts`, `CoverageContracts.cs`, `alertText.ts`, `ModuleBoundaryTests`. Миграцию Service
  `BackupCoverageRules` (только данные) при слиянии с M41 генерировать заново поверх миграции M41; снимок модели руками не
  править. M41 добавляет `ISyncCompletenessSource.IsConnected` (выключенный и ни разу не читанный источник не попадает в
  строки свежести): после слияния строку чтения CloudAlly во вкладке стоит подчинить тому же правилу.
- **Вне M42, найдено при проверке:** (1) в WebKit `focus()` на `<input type="date">` не даёт `focusin`, поэтому диалоги,
  которые открываются на поле даты, в Safari остаются `aria-hidden`, пока фокус не перейдёт на другое поле. По эвристике это
  `PriceListPage.tsx:301`, `ContractDialogs.tsx:276`, `ProjectPhaseForms.tsx:69` и `AlertHideDialog.tsx:78`, если оповещение
  уже загружено. Общее исправление — в `shared/components/Dialog.tsx`. (2) `tickets.spec.ts` (M39) кликает строку, пока
  отложенный поиск подменяет список заглушкой загрузки, и клик теряется (Firefox, первый прогон M42). Тесту стоит ждать
  сужения списка, странице — держать прежний список, пока грузится новый.
