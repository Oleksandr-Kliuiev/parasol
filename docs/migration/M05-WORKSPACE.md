# M05 — общий вход, роли и карточка клиента

PR #2 (этап M04) слит в `main` merge-коммитом `201ccc207a9a5398ff9882bce8a29897e3054bf7`.
M05 использует CRM как основной интерфейс Parasol: `/organizations/{CustomerId}`.
В этой карточке остаются контакты, договоры, сервис, документы и разрешённые финансовые
разделы. Техническая сводка прежнего сервиса интеграций на вкладке обзора, добавленная в M05,
удалена вместе с сервисом в [M38](M38-OPERATIONS-IN-CRM.md): техника клиента теперь во вкладке
«Drift» на данных Atera. В силе остаются разделы о входе, ролях и ключах сессий.

## Вход и роли

Один вход через существующий CRM BFF, Microsoft Entra ID / OIDC + PKCE. Токены Microsoft
остаются на сервере; браузер получает HttpOnly/Secure cookie. Проверка tenant, активного
сотрудника, подтверждённых ролей, срока сессии, повторного подтверждения и CSRF сохранена.
Выбор роли через development login по-прежнему запрещён вне Development.
`AzureAd:*` — историческое имя конфигурации Microsoft identity, не Azure hosting.
Внешняя регистрация приложения, tenant и назначения реальных сотрудников не менялись.

Не создаётся новая база паролей или параллельный справочник ролей. Роли назначаются в Entra;
их изменения инвалидируют UI-кеш при следующем чтении `/bff/user`. Сервер проверяет доступ
на каждом запросе.

С M38 у всех трёх сотрудников полный доступ: группа Entra «Parasoll – full tilgang» назначена
роли `Crm.Admin`, которая даёт все права CRM; без Entra ID P1 роль назначается трём пользователям
напрямую ([ADR-030](../../apps/crm/docs/adr/ADR-030-full-access-group.md), настройка —
[runbook 12 §1а](../../apps/crm/docs/runbooks/12-roles-and-sessions.md#1а-полный-доступ-через-одну-группу)).
Таблица ролей M05 со вторым уровнем доступа прежнего сервиса (членство по клиенту и личные токены)
ушла вместе с ним; её текст — `git show 73c0158:docs/migration/M05-WORKSPACE.md`.

## Ограниченный HTTP-клиент

Серверное чтение сводки прежнего сервиса удалено в M38, но его правила остаются образцом для
клиентов поставщиков (M39.0 распространяет запрет перенаправлений на Atera, PowerOffice и
Partner Center). HTTP-клиент не перенаправляется, не передаёт cookies, не повторяет запросы и
не пишет заголовки/пути в HttpClient logs. Общий timeout 10 секунд, максимум ответа 2 MiB,
глубина JSON 32. Ошибки возвращают фиксированный статус без тела ответа/исключения источника.
Ответ браузеру `Cache-Control: no-store`. Связь клиента перечитывается после ответа источника:
unlink, rebind или удаление клиента не возвращают старые данные.

## Ключи сессий на VPS (без развёртывания)

Ключи сессий больше не требуют Azure Blob / Key Vault. Вне Development обязательны:

```text
DataProtection__KeyRingPath=/var/lib/parasol/session-keys
DataProtection__CertificatePath=/run/secrets/parasol-session-key.pfx
DataProtection__CertificatePassword=<secret-if-used>
```

Оба пути абсолютные. Постоянный каталог доступен только runtime-пользователю и сохраняется
между релизами; экземпляры BFF используют один каталог и application name. PFX содержит
закрытый RSA ключ; на Linux он загружается в память. Сертификат хранится отдельно от key ring,
доступ к нему ограничивается, резервные копии обоих защищаются и проверяются восстановлением.
При ротации предыдущие PFX подключаются через `DataProtection__PreviousCertificatePaths__0`
и далее; пароль общий для перечисленных PFX. Старые сертификаты нельзя удалять, пока
нужны зашифрованные ими ключи. Старые Azure параметры отклоняются при старте.
TLS/reverse proxy должны задавать точные AllowedHosts и KnownProxies; wildcard и доверие
всей приватной сети не являются предлагаемой конфигурацией Hostinger.

## Граница этапа и остаток до VPS-релиза

Новые production dependencies, таблицы и миграции не добавлены. Исходные репозитории,
их локальные изменения и импортированная история не изменяются.

Это проверенная локально первая реализация M05, не проверка реального tenant или релиз.

На момент M05 до развёртывания на Hostinger оставались контейнеры и reverse proxy, ресурсы
баз данных, замена production document store и проверка backup/restore. **Хранилище документов
CRM в production тогда ещё требовало AzureBlob**: его локальная реализация не гарантирует
неизменность при записи из нескольких процессов. Этот запрет не ослаблен; нужен отдельный
VPS store с атомарной записью и тестами. Это ограничение устранено в
[M06: документы VPS](M06-VPS-DOCUMENTS.md). Azure инфраструктура не создавалась.
