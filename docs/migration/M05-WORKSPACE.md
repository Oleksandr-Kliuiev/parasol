# M05 — общий вход, роли и карточка клиента

PR #2 / M04 слит в `main` merge-коммитом `201ccc207a9a5398ff9882bce8a29897e3054bf7`.
M05 использует CRM как основной интерфейс Parasol: `/organizations/{CustomerId}`.
В этой карточке остаются контакты, договоры, сервис, документы и разрешённые финансовые
разделы, а на вкладке обзора появляется техническая сводка Atlas.

## Вход и роли

Один вход через существующий CRM BFF, Microsoft Entra ID / OIDC + PKCE. Токены Microsoft
остаются на сервере; браузер получает HttpOnly/Secure cookie. Проверка tenant, активного
сотрудника, подтверждённых ролей, срока сессии, повторного подтверждения и CSRF сохранена.
Выбор роли через development login по-прежнему запрещён вне Development.
`AzureAd:*` — историческое имя конфигурации Microsoft identity, не Azure hosting.
Внешняя регистрация приложения, tenant и назначения реальных сотрудников не менялись.

Не создаётся новая база паролей или параллельный справочник ролей. Для трёх сотрудников
можно использовать существующие Admin, Technician и Finance либо нужные комбинации.
Роли назначаются в Entra и видны в меню сотрудника; их изменения инвалидируют UI-кеш
при следующем чтении `/bff/user`. Сервер проверяет доступ на каждом запросе.

| Роль | Техническая сводка | Финансовые суммы | Управление связью Atlas |
| --- | --- | --- | --- |
| Admin | Да, при наличии индивидуального доступа Atlas | Да | Да |
| Management | Да, при наличии доступа Atlas | Да | Нет |
| Technician | Да, при наличии доступа Atlas | Нет | Нет |
| ServiceLead | Да, при наличии доступа Atlas | Нет | Нет |
| ReadOnly | Да, при наличии доступа Atlas | Нет | Нет |
| Sales | Нет | Существующие права CRM | Нет |
| Finance | Нет | Существующие права CRM | Нет |

Новое право `parasol.atlas.read` не выдаёт Atlas membership. Даже CRM Admin не получает
данные без персонального токена Atlas с `context:read` на соответствующего клиента.
Обычная работа в карточке не требует второго входа. Самостоятельная операторская консоль
Atlas пока сохраняет свой интерфейс и вход; в M05 не переносится весь её функционал.

## Серверное чтение Atlas

`GET /api/v1/parasol/customers/{CustomerId}/workspace`:

1. Проверяет сотрудника и `parasol.atlas.read`.
2. Находит клиента CRM и проверенную связь M04. Не ищет по имени и не принимает scope из URL-параметров.
3. Выбирает персональный токен по внутреннему CRM UserId, проверяет workspace в конфигурации.
4. Вызывает только `GET /clients/{AtlasClientId}/overview`. Atlas проверяет токен, membership и RLS.
5. Проверяет `ClientContextV1`, совпадение workspace/client, перечисления, даты и неотрицательные суммы счётчиков.
6. Повторно читает связь после ответа источника: unlink/rebind/удаление клиента не возвращают старую сводку.

HTTP-клиент не перенаправляется, не передаёт cookies, не повторяет запросы и не пишет
заголовки/пути в HttpClient logs. Общий timeout 10 секунд, максимум ответа 2 MiB, глубина
JSON 32. Ошибки возвращают фиксированный статус без тела ответа/исключения источника.
Ответ браузеру `Cache-Control: no-store`.

В браузер идут только известные Atlas количества устройств/людей, активных наблюдений
по severity и состояние снимков источников с датами. Имена устройств/людей, исходные
payload, connection IDs и финансовые значения не проецируются. Количество записей
не представляется общим числом машин клиента. Пустой снимок, отсутствующий снимок,
устаревшие данные и недоступный источник различаются. Fixture отмечен как синтетический.
Сводка скрывается на время нового чтения и после ошибки; смена клиента использует отдельный кеш.
Тексты переведены на nb/en/ru.

## Конфигурация VPS (без развёртывания)

По умолчанию bridge выключен. Сервер получает конфигурацию из защищённого environment
или файла вне Git. Для включения:

```text
Parasol__Atlas__Enabled=true
Parasol__Atlas__BaseUrl=https://<private-atlas-origin>/
Parasol__Atlas__Employees__<crm-user-guid>__WorkspaceId=<atlas-workspace>
Parasol__Atlas__Employees__<crm-user-guid>__Token=<personal-atlas-token>
```

HTTP допустим только на loopback: например, Atlas, опубликованный исключительно на
`127.0.0.1` VPS. Для другого адреса нужен HTTPS. Origin без пути/query/userinfo.
GUID сотрудника берётся из CRM `/bff/user`, а не из email или имени. Настроить по одному
actor/token для сотрудника, с минимальными клиентскими membership; одинаковые токены
для разных сотрудников запрещены при старте. Не выдавать общий административный токен.
Отзыв токена/membership Atlas останавливает следующее чтение. Изменение роли Entra
применяется через существующие directory sync и перепроверку сессии CRM, с их прежними
границами задержки и role grace при недоступности каталога. Изменения конфигурации
применяются при перезапуске. Включение bridge не запускает синхронизации,
write-команды, AI-запросы или обращения к провайдерам.

Ключи сессий больше не требуют Azure Blob / Key Vault. Вне Development обязательны:

```text
DataProtection__KeyRingPath=/var/lib/parasol/session-keys
DataProtection__CertificatePath=/run/secrets/parasol-session-key.pfx
DataProtection__CertificatePassword=<secret-if-used>
```

Оба пути абсолютные. Постоянный каталог доступен только runtime-пользователю и сохраняется
между релизами; экземпляры BFF используют один каталог и application name. PFX содержит
закрытый RSA ключ; на Linux он загружается в память. Сертификат хранится отдельно от key ring,
доступ к нему ограничивается, резервные копии обоих защищаются и проверяются восстановлением.
При ротации предыдущие PFX подключаются через `DataProtection__PreviousCertificatePaths__0`
и далее; пароль общий для перечисленных PFX. Старые сертификаты нельзя удалять, пока
нужны зашифрованные ими ключи. Старые Azure параметры отклоняются при старте.
TLS/reverse proxy должны задавать точные AllowedHosts и KnownProxies; wildcard и доверие
всей приватной сети не являются предлагаемой конфигурацией Hostinger.

## Граница этапа и остаток до VPS-релиза

Новые production dependencies, таблицы и миграции не добавлены. Исходные репозитории,
их локальные изменения и импортированная история не изменяются.

Это проверенная локально первая реализация M05, не проверка реального tenant или релиз.
Для подключения нужны существующие сопоставления M04 и индивидуальные Atlas credentials.
UI импорта/исправления связей, подробные устройства/наблюдения и управление ими — следующие задачи.
Microsoft 365 специальные ресурсы Stage 2 не выдаются через Stage 1 overview.

До Hostinger deployment остаются контейнеры/reverse proxy, ресурсы SQL Server + PostgreSQL,
замена production document store и проверка backup/restore. **Хранилище документов CRM
в production всё ещё требует AzureBlob**: его локальная реализация не гарантирует
неизменность при записи из нескольких процессов. Этот запрет не ослаблен; нужен отдельный
VPS store с атомарной записью и тестами. Azure инфраструктура не создавалась.
