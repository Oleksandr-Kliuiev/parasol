# M37 — исторические исходящие счета и кредит-ноты

Локальная ветка `feat/m37-invoice-history`, база `f167f0f` — первый срез надёжного
импорта. Использованы только синтетические данные и localhost-провайдер.
Рабочий PowerOffice не подключался. Публикации, развёртывания и новых production
зависимостей нет. Остальные функции и исходные репозитории сохраняются.

## Контракт источника

Модель старого зеркала не совпадала с официальным reporting API: идентификатор
счёта — UUID, номер — число, дата — `VoucherDate`, остаток — `Balance`.
Кредит-нота определяется `VoucherType=OutgoingCreditNote`, отмена — `IsReversed`.
Новый адаптер использует эти поля и отдельный постраничный запрос
`GET /OutgoingInvoices/{id}/Lines`. Проверены публичные первичные источники:

- [Outgoing invoices workflow](https://developer.poweroffice.net/workflows/reporting/outgoing-invoices).
- [Официальный OpenAPI](https://swagger.poweroffice.net/openapispecs/outgoinginvoices.json), проверен 18.10.2026.

Заголовки фильтруются по `balanceLastChangedDateTimeOffsetGreaterThan`.
`LastChangedDateTimeOffset` и время изменения остатка сохраняются раздельно.
UUID, номер, дата документа, тип, валюта, обязательные суммы и признак отмены
проверяются; отсутствие данных вызывает ошибку вместо выдуманных значений.

## Сохранённая информация

- UUID, номер, заказ/внешняя ссылка, исходный CustomerId, даты, тип, отмена,
  связанный номер счёта и оба времени изменения.
- Валюта документа; подписанные net/total в валюте документа отдельно от
  posted net/total и остатка в валюте учёта клиента. Значения не пересчитываются
  и знак кредит-ноты не исправляется по предположению.
- Строки со стабильным ID, порядком, типом, описанием, товаром/единицей,
  количеством, ценой, скидкой/надбавкой, ставкой НДС как долей и исходными суммами.
- Семантический JSON заголовка и каждой строки, включая дополнительные поля API.
  Это нормализованный JSON, а не архив исходных транспортных байтов/PDF.

Заголовок и полный полученный набор строк сохраняются одним атомарным JSON-снимком
в `billing.Invoices.HistoryJson`; индексируется `(System, ExternalId)`.
Точность строк не ограничивается старыми decimal(18,2) полями проекции остатка.
Строки Text/Summary/TotalHours сохраняются, но не дублируют финансовые итоги.

Покрытие явно обозначено:

| Значение | Значение для пользователя |
|---|---|
| `EmptyUnverified` | Источник не вернул строки; это не доказательство пустого документа |
| `RetrievedUnverified` | Строки получены, но состав/суммы не позволяют подтвердить итоги |
| `Reconciled` | Известные типы и суммы полученных финансовых строк сходятся с заголовком с допуском 0,01 |

Даже `Reconciled` не доказывает побайтовую полноту оригинала: PowerOffice сообщает,
что для импортированных в Go документов строки могут отсутствовать или быть
неполными. Неизвестные типы сохраняются с непроверенным покрытием. Ограничения одного
снимка: 10 000 полученных строк и 4 MiB сериализованного JSON; превышение останавливает
проход без checkpoint. Это явная ошибка, а не усечение данных.

## Связь с клиентом и основанием

Единственный источник связи — подтверждённый `poweroffice/Customer/CustomerId`
в `ExternalLinks` с целью Organization. Совпадение имени, номера документа или
заказа не создаёт связь. Отсутствующий/непригодный клиент сохраняется как
несопоставленный; счёт не теряется.

Связь читается после provider HTTP, под SQL lease строки/диапазона источника,
до завершения отдельной транзакции Billing. Применяется существующий lease
пригодности организации. Старые счета перепривязываются после появления связи,
разрыва/замены связи, даже когда их больше нет в incremental-окне. Снимок источника
и время его изменения при этом не переписываются. Короткая сверка выполняется
за каждый сохранённый CustomerId; это не событие мгновенного обновления карточки
при unlink — актуализация происходит во время следующего invoice sync.

Основание CRM присоединяется по внешней ссылке/заказу только если его организация
совпадает с организацией исходного CustomerId. Исторический импорт не создаёт
оснований, начислений, заказов, часов, банков часов или подтверждённых платежей.
RelatedInvoiceNo сохраняется как исходная ссылка по номеру: она не доказывает
единственный UUID и не погашает автоматически другой счёт.

## Возобновление и миграция

- Новый stream `invoice-history-v1` начинает полную загрузку независимо от старого
  header-only курсора `invoices`, который сохраняется.
- Существующий exclusive runner M37 сериализует задания PowerOffice. Billing
  дополнительно сериализует собственные import/binding транзакции по системе.
- Все страницы строк дочитываются до записи документа. Ошибка заголовков/строк,
  JSON null, 403/503 или конфликт дублирующегося ID не продвигают checkpoint.
  Ранее завершённые документы остаются; предыдущий снимок незавершённого документа
  не заменяется частичным. Повтор из свежего scope обновляет UUID без дублей.
- Одинаковые строки с одним ID дедуплицируются; противоречащие копии — ошибка.
- Курсор публикуется после сохранения документов и сверки связей, с прежним overlap
  5 минут. Отсутствие balance timestamp сохраняет документ, удерживает старый курсор
  и увеличивает Failed; SyncSuccess не публикуется. Устаревшие версии не откатывают
  остаток и не порождают новые наблюдаемые движения.
- Новая миграция добавляет nullable-поля и фильтрованные уникальные индексы,
  сохраняя старые счета, URL и наблюдаемые движения. UUID нельзя подменить номером;
  разные UUID с одинаковым номером остаются разными документами (включая отменённые).
- Старые строки без доказанного UUID сохраняются отдельно и не объединяются
  автоматически по номеру. Перед реальным backfill нужны сверка и явное решение
  для таких legacy-кандидатов: иначе старое зеркало и новая история могут попасть
  в общий список/итоги как две записи. В этом срезе использованы только синтетические записи.
  Откат миграции при наличии исторических строк запрещён, чтобы не потерять снимки.

Изменение Balance остаётся наблюдаемым движением, не ledger-платежом.
Открытые отрицательные кредит-ноты входят в openOnly список; кредит-ноты не считаются
просроченными требованиями к оплате. Posted-проекция остаётся в валюте учёта;
это не готовая мультивалютная бухгалтерская сверка.

## Чтение и ограничения среза

Существующий список счетов получает UUID, тип, DocumentCurrencyCode и признаки покрытия.
Имя DocumentCurrencyCode явно относится к документу; старые TotalIncVat/Outstanding
продолжают отражать posted-суммы в валюте учёта клиента.
`GET /api/v1/billing/invoices/{id}/history` возвращает сохранённые строки/JSON
только при одновременных `billing.read` и `finance.read`. Provider HTTP при чтении нет.
Отдельный редактор/просмотр строк в веб-интерфейсе в этот срез не входит.

PDF/вложения, ledger-операции, входящие счета, payroll и остальные категории из
общего плана M37 ещё не реализованы этим срезом. Полная замена PowerOffice остаётся
отдельным решением. Модель пока предназначена для одного настроенного PowerOffice
аккаунта; переключение на иной источник без отдельного namespace и миграции
не поддерживается.
