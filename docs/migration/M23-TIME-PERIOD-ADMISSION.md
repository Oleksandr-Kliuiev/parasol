# M23 — согласованное закрытие периода

Локальный этап без публикации, развёртывания, новых зависимостей и рабочих провайдеров.
Протокол реализован и проверен локально. Общая финансовая готовность требует отдельных
границ восстановления, перечисленных ниже.

## Проблема и требуемое поведение

Прежнее закрытие считало New-записи до транзакции. Между нулевым результатом и сохранением
TimePeriod сотрудник мог добавить часы: оба действия завершались успешно, но закрытый
месяц содержал неутверждённую работу. Проверка «период уже закрыт» в форме этого не устраняет.
Также два утверждения разных записей могли одновременно расходовать один лимит SLA,
а пакетный отзыв — вернуть часы первого банка до обнаружения закрытого месяца второй записи.

Нужны два допустимых порядка: запись сохраняется первой и закрытие отказывает из-за New;
или закрытие сохраняется первым и новая запись отказывает из-за закрытого периода.
Технический конфликт не должен превращаться в автоматический повтор финансового действия.

## Протокол

`MonthAdmission` владеет SQL transaction application locks `time:period:YYYY-MM`.
TimePeriod глобален для базы, поэтому ключ не содержит клиента. Полный набор старых и
новых месяцев нормализуется, проверяется и берётся в числовом порядке до строк Time.
Режим выбирается сразу, без повышения Shared → Exclusive после захвата строк:

- Shared: ручные create/update/adjust/delete, терминальная отметка invoiced и исправление
  технической принадлежности сотрудника.
- Exclusive: close/reopen, approve/withdraw и импорт. Импорт выбирает максимальный режим
  заранее, поскольку любая ранее прочитанная запись могла стать утверждённой.

Ручная проверенная цепочка сохраняет порядок Customers → integration namespace/link →
Service ticket → Activity Task → месяцы → create receipt → Time entry/allocations.
Импорт и исправление техника сначала берут source namespace; это не даёт новой source-строке
проскочить между обнаружением списка и применением mapping. Namespace берутся в ordinal
порядке перед всеми месяцами. Обычные ручные строки источником не управляются.

После допуска записи повторно читаются под UPDLOCK в порядке GUID. Если запись успела
перейти в месяц вне исходного набора, команда возвращает TIM_WORK_CHANGED до эффекта,
а не захватывает новый ключ в обратном порядке. Периоды читаются по точным допущенным
ключам; старого сканирования всего closed set внутри записи больше нет.
TIM_PERIOD_BUSY сообщает отказ допуска и предлагает обновить состояние. Любой отрицательный
ответ sp_getapplock не допускает изменения; отмена прекращает ожидание.

`TimeMutationScope` создаёт отдельный nonretrying контекст и owning ReadCommitted transaction
для команд. Все поля, аудит, outbox и квитанция сохраняются до release при commit/rollback.
Обработчик событий присоединяется к уже существующей транзакции Time inbox: возврат из
handler и его локальный CommitAsync не завершают транзакцию владельца сообщения.
Source HTTP и файловых операций под этими блокировками нет. Отказ владельцу чужой
записи сохраняет TIM_NOT_OWNER до результата о закрытом периоде.

## Покрытие писателей и политика закрытой истории

- Ручные create/update/adjust/delete проверяют актуальные старый и новый месяцы под допуском.
  Исторический повтор M22 clientRequestId остаётся чтением уже принятой записи; он не
  пытается повторно допустить часы в закрытый месяц. Постоянная квитанция не меняется.
- Close считает New и создаёт/закрывает период в одной транзакции под Exclusive, включая
  отсутствующую строку периода. Повтор уже закрытого месяца не добавляет аудит или
  TimePeriodClosed. Reopen сохраняет обязательную причину и прежние права Finance.
- Approve сериализует весь набор месяцев, поэтому два утверждения разных записей перечитывают
  общий использованный лимит Covered последовательно. Предыдущая политика skipped сохраняется.
- Withdraw проверяет весь пакет и все месяцы до первого ReverseConsumption. Внутренний
  withdrawal импортера требует уже выданный admission; отдельного unfenced writer нет.
- Поздняя новая source-запись в закрытом месяце сохраняется с явным ReviewNote.
  Изменение существующей строки, затрагивающее любой закрытый старый/новый месяц,
  оставляет прежнюю финансовую дату/часы/allocations и помечает её для проверки.
  Invoiced остаётся неизменным финансовым снимком; изменившийся источник даёт review.
- BasisExportedHandler может завершить Approved → Invoiced в закрытой истории, удерживая
  Shared допуск до commit inbox. Это завершение уже выполненного экспорта, не новые часы.
- TechnicianMappingHandler исправляет только соответствующий внешний источник. Сходный
  external technician ID в ручном Crm-источнике не меняется; unknown source игнорируется.
  Исправление metadata допускается в закрытой истории и проходит через отслеживаемый аудит.

## Проверки

[Свидетельство M23](../testing/evidence/time-period-M23-2026-10-17.json): 917/917 CRM unit,
94/94 architecture, 102/102 затронутых SQL integration. Полный frontend — 562/562 в 64 файлах;
ESLint, app/E2E/composition TypeScript, production build и budget 291.7/300 KB проходят.
CRM browser — 70/70, включая новый реальный сценарий периода в Chromium/Firefox/WebKit.
Полный совместный source-build — 9/9, 577 Atlas requests и 0 mutating requests;
точная Task/ticket/time/receipt/privacy evidence и restricted roles подтверждены. Все
временные ресурсы очищены; пропусков, retries, flaky и исключений нет.

Первый SQL-прогон 100/101 сохранён. Драйвер вернул SqlException при отмене подтверждённого
SQL lock wait. Исправлена нормализация только при отменённом caller token; исходное
утверждение OperationCanceledException сохранено. В повторном полном наборе 102/102
также подтверждены rollback, отсутствие созданного периода и освобождение блокировок.
Первоначальный analyzer diagnostic CA1512 исправлен штатным ThrowIfNegative без suppression.

824 backend/build и 389 web inputs совпадают с проверенными SHA256; 2634 входов
совместного прогона не менялись во время выполнения. Atlas не изменён: 1421 вход совпадает
с отдельным строгим 711 unit / 789 PostgreSQL / 90 browser; он не запускался заново.
Сохранность исходных Git HEAD/status/refs, import history, diff-check и redacted secret scan
проверяются перед локальным checkpoint.

Сценарии SQL включают отсутствующую строку месяца и оба порядка close/create, все
финансовые writers до commit, изменение месяца после discovery, лимит SLA двух утверждений,
отказ mixed-month withdrawal до bank effects, late import/review, source collision mapping,
реальный inbox owner commit/rollback и потерянное подтверждение commit. Negative controls
используют фактический SQL lock timeout; ожидание отмены подтверждается SQL wait state.
Web/Worker роли проверяют Shared и Exclusive отдельно. UI использует реальный API в трёх
движках: отказ закрытия при New, утверждение, закрытие, сохранность отказанного черновика,
отсутствие Reopen у ServiceLead и явное открытие Finance с причиной.

## Интерфейс и сохранённые диагностики

Finance имеет TimeUnlock без TimeManage. Прежний общий wrapper скрывал Reopen даже
при разрешённом серверном действии. Кнопка теперь проверяет TimeUnlock отдельно; approve,
withdraw и close по-прежнему требуют TimeManage. Три unit-проверки воспроизводят права
Finance, ServiceLead и открытого месяца, а реальный сценарий проходит в трёх движках.
Новые period busy / moved / closed сообщения локализованы на nb/en/ru.

Первый browser-прогон 67/70 остановился в новых трёх случаях на выборе клиента: fill
менял текст Combobox, но не открывал список. Клавиатурный ввод соответствует существующему
сценарию времени; production picker, timeout и assertions не менялись. Отдельный полный
frontend 561/562 обнаружил преждевременный getByRole у Try again после закрытия модального
редактора. DOM ещё имел aria-hidden от Fluent. Проверка теперь ожидает ту же доступную
кнопку, без hidden-запроса или продления timeout; сохранность старого черновика и отказ
его восстановления проверяются по-прежнему. TypeScript также потребовал убрать
неподдерживаемый параметр exact из нового RTL-теста; строковое имя роли остаётся точным.

После совместного прогона менялся только независимый CRM browser oracle: локатор Date
учёл обязательную звёздочку и добавлено сравнение отправленной даты. Первоначальный
manifest 2634 входов не менялся во время composition; все production и composition
исходники до сих пор совпадают. Только этот неисполняемый в composition E2E-файл получил
новый hash и заново прошёл полный frontend/static и browser 70/70. Оба browser-прогона
67/70 сохраняются: первый остановился на Combobox, второй — на подписи Date со звёздочкой.
Ни один не считается acceptance.

## Границы

Application locks — протокол всех обновлённых писателей приложения. Они не запрещают
произвольный DBA SQL или offline restore. Восстановление требует остановки всех писателей
и штатной проверки консистентности перед запуском. Схема не меняется, но смешивать старые
и новые версии Web/Worker нельзя: прежняя версия не участвует в admission. Будущее
обновление VPS должно остановить оба приложения и jobs, затем запустить их согласованно.

Периодные блокировки сами по себе не делают общий commit между Contracts HourBank и
Time и не устраняют промежуток между реальным экспортом basis и асинхронным Invoiced.
Существующие idempotent consumption keys сохраняются; эти границы требуют отдельной
проверки восстановления до финансового пилота. Реальные аккаунты и Hostinger остаются
внешними воротами. Исходные репозитории и пользовательские изменения сохраняются отдельно.
