# M30 — карточка проверяет экземпляр связи клиента

При проверке ежедневного обзора обнаружено расхождение между техническими чтениями.
Карточка после ответа Atlas повторно сравнивала только workspace/client; очередь,
диалог назначения и «Мой день» также проверяли LinkId. Удаление и новое подтверждение
той же пары меняют LinkId. Старый запрос карточки мог завершиться READY после замены
связи, хотя должен был потребовать нового чтения.

## Исправление

`AtlasWorkspaceReader` сравнивает и пару, и LinkId, сохранённые до запроса Atlas,
с текущей identity после него. При изменении ответ — IDENTITY_CHANGED с null summary:
без устройств, наблюдений и прежних технических полей. Дополнительного запроса Atlas,
автоматического повтора или изменения новой связи нет. Сотрудник читает актуальную
карточку кнопкой Refresh. Существующие проверки прав и индивидуальные credentials сохранены.

Проверки на границе concurrent attention reader остаются: он дополнительно сверяет
identity своего исходного binding до и после общего reader. Уточнён только комментарий.
Не добавлены таблицы, production dependencies, команды провайдеров или новый контракт API.

## Доказательство

SQL integration удерживает ответ Atlas через TaskCompletionSource, выполняет реальное
удаление/подтверждение связи через CRM API и только затем освобождает ответ. Нет sleeps
для организации гонки. Четыре варианта — unlink, та же пара, другая пара и unchanged.
После изменения старые данные отклоняются; новый явный GET получает READY или NOT_LINKED.
Счётчик outbound handler доказывает отсутствие автоматического повтора.

До исправления новый тест на той же паре воспроизвёл READY вместо IDENTITY_CHANGED:
22 из 23 workspace SQL проверок прошли, одна упала именно на этой проверке. Контейнер
и приватное состояние удалены; безопасная диагностика сохранена отдельно.

Frontend regression начинает с устройств старой карточки, удерживает refresh, проверяет
немедленное скрытие данных, затем IDENTITY_CHANGED и отсутствие скрытого повтора.
Третий запрос выполняется явным Refresh; новые наблюдение/hostname отображаются,
а старый hostname отсутствует. Production UI не менялся. Первый черновик frontend-теста
искал hostname отдельным текстом на вкладке наблюдений; проверка исправлена реальным
переходом на вкладку устройств, без ослабления ожиданий.

Точные итоговые проверки и границы повторного использования результатов фиксируются в
[свидетельстве M30](../testing/evidence/workspace-link-M30-2026-10-17.json).
Настоящий composition проверяется отдельно от SQL handler fixture и frontend mock.
Тесты рабочие аккаунты не используют; нет исключений или автоматических retry.

сгенерированные приватные состояния удалены. Исходные репозитории сохранены по HEAD,
refs и полному локальному статусу. Ничего не опубликовано и не развёрнуто.

## Границы

Закрыт локальный инвариант scope при замене связи; это не подтверждение совместимости
рабочих провайдеров или удобства для сотрудников. Требуются отзыв по LOCAL-DEMO.md,
измерение времени и отдельно разрешённые внешние проверки. M29 остаётся свидетельством
native восстановления на своих четырёх images до M30; здесь оно не выдаётся за новую
сборку/restore. Storage, схема и native recovery tooling в M30 не менялись.
