## Что видит сотрудник после M41

- **Инциденты Huntress — снова оповещения** (раньше их не было нигде, `PRODUCT_READINESS.md`). Инцидент, эскалация и
  platform action — «Driftsvarsel» вида Security с меткой «Kilde: Huntress»: в очереди `/alerts`, в «Hastevarsler» на «Min
  dag», во вкладке «Drift» клиента; их можно назначить задачей, скрыть до дня, как любое оповещение. Важность Huntress
  переводится в две CRM: critical и high — «Kritisk», low — «Advarsel».
- **Панель инцидента** (`?alert=`): статус у Huntress («Venter på deg», «Huntress utbedrer», «Tilbake hos SOC-en til Huntress»,
  «Lukket i Huntress»), сводка SOC, индикаторы со счётом, план исправлений (шаг, кто его делает, статус, детали), комментарии,
  детали Huntress за кнопкой. Действия: «Godkjenn planen», «Send planen tilbake …» (раскрывающаяся форма: причина из списка
  Huntress — без предвыбора, пояснение, «Planen var nyttig»), «Merk som utført» у ручного шага, «Lukk i Huntress» после
  одобрения, комментарий (не у отчёта, которого Huntress больше не знает). Устройство инцидента — **агент самого инцидента**
  (не старый агент переустановленного компьютера): состояние изоляции, если Huntress его сообщил, и «Isoler enheten …» /
  «Opphev isoleringen …».
- **Срочный инцидент, закрытый в Huntress, ждёт человека.** Критичный инцидент, который Huntress закрыла сама, остаётся
  открытым в Parasoll: строка очереди, «Min dag» и «Drift» пишут «Lukket i Huntress for 2 timer siden – må bekreftes» (точное
  время — в подсказке `<time>`), панель объясняет, а «Bekreft lukking» (в панели и в меню строки) закрывает его; кто и когда —
  в истории оповещения. Инцидент, закрытый человеком через Parasoll («Lukk i Huntress» или последний ручной шаг), подтверждения
  не ждёт; любое другое действие (комментарий, одобрение, возврат плана) закрытие, сделанное самим Huntress, не подтверждает.
- **Эскалация:** о ком или о чём она (устройства, учётные записи), и «Lukk eskaleringen» с ответом. Эскалация доступа из
  неожиданной страны или VPN принимает ответ «Tilgangen var ventet» / «Tilgangen var uautorisert» / «Bare lukk den» — только для
  этих учётных записей; ответ не выбран заранее (он остаётся у Huntress навсегда), без выбора кнопка просит выбрать. Parasoll
  никого не блокирует и не отключает. **Platform action** закрывается в Huntress сама, когда причина
  устранена: панель говорит это и ничего не предлагает.
- **Карточка устройства:** одна строка на компьютер, Atera и Huntress вместе (серийный номер, MAC, имя хоста). У источника
  Huntress — «Defender: I orden / Ikke i orden · подстатус · meldt …», изоляция («Isolert fra nettverket», «Blir isolert»,
  «Isoleringen oppheves», «Ikke isolert»), версия агента (один раз: у устройства только с Huntress она — в инвентаре); действия
  «Isoler enheten …», «Opphev isoleringen …», «Fjern Huntress-agenten …». Железо карточки по-прежнему описывает Atera, раздел
  «I Atera» остаётся у устройств Atera.
- **Панель «Sikkerhet» во вкладке «Drift»:** что Huntress считает по связанной организации — фактурируемые агенты (и всего),
  не отвечающие, устаревшие, изолированные, идентичности, обучающиеся — и месячные отчёты (месяц, инциденты, сигналы,
  агенты, ссылка на PDF в Huntress), со временем чтения. Цифр нет — панель говорит, что Huntress их не дал, и как связать
  организацию (без утверждения «не связана»: связь могли сделать после последнего часового чтения); Huntress ни разу не
  читался — так и сказано; отчёты ещё не читались — тоже, нули не показываются. Huntress выключен и ни разу не читался — панели
  нет.
- **«Dekningskontroller»:** пять новых правил — «Enhet uten Huntress», «Enhet uten Atera», «Huntress-agent som ikke melder
  seg», «Utdatert Huntress-agent», «Defender beskytter ikke»; у правила со своим смыслом порога своя подпись поля («Dager før
  driftsvarsel», «Dager på eldre versjon»).
- **Сопоставления:** организации Huntress появляются на экране «Koblinger» и связываются с организацией CRM руками —
  номера организации у Huntress нет, автоматика не угадывает.

## Как устроено

### API Huntress (сверено с официальной документацией)

Источник — справочник Huntress `https://api.huntress.io/docs`, его OpenAPI 2.0 `https://api.huntress.io/v1/swagger_doc.json`
(прочитан 22.10.2026). Подтверждено и используется:

- база `https://api.huntress.io/v1/`, HTTP Basic: Base64 от `key:secret`; ключ аккаунта только читает, запись требует ключа
  пользователя (все действия пойдут от него);
- лимит **60 запросов в минуту на аккаунт, скользящее окно**; списки — `limit` (до 500) и `page_token`, ответ
  `{ <plural>: [...], pagination: { next_page_token, next_page_url } }`, одиночный ресурс — `{ <singular>: {...} }`;
- агенты: `defender_status`, `defender_substatus`, `defender_policy_status`, `last_survey_at`, `firewall_status` (`Disabled`,
  `Enabled`, `Pending Isolation`, `Isolated`, `Pending Release`), `last_callback_at`, `version`, `platform`, `serial_number`,
  `mac_addresses`, `ipv4_address(es)`; `POST/DELETE agents/{id}/isolation` (асинхронно), `DELETE agents/{id}` — удалённая
  деинсталляция, агент сразу уходит из аккаунта;
- инциденты: статусы `sent`, `closed`, `dismissed`, `auto_remediating`, `deleting`, `partner_dismissed`, `draft` (только по id);
  первые 10 исправлений внутри отчёта (`has_more`), `GET …/remediations`, `POST …/remediations/bulk_approval` и
  `bulk_rejection` (**одобрение и отказ — сразу для всех неодобренных шагов**), `POST …/remediations/{id}/completion`
  (`completed`, только `manual`), `POST …/resolution` (все шаги одобрены, статус `sent`), комментарии (≤ 2048, SOC их не
  читает);
- эскалации и platform actions: `open`, `overdue`, `resolved`, стабильный `type_code`, сущности — только при чтении по id;
  `POST escalations/{id}/resolution` с `determination`/`scope` для эскалаций доступа; без них — «dismiss» до следующего раза;
- организации с `actual_usages` (EDR: billable, unresponsive, outdated, isolated; ITDR; SAT) — только при чтении по id;
- месячные отчёты `GET reports` с `period` `start...end` и ссылкой на PDF.

### Клиент (`apps/crm/src/Integrations/Crm.Integrations.Huntress`)

- `HuntressClient` (`.cs`, `.Paging.cs`, `.Json.cs`): постраничное чтение с повторным чтением предыдущей страницы, токен,
  названный дважды, и нечитаемая запись проваливают чтение; 404 одиночного ресурса — «не знает». `ProviderHttp.NoRedirects()`.
- Два HTTP-клиента одного класса — **два бюджета**: чтения заданий 45 в минуту (`IHuntressClient`), действия людей 15
  (`IHuntressActionClient`), каждый в своём `SlidingWindowRateLimiter` с окном 70 с из 7 сегментов: запрос покидает окно только
  когда его сегменту полная минута, так что вместе не больше 60 за любые 60 секунд. Повтор: 429 — любой метод, 5xx и таймауты —
  только чтения. Сумма бюджетов > 60 не проходит проверку параметров при старте.
- Ключ и секрет — только `Integrations:Huntress:ApiKey`/`ApiSecret` конфигурации Worker; Web получает переключатели.
  Все переключатели записи закрыты по умолчанию: `WriteEnabled`, `DryRun`, пустой `EnabledActions`, `WriteAllowedCustomerIds`
  (id организаций Huntress). Ссылки на страницы Huntress — только шаблоны конфигурации (`IncidentUrlTemplate`,
  `EscalationUrlTemplate`, `PlatformActionUrlTemplate`, `AgentUrlTemplate`), по умолчанию пустые.

### Задания

| Задание | Cron по умолчанию | Что делает |
| --- | --- | --- |
| `huntress-organizations` | `25 * * * *` | организации — внешние записи экрана сопоставлений; для связанных — `actual_usages` в `security.ProductUsages` |
| `huntress-agents` | `35 * * * *` | агенты — устройства системы `huntress` в `service.Devices` по связанным организациям (полный список, ушедшие помечаются удалёнными), затем проверки покрытия Huntress |
| `huntress-alerts` | `*/5 * * * *` | открытые инциденты (`sent`, `auto_remediating`), эскалации и platform actions (`open`, `overdue`) с деталями в модуль Security, затем снимок оповещений вида Security |
| `huntress-reports` | `45 4 * * *` | месячные отчёты связанных организаций за 13 месяцев |

Чтение оповещений применяется только целиком. Хранимый открытый инцидент, которого списки больше не называют, читается по id:
`draft` (план отклонён, отчёт у SOC) — остаётся открытым, закрытый — закрывается, неизвестный Huntress — остаётся историей
со статусом `deleted`. Закрытый отчёт организации, связь которой убрали, всё равно записывается закрытым — под клиентом, у
которого он хранился (иначе его читали бы по id каждые 5 минут). **Чтение, начавшееся раньше действия человека, его не
отменяет:** снимок несёт `ReadStartedAt`, и оповещение, решённое после начала чтения (чтение после действия), им не
открывается заново; запись зеркала с более ранним `ReadAt`, чем хранимая, пропускается (`IncidentReading.ReadAt`,
`ExternalNotice.ReadAt`). Следующее чтение решает как обычно. Так же — эскалации и platform actions. Сущности эскалации читаются по id, только когда она новая или
изменилась после прошлого чтения. Оповещение инцидента — `incident:{id}`, эскалации — `escalation:{id}`, platform action —
`platform-action:{id}`; уведомление, затрагивающее несколько организаций, встаёт к первой связанной, уведомление всего аккаунта
(без организации) оповещением не становится.

### Модуль Security (`apps/crm/src/Modules/Security`, схема `security`)

`Incidents` (+ `Remediations`, `IncidentComments`, каскад), `Notices` (эскалации и platform actions, `Kind`), `SummaryReports`,
`ProductUsages`; миграция `HuntressMirror`. Пишет интеграция через `Crm.Security.Contracts/ISecurityApi` под app lock по
источнику и виду записи; чтение интерфейса — `GET /api/v1/security/{system}/incidents/{id}`, `…/escalations/{id}`,
`…/platform-actions/{id}`, `GET /api/v1/security/organizations/{id}/overview` (право `service.read`). Хранение — класс
`security.closed-incidents` (предложение — год после закрытия; до утверждения EXT-07 ночная задача только считает): закрытые
инциденты с планом и комментариями и решённые эскалации/platform actions; открытые не удаляются никогда.

### Модуль Service

- Устройство получило `Platform`, `AgentVersionSince` (когда устройство впервые прочитано с нынешней версией агента) и защиту
  `AntivirusStatus`/`Substatus`/`PolicyStatus`/`ReportedAt`, `Isolation`; `ExternalDevice` — `Platform` и `Protection`. У устройств
  Huntress второй id (`AlternateId`) — организация Huntress агента: по ней действия сверяются со списком разрешённых.
  `PerAteraDevice` по-прежнему считает только `System == "atera"`.
- Оповещение получило `ConfirmClose` и `SourceClosedAt`: критичное оповещение источника, который просит подтверждения
  (`ExternalAlert.ConfirmClose`, у Huntress — инциденты), полное чтение без него не закрывает, а помечает; повторное
  появление снимает пометку. `POST /api/v1/service/alerts/{id}/confirm-closed` (If-Match строки статуса, под lock источника),
  переход `AlertTransitionKind.Confirmed`. Закрытие из действия (`ResolveAlertAsync`) подтверждения не ждёт.
- `IServiceApi.ApplyDeviceAsync` (одно устройство после действия), `RemoveDeviceAsync` (агент удалён), `GetDeviceAsync`.
- Чтения сводки «Drift» и карточки машины называют и Huntress (`security-alerts`, `security-devices`). Источник, который
  выключен и ни разу не читался, в строках чтений не называется (очередь, «Min dag», «Drift», карточка машины, панель
  «Sikkerhet»): `ISyncCompletenessSource.IsConnected` отвечает по адаптеру, `ServiceSourceRead.ShownAsync` — правило в одном
  месте. Иначе при `Enabled=false` (по умолчанию до ключей) везде висело бы «Huntress er ikke lest ennå» в тоне предупреждения.
  Однажды прочитанный и выключенный после источник остаётся со своим последним (опоздавшим) чтением: его данные ещё видны.
- Миграция `HuntressDevices` — колонки устройств и оповещений и строки настроек пяти правил. **При слиянии с M42 (CloudAlly),
  если там тоже есть миграция контекста Service, более позднюю из двух генерируют заново** (`dotnet ef migrations add`), снимок
  модели руками не правят.

### Действия (путь M39.1)

| Вид | Уровень | Цель | Вызов Huntress |
| --- | --- | --- | --- |
| `incident.approve` | Standard | `alert` `incident:{id}` | `bulk_approval` (всё неодобренное) |
| `incident.reject` | Standard | то же | `bulk_rejection` с причиной, пояснением, `useful`; имя и адрес не передаются |
| `incident.step` | Standard | то же, `{remediation, completed}` | `completion`, только `manual` |
| `incident.resolve` | Standard | то же | `resolution`, когда ничего не ждёт одобрения |
| `incident.comment` | Standard, неповторяемое | то же, `{text}` ≤ 2048 | `comments` |
| `escalation.resolve` | Standard | `alert` `escalation:{id}`, `{answer}` | `resolution`; `expected`/`unauthorized` — `scope: identity`, `revoke_and_disable_identities: false` |
| `agent.isolate`, `agent.release` | Disruptive (причина) | `device` (id агента) | `POST`/`DELETE agents/{id}/isolation`, причина уходит в Huntress |
| `agent.uninstall` | Destructive | `device` | `DELETE agents/{id}` |

Попытка сначала читает запись у Huntress: что уже так — «Allerede gjort», чужая организация — отказ, 400/401/403/404/409/422 —
«Huntress avslo», 429, переживший повторы, — «позже, ничего не отправлено» (не «неопределённо»: Huntress ничего не обработал).
После отправки `HuntressReadBack` читает запись снова (на бюджете действий) в зеркала: план, комментарии, изоляцию устройства.
Оповещение инцидента это чтение закрывает, **только если инцидент закрыл человек** (`IncidentClosing`): «Lukk i Huntress»
(Huntress принял — оповещение закрывается, даже если чтение после него не удалось) или отметка последнего ручного шага, после
которой Huntress показывает отчёт закрытым. Комментарий, одобрение и возврат плана закрытие, сделанное самим Huntress, не
подтверждают: срочный инцидент ждёт человека. Ответ на эскалацию доступа шлёт `revoke_and_disable_identities: false` только
вместе с `unauthorized` — справочник Huntress разрешает поле лишь там (заглушка отвергает его иначе). Тексты действий — персональные данные
класса `integration.vendor-action-texts`, как у Atera.

## Риски и что нельзя подтвердить без рабочего аккаунта

- **Ключ пользователя.** Ключ аккаунта только читает; для действий нужен ключ пользователя Huntress с правами на изоляцию,
  удаление, исправления и эскалации — все действия в Huntress будут от его имени. Права ключа и их имена в интерфейсе Huntress
  не проверены.
- **Лимит общий для аккаунта.** 45 + 15 = все 60 запросов в минуту: если тем же аккаунтом пользуются другие интеграции
  (PSA, RMM), их запросы будут получать 429 и наоборот. Бюджеты настраиваются (`ReadRequestsPerMinute`,
  `ActionRequestsPerMinute`), сумма проверяется при старте.
- **Статусы Defender.** Справочник даёт только примеры (`Healthy`, `Up to date`, `Compliant`); публичные источники подтверждают
  `Unhealthy` и `Unmanaged`. Правило считает «не защищает» только `Unhealthy` и `Disabled`; другое слово Huntress пробела не даёт.
  Сверить на реальных агентах.
- **`firewall_status` `Enabled`** в справочнике не объяснён; изолированными считаются только `Isolated` и `Pending Isolation`.
- **«В сети».** У агента Huntress нет флага «онлайн»: Parasoll считает машину в сети, если агент выходил на связь в последние
  60 минут на момент чтения (раз в час).
- **«Устаревший агент».** API говорит, сколько агентов организации Huntress считает устаревшими, но не какие; правило
  сравнивает версии с новейшей версией платформы в аккаунте, считая срок с первого чтения новейшей. Поэтапный выпуск версии
  Huntress может дать ложный пробел до порога (14 дней).
- **404 у инцидента.** Справочник для `GET incident_reports/{id}` документирует только 403; отсутствующий отчёт CRM считает
  удалённым по 404. Если Huntress отвечает 403, чтение оповещений провалится целиком (ничего не закроет) — проверить.
- **Сущности уведомлений.** Что `id` сущности `Agent` — это id агента, справочник не говорит; если нет, оповещение уведомления
  найдёт машину по имени хоста.
- **Прямые ссылки** на страницы Huntress не подтверждены: шаблоны пусты, ссылки «Åpne i Huntress» нет. Ссылка на PDF отчёта —
  та, что дал Huntress; нужен ли вход в Huntress для её открытия — не проверено (сохранение PDF в документы клиента — M43).
- **Ответ эскалации** — только «ожидаемо/неожиданно/просто закрыть» для учётной записи; отзыв сессий и отключение учётных
  записей остаются в Huntress или Microsoft 365. Дополнительный ответ SOC через API не подтверждён.
- **Удаление агента** — удалённая деинсталляция при следующем выходе машины на связь; агент сразу исчезает из аккаунта.
- **Откат на M40** при сохранённом переходе `Confirmed` (новое значение перечисления) уронит чтение истории такого оповещения
  прежним релизом; колонки и строки M41 прежний релиз просто не читает.
- **Миграции при слиянии с M42:** см. выше; общие горячие точки — локали, регистрация в хостах, `ConnectionCatalog.cs`,
  `FreshnessLimits.cs`, `external-apis.mjs` (заметка для M42 оставлена в общей папке сессий).
- **Тип исправления `containment`** показан как «Isolering» (nb/nn) и «Containment» (en): справочник перечисляет тип без
  описания; что это всегда изоляция хоста, не проверено на реальных отчётах.
- **Устаревшее чтение и правка Atera.** Правило «чтение, начавшееся раньше действия, его не отменяет» (`ReadStartedAt`) включено
  только для чтения Huntress; чтение Atera (M38/M40) его пока не передаёт — отдельная доработка.
- Webhooks Huntress (подпись Svix) — M44; инциденты появляются в CRM в пределах 5 минут (cron задания).
