# M12 — наблюдение Atlas → назначенная задача CRM

Разработка локальная, в Parasol. Исходные Atlas/CRM, их рабочие изменения и архивные
Git-ссылки сохраняются. Публикация, развёртывание и обращения к рабочим провайдерам не выполняются.

## Рабочий сценарий

В активных наблюдениях и полной очереди клиента есть действие «Назначить работу».
Диалог заново читает точное наблюдение Atlas с личными правами сотрудника, показывает
источник и подтверждённое устройство. Сотрудник явно выбирает активного технического
исполнителя, при необходимости срок и подтверждает просмотренные данные.

Сохраняется обычная CRM Task: `Review technical observation`, пустое тело, исполнитель,
срок и приоритет High для HIGH/CRITICAL, иначе Normal. Она доступна в активностях клиента
и «Мой день». Кнопка просмотра источника делает новое личное чтение Atlas.
Подробности источника не копируются в общие Activity/Audit: у финансовых и коммерческих
ролей есть доступ к задачам, но нет технического доступа Atlas.

Завершение, переоткрытие и редактирование выполняются существующим CRM-модулем.
Для связанной задачи тип Task и клиент закреплены; слияние клиентов работает через
имеющийся обработчик слияния. Изменённый исполнитель также должен быть активным
техническим сотрудником. Завершение задачи не меняет статус наблюдения Atlas.

## Контракт и неизменность связи

- Atlas добавляет точный read-only маршрут
  `GET /clients/:id/observations/:observationId`; доступны все четыре lifecycle-состояния.
  Проверяются `context:read`, доступ к клиенту и composite key workspace/client/observation.
  Записи за пределами overview находятся без обхода страниц и без зависимости от cursor.
- CRM: `GET /api/v1/parasol/customers/{customerId}/observations/{observationId}/task-preview`,
  `POST …/task`, `GET /api/v1/parasol/activities/{activityId}/atlas-observation`.
  GET требуют ActivitiesRead **и** AtlasRead; POST дополнительно ActivitiesWrite.
  Каждое право задаётся отдельным requirement: список в `RequirePermission` означал бы OR.
- POST принимает только `assigneeId`, `dueAt`, `expectedSha256`, максимум 4 КиБ, с CSRF.
  Workspace/client, приоритет и текст задачи выводятся сервером. Неизвестные поля запрещены.
  SHA-256 связывает сотрудника, просмотренную запись, её состояние, mapping LinkId и относящееся к ней
  устройство. Смена источника требует нового просмотра; подтверждение не переиспользуется.
- Overview и точное чтение делят один бюджет 10 секунд. HTTP ограничен размером/глубиной,
  фиксированными маршрутами, без redirects/cookies/retries и upstream error text.
  DTO исключает workspace/client/connection IDs, payload и credentials; ответы no-store.

`activities.SourceTaskLinks` принадлежит Activities. Ключ — SHA-256 канонического точного
кортежа `[SourceTaskV1, Atlas, workspace, client, observation, Task]`; SQL collation не
смешивает исходные ID разного регистра. Task, receipt, аудит и outbox создаются одной
транзакцией. Первый успешный writer определяет исполнителя/срок. Повтор возвращает ту же
задачу без изменений, в том числе после завершения или отмены. После удаления/стирания
receipt сохраняется, задача отмечается недоступной и новая автоматически не создаётся.
Receipt имеет restrict FK на Task и уникальный ActivityId. Исходные технические значения
не попадают в subject/body или детали аудита.

HTTP-чтения завершаются до SQL-блокировок. Порядок: read-only Serializable guard связи
в Integration с Shared `parasol-customer-identity` → read-only lease строки клиента
в Customers → единственная долговременная запись Activities. Import/unlink используют
Exclusive тот же app lock; row locks дополнительно ограждают изменение связи обработчиком
слияния. Lease клиента удерживается до commit задачи, поэтому слияние обработает уже
существующую задачу. Здесь нет распределённой транзакции из нескольких записывающих модулей.

Сохранение задачи подтверждает локальную работу по проверенному наблюдению. Это не
acknowledgement провайдеру: Atlas может измениться после чтения, распределённого snapshot нет.
Если активность переехала при слиянии, владение receipt проверяется по её текущему клиенту.
При смене сопоставления старый источник не читается под новым клиентом.

| CRM SQL: source task + identity/workspace/queue | 77/77; после employee binding 11/11, всего 78 разных проверок |
| CRM architecture | 94/94 |

| Playwright CRM: handoff, отзыв доступа, M10/M11/workspace/reverify | 24/24, без retries; Chromium/Firefox/WebKit, обе темы |

| Root tooling / history / Gitleaks / diff | Пройдены; исходные HEAD/status/refs совпадают с началом работы |

Наборы проверяют
идемпотентность независимых SQL scope, потерянный ответ commit, rollback всех четырёх записей,
ожидание слияния на lease, права, неизвестного/неактивного исполнителя, свежий source/hash,
отзыв доступа и идентичность клиента. Браузерные проверки диалога используют управляемый
BFF-контракт; долговременная запись проверяется настоящим CRM SQL/HTTP набором.

После изменения Atlas обязателен полный strict unit/PostgreSQL/browser gate без исключений.
Нативный тестовый PostgreSQL запускается с UTC независимо от часового пояса компьютера:
исторические timestamp-without-timezone ограничения тестовых token expiry ожидают UTC.

Полный PG-прогон выявил гонку существующего worker: `nextAttemptAt` округлялся в БД до
миллисекунд, а application cutoff мог оказаться на 1 мс раньше. Событие уже было готово
по часам БД, но немедленный проход возвращал пустой результат. По умолчанию worker использует
часы БД с той же точностью; явное время сохраняется для детерминированных сценариев.
Отдельно проверяется, что повтор после transient failure сохраняет backoff на тех же часах.
Регрессии не добавляют ожиданий или повторов, маскирующих ошибку выборки.

В PG-проверке R-EVAL исправлен setup: cleanup регистрируется до запуска дочерних процессов,
порт выделяется динамически, а owner IDENTITY проверяется до подключения инструмента.
Неуспешный startup больше не оставляет тестовые процессы; отдельная регрессия это проверяет.
Исходная причина однократного IPC_CONNECT_FAILED не доказана, production R-EVAL не менялся.
Ещё один тест выбирал последнюю denial-запись только по timestamp(3). Подтверждено совпадение
времени двух разных UUID в одной миллисекунде; теперь проверяется ровно один новый audit ID
с ожидаемым eventType и пустой metadata. Проверки прав и отсутствия client audit сохранены.

Независимая проверка дополнительно обнаружила перенос подтверждения между двумя сотрудниками
с одинаковым доступом и сохранение старой родительской сводки после source denial при POST.
Employee binding и повторная проверка всей карточки закрывают эти случаи; SQL и браузерные
регрессии пройдены. Первые SQL-сбои относились к тестовым CSRF/enum/fixture-настройкам;
итоговые наборы перечислены выше. Первый browser-тест использовал fill без открытия
Combobox: теперь он выбирает реального сотрудника клавиатурой. Исключений и retries нет.

Совместный синтетический проход двух реально запущенных приложений CRM → Atlas → PostgreSQL
остаётся отдельным обязательным продуктовым воротом. Эти послойные проверки его не заменяют.
Рабочие аккаунты провайдеров, Entra consent и VPS при этом не проверяются.
