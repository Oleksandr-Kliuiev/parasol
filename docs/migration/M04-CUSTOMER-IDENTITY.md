# M04 — единая идентичность клиента

Цель: один `CustomerId` для карточки клиента в Parasol, без перенумерации существующих
записей Atlas и CRM. Реализован первый путь переноса связей через защищённые API.
Общий вход реализован в M05; пользовательский экран сопоставления добавлен в
[M08](M08-CUSTOMER-MAPPING-UI.md).

## Решение

- CRM остаётся мастером организаций. `CustomerId` — существующий UUID `Organization.Id`.
  Название и номер организации не становятся идентификатором и не создают связь автоматически.
- Atlas сохраняет свои `(workspaceId, clientId)`, разрешения и RLS. Связь с CustomerId
  хранится в уже существующей `integration.ExternalLinks` CRM: `System=Atlas`,
  `ExternalType=Client`, `EntityType=Organization`. Вторая мастер-база клиентов не создаётся.
- `ExternalId` — SHA-256 JSON-массива `[workspaceId, clientId]`, без неоднозначного склеивания
  строк. Оригинальная пара хранится в минимальном payload `ExternalRecords`; чтение проверяет
  её хеш. Имя из экспорта служит только подписью для проверки сотрудником.
- Существующие уникальные индексы обеспечивают связь один-к-одному. Один клиент CRM в этом
  выпуске связывается с одним клиентом Atlas. Внешние связи Atera/PowerOffice и других систем
  продолжают принадлежать тому же Organization.Id и не переписываются импортом.
- Связь является метаданными, а не разрешением доступа: авторизация обоих приложений
  остаётся независимой. Автоматические HTTP-вызовы между приложениями ещё не добавлены.

## Рабочий путь

1. Авторизованный сотрудник получает `GET /clients/identity-export` из DB-режима Atlas.
   Ответ содержит `schemaVersion`, `source`, `workspaceId`, `clients[{clientId,name}]`.
   В нём только клиенты с `context:read`; отсутствуют токены, secretRef, подключения и payload
   провайдеров. Частичный экспорт допустим. Ответ имеет `Cache-Control: no-store`.
2. Сотрудник выбирает CRM CustomerId для каждой переносимой записи и формирует тело:

   ```json
   {
     "snapshot": { "schemaVersion": 1, "source": "atlas", "workspaceId": "example-workspace",
       "clients": [{ "clientId": "example-client", "name": "Example (synthetic)" }] },
     "mappings": [{ "atlasClientId": "example-client", "customerId": "11111111-1111-4111-8111-111111111111" }]
   }
   ```

3. `POST /api/v1/parasol/customer-identities/import` в CRM по умолчанию делает **только
   предпросмотр**. Возвращает SHA-256, `canApply`, число невыбранных клиентов и результат каждой
   строки. Нужны существующая BFF-сессия, CSRF-заголовок и `integrations.manage`.
4. То же тело с `?dryRun=false&expectedSha256=<sha256 из предпросмотра>` применяется атомарно.
   Хеш связывает подтверждение с содержимым файла; это не подпись источника или доказательство
   просмотра человеком. Права сотрудника проверяются отдельно. Любой конфликт блокирует весь
   пакет. Данные вне выбранных строк не удаляются и не помечаются отсутствующими.
5. `GET /api/v1/parasol/customers/{customerId}/identity` возвращает CustomerId и пару Atlas
   либо `atlas: null`; требуется `customers.read`. Удалённая или скрытая после слияния организация не разрешается.
6. Ошибочную связь можно удалить существующей операцией
   `DELETE /api/v1/integrations/links/{linkId}` с `integrations.manage` и CSRF, затем подтвердить
   новый план. Для Atlas удаление и запись аудита выполняются одной транзакцией; устаревший
   linkId не может удалить новую связь.

Клиентский JSON ограничен 1000 строками, ID длиной 1–128 ASCII-символов (`A–Z`, `a–z`, цифры,
`._:-`) и именем до 256 символов. Неизвестные поля JSON отклоняются. Унаследованные записи
за этими границами требуют отдельной проверки, а не неявного усечения.

## Надёжность и эксплуатация

Импорт использует существующие таблицы CRM, SERIALIZABLE-транзакцию, транзакционную блокировку
SQL Server и уникальные индексы. Повтор того же плана возвращает `ALREADY_LINKED` и не дублирует
аудит. Применение заново проверяет существование организаций и конфликтующие связи.
`ParasolIdentityLinked`/`ParasolIdentityUnlinked` фиксируют сотрудника, ссылку и хеш плана;
имена и исходные файлы в детали этих событий не копируются. Повреждённый payload связи
возвращает `PARASOL_IDENTITY_INCONSISTENT`, а не чужую идентичность.

Слияния организаций продолжают использовать штатный CRM merge/undo и его асинхронный
перенос ExternalLinks. При конфликте двух Atlas-связей исходная связь остаётся для ручной
проверки. Перенаправление старых CustomerId после merge — отдельная задача перед автоматическими
межсервисными вызовами; этот выпуск не обещает таких перенаправлений.

Новых production-зависимостей, Azure API, облачной инфраструктуры и фоновых интеграций нет.
Проверка выполняется на синтетических данных в отдельных локальных PostgreSQL/SQL Server.
SQL Server остаётся текущим хранилищем CRM; M04 не является переносом CRM на PostgreSQL.
Целевая площадка — **Hostinger VPS**. Замена оставшихся Azure-зависимостей CRM, упаковка,
резервное копирование/восстановление и сам deployment — следующие этапы.

Общий пример контракта: `contracts/customer-identity/atlas-export.v1.example.json`.
Atlas PostgreSQL HTTP-тест сравнивает с ним настоящий ответ API; CRM читает тот же файл
в unit- и SQL integration-тестах. Проверяются права, CSRF, предпросмотр без записей,
точное подтверждение, конфликты, частичный экспорт, идемпотентность, конкурентное применение,
откат после SQL-ошибки, целостность ссылки и аудируемое удаление.
