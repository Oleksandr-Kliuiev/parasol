# M22 — задача, сохранённая заявка и собственные часы

Локальная разработка без публикации, развёртывания и рабочих аккаунтов провайдеров.
Цель этапа — пройти из наблюдения Atlas через существующую CRM Task к сохранённой
Service-заявке и явно записанному времени сотрудника, без ручного копирования номера
и без автоматического начисления часов.

## Поведение сотрудника

В строке Task есть действие «Сервисная заявка». Сотрудник с правами Activities и Service
может выбрать сохранённую заявку этого клиента, заменить связь или явно убрать её.
Одна заявка допускает несколько задач. Список загружается по запросу, продолжение страниц
явное; поиск обозначен как поиск по уже загруженным записям. Статус и дата импорта
показывают сохранённые сведения, а не текущий ответ Atera.

Из связанной задачи открывается существующая форма времени: клиент и точная заявка уже
выбраны, часы и описание пусты. Сотрудник сам указывает фактическую работу. Автор времени
не подменяется исполнителем задачи; срок задачи не становится датой работы. Сохранение
времени не завершает задачу и не меняет наблюдение Atlas. На телефоне форма работает
с клавиатуры, сохраняет фокус при смене темы и возвращает его после закрытия.

Привязка и отвязка используют показанный ETag. При чужом изменении требуется обновить
и пересмотреть выбор; старый ответ не перезаписывает новую версию. Удалённая или больше
не подтверждённая заявка недоступна для новых часов, но её старую связь можно убрать.
Смена клиента, сотрудника или задачи отменяет чтения и исключает поздние уведомления
и изменения другой формы. Ручной ввод номера остаётся отдельным явным вариантом,
очищающим внутреннюю проверенную связь и происхождение.

## Источник и согласованность

- Service хранит owner external customer ID, точный LinkId и ImportedAt. Старые строки
  без подтверждённого owner не получают его задним числом и не становятся подходящими
  только по совпадению номера. Новое поступление Atera записывает подтверждённый owner;
  owner-only изменение учитывается, повтор неизменённой записи не считается изменением.
- Каноническая связь — ровно `Organization / atera / Customer`, положительное десятичное
  значение без числовых алиасов. Коллизии и неоднозначность закрывают доступ. Cursor
  списка связан с клиентом, LinkId и внешним customer ID.
- Контракты `ITicketWorkApi`, `IOrganizationWorkLease` и `ITaskWorkApi` соединяют модули,
  не раскрывая чужие DbContext. SQL leases удерживают customer → integration namespace /
  link → saved ticket → Task → Time до завершения записи. Обычные SQL UPDATE/DELETE и
  конфликтующая вставка алиаса также блокируются. Callback не переигрывается автоматически.
- Связь хранится как nullable Activity.LinkedTicketId; время — существующий TicketId
  плюс nullable SourceActivityId. Межмодульных FK нет; миграции только расширяют схему.
  Сервер выбирает сохранённые номер и название, не доверяя присланным подменам.
- Изменение связи оставляет аудит и rowversion, но не порождает ActivityLogged:
  техническая привязка не является контактом с клиентом и не обновляет stale-deal clock.
  Статус, исполнитель, срок, текст и результат Task сохраняются.
- Стабильный clientRequestId формы создаёт постоянную TimeEntryCreateReceipt в одной
  транзакции с часами и аудитом. Точный повтор возвращает ту же запись; конфликт намерений
  или чужой автор получают 409. После потери ответа повтор принимает уже сохранённую
  историю даже при последующей отвязке задачи. Удалённая запись не воскрешается.
  Runtime-роли Web/Worker имеют INSERT/SELECT, но не UPDATE/DELETE квитанций.
- Ручные часы, округляющиеся к нулю, отклоняются до создания или изменения полей.
  Существующее округление двух знаков ToEven сохранено: 0.005 отклоняется, 0.006 → 0.01.
  Импорт часов не переопределяется этим правилом ручной формы.

## Проверка

[Свидетельство M22](../testing/evidence/task-ticket-time-M22-2026-10-17.json): CRM unit
911/911, architecture 94/94, затронутые SQL integration 63/63; полный frontend 559/559
в 63 файлах; ESLint, app/E2E/composition TypeScript, production build и budget 291.7/300 KB.
CRM browser 67/67 в трёх движках и полный source-build composition 9/9 прошли без skips,
retries, flaky или исключений; все временные ресурсы очищены. Компактный
[совместный отчёт](../testing/evidence/composition-current-2026-10-17.json) содержит
554 Atlas requests, 0 mutating requests и точные SQL/privacy counts.
387 web и 811 backend/build входов совпадают с проверенными SHA256.

Atlas не менялся: все 1421 входов и inventory совпадают с отдельным строгим прогоном
711 unit / 789 PostgreSQL / 90 browser. Этот долгий набор не запускался повторно в M22.
Проверки исходных HEAD/status/refs, import history, diff-check и redacted secret scan
выполняются перед локальным checkpoint.

Первый запуск упал на QUOTED_IDENTIFIER синтетического seed; исправлен только fixture.
Два полных 8/9 и одиночная диагностика выявили сканирование затемнённой, недоступной
фоновой кнопки при modal Axe: фокус оставался в textarea, ancestor имел aria-hidden.
Теперь все правила проверяют активный modal, а всю страницу — до и после него; дополнительно
проверяются фокус при смене темы, Escape и возврат фокуса. Production ARIA/inert не менялись,
правила не отключались. Первый полный проход настоящей цепочки дал browser 9/9, но был
отклонён durable gate: привязка заявки порождала третье ActivityLogged. Исправлены домен
и SQL/unit assertions: аудит остаётся, событие контакта не возникает. Новый полный запуск
подтверждает ровно два события — создание и завершение Task. Отдельный последующий
прогон обнаружил гонку theme-render: сканирование начало замер до применения media
события React, при этом диагностика уже показывала конечные правильные цвета. Теперь
перед Axe явно проверяются отрисованные dark surface и foreground кнопки Cancel.
Правила контраста, timeout и production styles не менялись. Предыдущие неуспешные
результаты, включая исправленные compile-only ошибки, сохранены отдельно.

Проверки включают реальные SQL leases и ограничения runtime-ролей, смену owner/link,
чужой клиент, удаление/повторный импорт заявки, конкурирующие If-Match, одинаковые и
конфликтующие повторы времени, потерянное подтверждение commit, отмену и старые UI-ответы.
Совместный браузерный сценарий использует именно Task, созданную из наблюдения Atlas
предыдущим сценарием, а не отдельную имитацию задачи. Проверяются собственные 0.75 часа
администратора при другом исполнителе Task, одна запись/квитанция/аудит и сохранённый срок.

## Границы и следующий этап

Это сохранённые Service-данные; рабочая совместимость Atera и остальных провайдеров
остаётся непроверенной. Шифрованное резервирование и Hostinger имеют отдельные ворота.
Новых production dependencies и Azure-инфраструктуры нет. Исходные репозитории и
пользовательские изменения не входят в этот этап.

M23 должен устранить существующую гонку закрытия периода с записью времени. Сейчас
проверяется отказ для уже закрытого периода; это не доказывает атомарность конкурентного
закрытия. Требуется единый протокол допуска по месяцам для create/update/adjust/delete,
approve/withdraw, close/reopen, импорта, финализации invoice basis и technician mapping,
с каноническим порядком старого/нового месяцев и владением до commit. Финансовый пилот
до этого исправления не заявляется готовым. Также остаются отдельные границы atomicity
HourBank и асинхронного export → invoiced; один period lock их сам по себе не устраняет.
