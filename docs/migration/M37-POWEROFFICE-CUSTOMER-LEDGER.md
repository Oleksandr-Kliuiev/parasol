# M37 — подтверждённые платежи и клиентские операции

Ветка `feat/m37-customer-ledger`, база `7662751` — исторические счета со строками.
Работа локальная: синтетические записи, WireMock и отдельный SQL-контейнер.
Рабочий PowerOffice не подключался; публикации и развёртывания нет. Новых
production dependencies нет. Исходные репозитории и primary checkout сохраняются.

## Источник и смысл платежа

Используется официальный v2 `GET /Customerledger/Statement`:

- [OpenAPI Customer Ledger](https://swagger.poweroffice.net/openapispecs/customerledger.json).
- [Customer ledger workflow](https://developer.poweroffice.net/endpoints/reporting/customer-ledger).
- [Retrieving invoice payments](https://developer.poweroffice.net/workflow/usecase/reporting/retrieving-invoice-payments).

Контракт проверен 18.10.2026. Идентичность операции — `(System, Id)`, где Id —
числовой ID строки реестра. VoucherId — UUID бухгалтерского документа; для
исходящего счёта он совпадает с UUID OutgoingInvoice. Номер счёта не заменяет UUID.

Платёж подтверждает проведённая операция с типом IncomingOcrGiro,
IncomingBankRemittance или BankJournal. Это подтверждение в учёте PowerOffice,
без обращения к банку. Положительные/отрицательные суммы сохраняются, поэтому
возврат не превращается в поступление. IsWriteOff=true имеет приоритет и даёт
WriteOff. OutgoingInvoice, OutgoingCreditNote и ReversalVoucher различаются;
ManualJournal, неизвестный или отсутствующий тип остаются Other. Уменьшение
остатка и отрицательная сумма сами по себе не доказывают платёж.

Сохраняются исходные даты проводки/документа/срока, VoucherNo, исходный CustomerId,
InvoiceNo, MatchId, IsWriteOff, Created/LastChanged, подписанные Amount/Balance
в валюте учёта клиента и отдельный CurrencyAmount/CurrencyCode. Nullable currency
не заменяется выдуманным NOK. Нормализованный SourceJson сохраняет дополнительные
поля (например, KID, измерения и источник платежа); это не архив байтов PDF.
Суммы в JSON не ограничиваются decimal(18,2) и не пересчитываются.

## Получение и возобновление

Для небольшой базы выбран полный постраничный проход Statement. Запрос задаёт
fromDate=0001-01-01, toDate=9999-12-31, OrderBy=Id asc. Таким образом чтение не
ограничивается текущим месяцем и включает будущие даты проводки. В схеме API эти
параметры не имеют более узких границ; совместимость конкретного аккаунта с
границами дат ещё предстоит проверить на разрешённом тестовом аккаунте.

Нет фильтров onlyBalancesLessThanAmount, voucherTypes, onlyCreatedByCurrentIntegration
или lastChanged: старые ручные match/unmatch и несопоставленные поступления должны
попадать в полный проход. Для 40 клиентов это проще контролировать, чем поддерживать
неполный изменяемый граф зачётов по разрозненным incremental-страницам.

- Сначала читаются все страницы. JSON null, 403/503, неверное обязательное поле
  или конфликт копий одного Id останавливают проход без публикации нового cursor.
  Полностью одинаковые копии дедуплицируются.
- После чтения каждый исходный CustomerId сохраняется отдельной атомарной
  транзакцией Billing. Сохранение состояния scan и всех его операций откатывается
  вместе при ошибке. Завершённые клиенты переживают сбой между транзакциями.
- Внешние IDs и версии идемпотентны. Новый scope повторяет полный проход; номер
  изменяемой страницы не используется как надёжная позиция продолжения.
- Stream `customer-ledger-snapshot-v1` публикует JSON checkpoint завершённого
  прохода с scanId, окном чтения и количеством записей. Он не используется как
  incremental-фильтр. Существующие курсоры/задания M37 сохраняются.
- Верхние границы: 100 000 уникальных строк, 64 MiB нормализованного исходного JSON
  за проход, 256 KiB сохранённого снимка одной строки. Превышение — явная ошибка,
  усечения и ложного успешного checkpoint нет.

Это не гарантированный upstream-снимок на одну наносекунду: API не выдаёт snapshot
токен. Новая операция/сопоставление во время пагинации может потребовать следующего
полного прохода; противоречащие копии отклоняются. Отчётность на дату, полная
бухгалтерская сверка и банковская проверка находятся за пределами этого среза.

## Сохранность и конкурентность

Добавлены три таблицы Billing:

- CustomerLedgerEntries: текущая сохранённая версия и уникальный внешний ID.
- CustomerLedgerVersions: каждая принятая изменившаяся версия SourceJson с временем
  источника и наблюдения. Повтор той же версии не добавляет дубликат.
- CustomerLedgerSnapshots: последний завершённый scan каждого исходного клиента,
  его CRM-связь и время чтения/сохранения.

Проведённые суммы, документ, даты и уже известный исходный клиент не переписываются.
Отсутствующий CustomerId может быть дозаполнен источником у того же ID операции;
это обновляет одну запись и добавляет версию, сохраняя первоначальный orphan-снимок. Старое
время источника и противоречащие match-состояния с одинаковым временем отвергаются.
SourceJson не копируется в общий audit payload: история хранится в защищённых
Billing-версиях. Runtime SQL не может удалять записи/версии/scan-состояния и не
может изменять прежние версии. Откат миграции при наличии ledger-данных запрещён.
Существующие счета, движения остатка, строки и исходные URL не меняются миграцией.

Задания PowerOffice используют прежний system-scoped exclusive runner. Billing
использует тот же application lock, что и импорт счетов. Чтение списка/связей
проходит в serializable-транзакции; писатель сначала меняет строку scan-состояния,
затем операции. Читатель не смешивает scanId и операции двух коммитов.

## Клиенты, счета и граф сопоставлений

Связь CustomerId → CRM Organization читается после provider HTTP под существующим
lease ExternalLinks, с lease пригодности организации. Имена, CustomerAccountNo,
InvoiceNo и похожие суммы не создают клиентскую связь. Записи без связи и даже
без CustomerId сохраняются. Следующий полный проход применяет link/unlink/relink;
это не мгновенная реакция на ручную смену связи до синхронизации.

Связи со счетами вычисляются из сохранённых данных при чтении:

1. Ledger-строка типа Invoice/CreditNote должна иметь VoucherId, равный ExternalId
   импортированного счёта того же типа, System и исходного CustomerId.
2. Другие текущие строки этого клиента с тем же ненулевым MatchId относятся к
   группе сопоставления. MatchId никогда не пересекает клиентскую границу.
3. CRM-связь счёта должна совпадать с текущей сохранённой CRM-связью ledger-клиента.
   При рассогласовании после relink связь временно не показывается до обновления
   импорта счетов; операция остаётся в списке своего ledger-клиента.

Один платёж может иметь несколько связанных счетов и наоборот. Отношения помечены
DirectVoucher/MatchGroup; суммы распределения между счетами не изобретаются.
Непривязанный платёж с тем же InvoiceNo не считается оплатой этого счёта.
Позднее появление импортированного счёта автоматически создаёт доступную связь
без нового provider HTTP. Ledger-операции не создают сами счета/начисления.

При unmatch текущая связь исчезает, прежняя версия остаётся. Строка, отсутствующая
в последнем полном проходе, также сохраняется: PresentInLatestScan=false,
LastSeenAt — прежнее время, Invoices — пустой список. Её прежний Source.MatchId
является историческим значением и не участвует в текущих связях. Физического
удаления финансовых записей нет.

Операции существуют отдельно от старых InvoicePayment/InvoiceMovementKind.
Импорт не выводит новый платёж из BalanceDecrease, не добавляет его вторично в
движения остатка и не переписывает Invoice.Outstanding. Остаток счёта обновляет
собственный invoice sync; времена двух чтений могут отличаться.

## Чтение и включение

`GET /api/v1/billing/customer-ledger` принимает organizationId, invoiceId, offset
и limit (1–200, по умолчанию 50). Возвращает сохранённые операции, тип, источник,
признак присутствия в последнем scan и список связанных счетов. Нужны одновременно
billing.read и finance.read, включая доступ к исходному JSON. Provider HTTP при
просмотре не выполняется. Отдельный экран операций в этот срез не входит.

CustomerLedgerSyncEnabled по умолчанию false. Worker регистрирует задание
poweroffice-customer-ledger только при включении; стандартный cron — `35 * * * *`
по Oslo. Само задание также проверяет включение и обычную настроенность PowerOffice.
Тесты включают флаг только с localhost WireMock и WriteEnabled=false. Изменений
рабочей конфигурации/секретов нет. Новый stream не включён в прежний M15 агрегат
готовности; его итог и ошибки записываются в обычные SyncRuns отдельно.

Модель сохраняет прежнее ограничение одного настроенного PowerOffice-аккаунта:
переключение компании или объединение нескольких источников требует отдельного
namespace. PDF/вложения, supplier/general ledger, payroll и полная замена
PowerOffice остаются отдельными этапами общего плана M37.

затронутых SQL/HTTP**, включая **30 новых unit** и **29 новых SQL-сценариев**.

включает заполнение CustomerId у orphan-записи и 2201 операцию с ограниченными
