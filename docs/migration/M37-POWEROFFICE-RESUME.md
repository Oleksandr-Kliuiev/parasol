# M37 — возобновляемый импорт PowerOffice, первый срез

Локальная ветка: `feat/m37-poweroffice-resume`, база `63b595a` (M36).
Текущий статус проверок см. в разделе «Результат» ниже.

## Решение владельца

Требуется перенос всех данных и обновлений. Возможен полный переход с PowerOffice
на CRM; окончательное решение не принято. Существующие функции, интеграции и
история проекта сохраняются. Этот срез улучшает надёжность существующей загрузки;
полный объём переноса описан в [плане](M37-POWEROFFICE-REPLICA-PLAN.md).

Работа локальная и использует синтетические данные. Рабочий аккаунт, credentials,
Azure и развёртывание не задействованы. Новых production dependencies нет.
Первичный checkout с незакоммиченными планом/картой и исходные репозитории не меняются.

## Воспроизведённый сбой

Клиент и контакт сохранялись в `ExternalRecords` раньше завершения сопоставления
и записи реквизитов. При остановке между этими шагами курсор оставался прежним,
но повторная загрузка пропускала неизменившийся payload. Три теста на SQL до
исправления завершились ошибками: связь клиента, реквизиты и связь контакта
оставались незавершёнными. Перезапуск приложения сам по себе это не исправлял.

Есть и отдельная граница: модуль Customers/Catalog успевает создать сущность,
а сохранение `ExternalLink` падает. Клиент без оргномера или контакт без e-mail
не имеют устойчивого естественного ключа для повторного создания.

## Изменения

### Загрузка и checkpoint

- Клиенты повторно проходят сопоставление и применение реквизитов даже при том же
  payload. Сами модульные записи остаются идемпотентными.
- Контакты повторно проходят сопоставление; e-mail берётся из сохранённой записи,
  в которой действует privacy redaction. Исходный e-mail подавленного лица не
  возвращается в процесс сопоставления.
- Курсор остаётся checkpoint завершённого прохода. При ошибке страницы или
  последующей обработки незавершённый диапазон перечитывается с прежней позиции
  и существующим overlap. Это безопасное повторное чтение, а не сохранение номера
  изменяемой страницы как надёжной позиции.
- JSON `null` вместо массива больше не означает конец данных. Ошибка страницы
  не должна позволять публиковать новый курсор. 204/пустой массив остаются
  предусмотренными текущим клиентом признаками окончания.

### Исключение параллельных писателей

`RunExclusiveAsync` сериализует задания клиентов, контактов, товаров и счетов
PowerOffice по SQL application lock одного integration system. Ручной запуск и
расписание используют тот же путь; другой процесс Worker получает тот же lock.
Существующие задания остальных интеграций сохраняют свои точки запуска.

Lock принадлежит сессии: HTTP не держит открытую транзакцию. Для этого соединения
отключены pool и idle reconnect; внешняя EF execution strategy охватывает целую
попытку, чтобы отдельный SQL statement не повторился на новой сессии без lock.
Каждая EF-команда IntegrationDbContext во время попытки проверяет фактический
application lock непосредственно в SQL batch. Переоткрытое соединение не может
сохранить курсор под авторитетом предыдущей сессии. Физическое закрытие освобождает
lock при успехе, исключении и отмене; отдельные SQL-тесты проверяют также KILL.

### Создание карточек без дублей

Сохранённый `ExternalRecord.Id` используется как устойчивый ключ создания новой
сущности Customers/Catalog. Он создаётся сервером и уникален для конкретной внешней
записи в текущей БД. Номер клиента, название, артикул и e-mail не заменяют этот ключ.
При повторе модуль возвращает ранее созданную сущность и не повторяет Create/event.
PK защищает и два конкурентных запроса; проигравший запрос можно повторить.

`ExternalLink` сохраняет существующее назначение и ограничения. При совпадении с
ранее существующей карточкой сохраняются прежние правила сопоставления. Восстановление
своей созданной карточки выполняется до эвристики похожих названий в bulk import.
Удалённый/обезличенный объект не создаётся заново. Изменённая принадлежность контакта
требует разбора; повтор не восстанавливает её автоматически.

Предпросмотр вызывает тот же модульный путь решения с `PreviewOnly`: без записи
сущностей, связей, affiliations и событий. Он различает создание и восстановление.
Схема БД не меняется. Этот протокол защищает создания после M37; старые бесхозные
карточки без сохранённого внешнего ключа требуют отдельной сверки.

## Проверки

Новые SQL/HTTP сценарии:

- Остановка после payload до сопоставления клиента/контакта и до применения
  реквизитов; новый scope Worker, неизменный payload и два повторных запуска.
- HTTP 503 и JSON null на следующей странице: старый курсор, сохранённая первая
  страница и повтор без дублирования, включая одинаковые записи/timestamps.
- Один system, разные streams и разные SQL sessions: второй писатель не входит
  в работу; другой system доступен. Ошибка/отмена освобождают lock.
- KILL сессии и явное переоткрытие соединения: запрещена публикация курсора без lock.
- Клиент без оргномера, контакт без e-mail и товар: реальная запись сущности,
  ошибка перед link, предпросмотр восстановления и повтор без второй карточки.
- Конкурентный импорт тех же трёх типов; удаление/обезличивание тестовой карточки
  между сбоями не вызывает её повторного создания. Новый preview не создаёт цель.

Проверки работают с настоящим SQL Server под существующим runtime role, HTTP —
только локальные WireMock-сервисы. Тестовая инъекция ошибки link не заменяет SQL.
Изолированная копия fixture фиксирует digest SQL image и loopback binding; продуктовый
fixture и миграции сохраняются. Старые M36 отчёты не являются проверкой этого backend.

## Границы выпуска

Это основа надёжной загрузки существующих типов, не законченный перенос «всего».
Полная финансовая история, строки счетов, прямая связь исторических счетов по
CustomerId, ledger, документы, остальные категории и account binding ещё требуют
реализации. Пяти минут overlap недостаточно для доказательства полного покрытия
произвольных запоздалых изменений или перестановок страниц источника: полная
сверка и политика каждого endpoint остаются в плане.

Источник в текущей модели определяется integration system в одной CRM БД. Смена
рабочей компании/аккаунта без явной миграции связей не разрешается этим срезом.
Гарантия устойчивого создания относится к сохранённому ExternalRecord key.
Изменение исходных данных во время сопоставления с ранее существующей карточкой
и история таких решений требуют отдельного контракта; текущие сценарии восстановления
используют ту же версию payload.
SQL guard защищает IntegrationDbContext/checkpoint; отдельные модульные записи
имеют свои транзакции и устойчивые ключи, общего снимка всех модулей пока нет.
Копия не становится бухгалтерской системой автоматически. Решение о полном
переходе потребует отдельного покрытия и проверки функций учёта.

Существующие outbound возможности сохранены. Для этих тестов нового чтения
используется `WriteEnabled=false`; глобальный запрет уже накопленных outbound
заданий в отдельном режиме полной копии ещё не заявляется как реализованный.
Регрессионные тесты прежних исходящих возможностей используют локальные заглушки.

## Результат

18 октября 2026: **970/970 unit**, **94/94 architecture**, **63/63 затронутых SQL/HTTP**,
включая **21 новый сценарий**, без пропусков и исключений из набора. Обычная сборка
integration project и сборка изолированного SQL-кандидата проходят с нулём предупреждений
и ошибок. Все 862 исходных входа SQL-кандидата сверены с текущими файлами.

Unit/architecture проверены на окончательном production code. После них изменилась
только collection-аннотация integration-теста; финальные обычная сборка и SQL-прогон
включают её. Новые фикстуры общего хранилища выполняются отдельно от чужих fixed-cursor
сценариев; внутри тестов сохранены реальные конкурентные вызовы.

Первый объединённый прогон дал 38/40: исправлены пересечение фикстур общего курсора
и чтение smallint @@SPID как int. Исходные три воспроизведения и все промежуточные
отчёты сохранены; ожидания, дедлайны и оригинальные проверки не ослаблялись.
Предыдущий расширенный прогон 63/63 дополнен финальной проверкой Imported provenance.

Все четыре SQL-контейнера остановлены и удалены с их собственными томами;
их private state удалён. Полный frontend/browser/Atlas и backup/restore здесь не
перезапускались: UI, Atlas, схема и протокол файлов не менялись. Эти результаты
не заменяют проверку полного исторического импорта или рабочего аккаунта.
