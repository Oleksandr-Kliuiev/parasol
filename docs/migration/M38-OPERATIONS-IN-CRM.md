# M38 — Atlas выведен из Parasol, в CRM появляется «Drift»

Статус: в работе, ветка `feat/retire-atlas` от `feat/crm-hearth-design`. Последний опубликованный коммит до
удаления — `73c0158`. Публикации, развёртывания и записи в рабочие аккаунты поставщиков нет.

Это единственный документ Parasol, кроме записей об импорте (`sources.json`, [IMPORT.md](IMPORT.md),
[M01–M03](M01-M03.md)), который называет удалённый сервис. Остальные документы говорят «прежний сервис
интеграций» и ссылаются сюда.

## Почему

Atlas был отдельным приложением (Node/TypeScript, Prisma, PostgreSQL 17, свой операторский интерфейс), которое
только читало данные: инциденты и агенты Huntress, снимки заявок и агентов Atera, каталог Microsoft 365. Оповещения
Atera он не читал, в Atera и Huntress ничего не писал, его действия существовали только как макет, а на целевом VPS
опрос был выключен. У CRM уже была своя, более полная интеграция с Atera: клиенты, контакты, заявки, часы, агенты,
оповещения, создание заявок. Поэтому устройства показывались дважды, а связь с Atera была заведена двумя путями.

Сотрудники путались в слове: в интерфейсе CRM около 95 строк на каждом языке требовали понимать отдельную систему
(«личный доступ Atlas», «ID клиента Atlas», «экспорт Atlas JSON», «реестр Atlas»). Цель владельца — сотрудники не
заходят в консоли Atera, Huntress и CloudAlly, ежедневная работа идёт в Parasoll. Ничего не развёрнуто и рабочих
данных нет, поэтому отказаться от сервиса сейчас дешевле всего.

Решения владельца:

1. Atlas убирается полностью; Atera, Huntress и CloudAlly подключаются к CRM напрямую. Код остаётся в истории Git,
   история не переписывается.
2. Oleksandr, Asbjørn и Bjarte имеют полный доступ ко всем функциям; роли не настраиваются.
3. Из CRM выполняется всё, что позволяют API поставщиков; каждое действие подтверждается и пишется в журнал,
   разрушительные — с усиленным подтверждением.

Принято по лучшей практике (обратимо): Atera остаётся системой заявок (почта и портал клиентов), CRM — полный
рабочий интерфейс к ним; названия в интерфейсе — по смыслу, имя поставщика только как метка источника; обзор
Microsoft 365 (счётчики каталога и входов) уходит вместе с сервисом, лицензии остаются через Partner Center;
Ask Atlas, слой решений OpenAI, макеты действий и PowerOffice внутри сервиса не переносятся — у CRM есть настоящая
интеграция PowerOffice, а ИИ-помощник остаётся решением владельца ([UX-2026 §7.5](../ux/UX-2026.md#7-нужны-решения-владельца)).

## Что видит сотрудник после M38

- Слова Atlas нет нигде; нет «личного доступа», «ID клиента», импорта JSON и отдельного экрана сопоставления.
- Вкладка клиента **«Drift»** (EN «Operations») вместо «Service»; старые ссылки `?tab=service` работают. Порядок:
  сводка → оповещения → устройства (у каждого число открытых оповещений) → заявки Atera → запросы заявок. Во
  «Обзоре» нет прежнего технического блока; в «Клиент в двух словах» — число открытых оповещений со ссылкой на «Drift».
- **«Arbeid → Driftsvarsler»** (`/alerts`) вместо очереди наблюдений `/observations`: открытые оповещения всех клиентов,
  фильтры, «Назначить» → задача CRM. Тема задачи — заголовок оповещения, её можно изменить; у задачи кнопка «Источник».
- **«Мой день»:** панель пяти самых срочных открытых оповещений всех клиентов (сначала Critical, затем самые новые; до
  28.10.2026 — самые старые, см. [M45, «После M45»](M45-ALERT-BULK-ACTIONS.md#после-m45-свежее-сверху-28102026))
  со ссылкой `/alerts?alert=<id>`, свежестью копии Atera («прочитано в …», «чтение не завершилось», «ещё не
  прочитано») и числом открытых; плитка «Kritiske driftsvarsler» берёт то же чтение, переход по разделу ведёт к панели.
  Раскладку (работа, руководство или финансы; по умолчанию работа) каждый выбирает сам переключателем «Показать
  первым»: при полном доступе выбор по правам поставил бы всем биллинг первым.
- **`/connections`:** каждая интеграция экземпляра (Atera, PowerOffice, Partner Center, Microsoft Graph,
  Brønnøysund) — включена или нет, каждое регулярное задание с последним полным чтением, возрастом, пределом и
  последним упавшим прогоном, неотправленные изменения и пульс Worker. Зелёная строка — только когда все включённые
  задания свежие, ничего не на паузе и не ждёт отправки, а Worker отвечает; иначе пробелы перечислены в той же
  рамке. «Личной конфигурации» больше нет; страница ничего не вызывает у поставщиков и секретов не показывает.
- **Доступ:** экраны «Нет доступа» и отказы говорят о доступе и группе «Parasoll – full tilgang», а не о роли;
  в карточке учётной записи — адрес e-mail вместо названия роли.
- Временно нет инцидентов Huntress (вернутся в M41) и обзора Microsoft 365 (снят). Ничего не развёрнуто, поэтому
  никто из сотрудников не затронут.

Связи задач с прежней системой, созданные до M38, есть только в синтетических базах. Миграции с удалением строк нет:
такие связи молчат — кнопки «Источник» у них нет, API отвечает 404.

## Модель доступа

Подробно — [ADR-030](../../apps/crm/docs/adr/ADR-030-full-access-group.md), настройка —
[runbook 01 §7](../../apps/crm/docs/runbooks/01-first-deployment.md#7-домен-и-вход) и
[runbook 12 §1а](../../apps/crm/docs/runbooks/12-roles-and-sessions.md#1а-полный-доступ-через-одну-группу).

- Одна группа безопасности Entra **«Parasoll – full tilgang»** назначена роли приложения `Crm.Admin`; эта роль даёт
  все права CRM (`Permissions.cs`, набор `Everything`). Три сотрудника — прямые члены группы: вложенные группы ролей
  не дают (ADR-019).
- Назначение роли группе требует Microsoft Entra ID P1. Без него роль `Crm.Admin` назначается трём пользователям
  напрямую; синхронизация ролей читает и прямые назначения.
- Проверки прав в коде остаются защитой: вход только своих сотрудников (`appRoleAssignmentRequired`), отзыв доступа
  за ~2,5 минуты (`entra-role-sync` каждые 2 минуты), повторный вход перед опасным действием (`AUTH_REVERIFY_REQUIRED`).
  Пользователь ролей не видит и не настраивает: отказы говорят о группе, а не о роли. Вход разработчика первым
  предлагает `Crm.Admin` («Employee (full access)»); узкие роли остаются ниже для проверки прав.
- Правило «две подписи двух разных людей» для крупного биллинга (BR-BIL-04) сохраняется: при полном доступе подписать
  может любой второй сотрудник.
- Задачи из источника требуют `activities.read` и `service.read`, исполнитель — `activities.write` и `service.read`.

## Оповещения Atera: жизненный цикл (C4)

Раньше каждое чтение удаляло открытые оповещения клиента и вставляло их заново. Теперь (миграция
`20261021102012_AlertLifecycle`, `apps/crm/src/Modules/Service`):

- `service.Alerts` хранит оповещение с постоянным id: `State` Open / Acknowledged / Resolved, `Kind` Monitoring
  (Atera) / Security (Huntress) / Backup (CloudAlly), внешний id клиента, устройство, ссылка, `LastSeenAt`,
  `ResolvedAt`; уникальность — `System` + `ExternalId`.
- `IServiceApi.ApplyAlertSnapshotAsync` записывает перечисленные оповещения как открытые (закрытое ранее открывается
  снова, отметка Acknowledged сохраняется). Хранимое Open или Acknowledged закрывается (Resolved) только тогда, когда
  **полное** чтение его больше не перечисляет. Оповещения клиентов без связи с организацией не трогаются: открытое у
  Atera, но не сопоставленное, остаётся как есть. Неполное или упавшее чтение ничего не меняет.
- Чтение Atera (`atera-alerts`, `5,35 * * * *`) падает целиком при проблеме страницы или оповещении без id; соседняя
  предыдущая страница перечитывается, чтобы сдвиг списка ничего не потерял. Одновременные записи одного источника
  ждут друг друга (app lock на транзакцию).
- Устройство ставится, только если ровно одно текущее устройство того же клиента и источника носит это имя (без учёта
  регистра); два устройства с одним именем или ни одного — оповещение без устройства, а не с догадкой.
- Ссылка в Atera берётся только из `Integrations:Atera:AlertUrlTemplate` (по умолчанию пусто): адрес страницы
  оповещения не подтверждён, а угаданный вёл бы не туда.
- Чтение для интерфейса: `GET /api/v1/service/alerts?organizationId&state&severity&deviceId&q&cursor&limit` →
  `{items, nextCursor, totalCount, critical, warning}` (открытые по умолчанию, новые первыми, keyset-курсор, 25 по
  умолчанию и до 100; итоги считаются до пагинации) и `GET /api/v1/service/alerts/urgent?limit=5` →
  `{items, totalCount, critical, warning, reads: [{system, startedAt, complete}]}` (самые важные, среди них самые
  старые; `reads` говорит, насколько свежий список). Оба требуют `service.read`.
- Макет: `apps/crm/tools/dev-mocks/atera.mjs` с маршрутами только для тестов (`/_mock/atera/customers`, `agents`,
  `alerts`, `DELETE /_mock/atera/alerts/{id}`), описание — в README макетов.

Закрыть оповещение в Atera, скрыть его у себя до даты и найти пробелы покрытия — этап M40. Решённые оповещения
хранятся как история; их чистка — тоже M40.

## Целевая архитектура

Одно приложение — CRM (.NET, SQL Server, Hangfire). Нет PostgreSQL, Node-сервиса, личных токенов и импорта JSON.
Ключи поставщиков лежат только в закрытой конфигурации Worker (`deploy/hostinger/tools/configure.py` пишет
`worker.json`); Web получает только переключатели.

| Где | Что | Образец в коде |
| --- | --- | --- |
| `Integrations/Crm.Integrations.Atera` (расширить) | вход по Bearer JWT вместо `X-API-KEY`, комментарии и изменение заявок, отправка часов, закрытие и удаление оповещений, инвентарь и патчи, `AppViewUrl`; `AteraClient.cs` разбить на partial-файлы | сам модуль, `AteraOptions.cs` (Enabled, WriteEnabled, WriteAllowedCustomerIds, cron) |
| `Integrations/Crm.Integrations.Huntress` (новый) | организации и использование, агенты, инциденты с исправлениями и комментариями, эскалации, platform actions, отчёты; лимит 60/мин: 45 на синхронизацию, 15 на действия | `Crm.Integrations.Atera` |
| `Integrations/Crm.Integrations.CloudAlly` (новый) | аккаунты, задачи и пользователи копий, статусы, счета; вход партнёра и обновление токена | `PowerOfficeTokenProvider` |

| `Modules/Backup` (новый, схема `backup`) | аккаунты, задачи и сущности CloudAlly, строки счетов | то же |

**Склейка машин** (`Service/Features/MachineMatcher.cs`, чистая функция с табличными тестами): только внутри одного
клиента. Ключи по порядку: серийный номер (без заглушек вроде «To be filled by O.E.M.»), общие MAC, имя хоста (без
домена, первые 15 символов). Автоматически — при совпадении серийника, имени и MAC или уникального имени без
противоречия серийника; иначе предложение человеку. Ручные решения применяются первыми и переживают синхронизацию.
Счёт `PerAteraDevice` по-прежнему считает только `System == "atera"`.

**Оповещения из всех источников:** оповещение Atera, инцидент, эскалация, platform action, ошибка копии, пробел
покрытия. Состояние у поставщика зеркалится и не перезаписывается; статус CRM: открыто → закрыто / закрыто в источнике /
скрыто (с причиной и сроком), можно открыть заново. Неполное чтение ничего не закрывает. Срочный инцидент безопасности,
закрытый в Huntress, ждёт подтверждения человека. CRM сама находит пробелы: агент молчит N дней; машина Atera без
Huntress или наоборот; Defender выключен; копия не удалась, старше 26 ч или на паузе; лицензированный пользователь не
в копии. Пробел закрывается после двух чистых проверок подряд.

**Единый путь действий:**

1. Предпросмотр `POST /api/v1/actions/preview` строится только из сохранённых данных: цель, последствия, уровень,
   причина блокировки, подписанный `previewToken` на 10 минут.
2. Подтверждение. Обычное — одна кнопка. Ощутимое (изоляция, пауза копий) — с причиной. Разрушительное (удалить
   агента, удалить организацию, отключить аккаунт копий, восстановить на место) — повторный вход
   (`.RequiresFreshRoles()`, `auth/ReverifyDialog.tsx`), ввод имени цели, причина и 60 секунд на отмену.
3. Команда: `VendorAction` и `OutboundOperation` сохраняются одной транзакцией; повтор запроса возвращает то же
   действие; одновременно идёт не больше одного действия на цель.
4. Отправка: цикл Worker раз в 5 секунд. Перед отправкой повторно проверяются переключатели и живое состояние у
   поставщика; если там уже сделано, результат «Пропущено».
5. Итог: Выполнено, Смоделировано (DryRun), Пропущено, Отклонено, Ошибка или **Неясно**. «Неясно» даёт ссылку
   «Проверить у поставщика» и ручное закрытие с причиной. Все действия видны в журнале на `/connections`.

Запись у каждого поставщика включается отдельно: `WriteEnabled`, `DryRun`, список разрешённых клиентов,
`EnabledActions`. Новые виды действий выключены, пока их не перечислят. Сначала тестовый клиент.

## Правила, которые остаются в силе

Из удалённых документов в код CRM переходят такие правила.

**Вход и ключи сессий** (M05, документ остаётся): вход только через BFF CRM (Entra OIDC + PKCE), токены Microsoft на
сервере, браузер получает HttpOnly/Secure cookie; на VPS ключи Data Protection лежат в постоянном каталоге с
сертификатом (`DataProtection__KeyRingPath`, `DataProtection__CertificatePath`), а AllowedHosts и KnownProxies
задаются точно. Подробности — [M05](M05-WORKSPACE.md).

**Квитанции задач из источника** (M12): `activities.SourceTaskLinks` принадлежит модулю Activities. Задача, квитанция,
аудит и outbox создаются одной транзакцией. Первый успешный автор определяет исполнителя и срок («первый пишущий
выигрывает»); повтор возвращает ту же задачу без изменений, в том числе завершённую или отменённую. После удаления
или стирания задачи квитанция остаётся, задача помечается недоступной, новая сама не создаётся. У квитанции restrict
FK на задачу и уникальный ActivityId. Каждое право — отдельное требование: список в `RequirePermission` означал бы OR.
POST принимает только явно перечисленные поля с CSRF, остальное сервер выводит сам. Изменилось в M38: тема задачи —
заголовок оповещения, её можно изменить (раньше тема была общей, потому что финансовые роли не видели источник).

**Задача и оповещение живут отдельно** (M12, M22): завершение задачи не закрывает оповещение, закрытие оповещения не
завершает задачу; учёт часов не завершает задачу.

**Язык документа** (M36): атрибут `lang` у HTML выставляет общий i18n-механизм — при начальной загрузке переводов и
при каждой фактической смене языка; меню профиля идёт тем же путём.

**Задача после связи заявки** (M28): успешное сохранение связи помечает текущий scope; окно остаётся открытым для
учёта часов. После закрытия фокус остаётся на исходной кнопке, затем родитель перечитывает полную Activity
(`TaskTicketButton`, `MyTasksPanel`, `ActivityTimeline`), а «Мои задачи», выбранная запись и лента прячут старые
действия на время чтения. ETag связи не подставляется в старые поля задачи, complete не повторяется сам, отказ
сохранения связи обновления не запускает; фокус после обновления — на существующей кнопке обновления.

**Честные данные** (M10, M15, M36): пусто или недоступно ≠ «всё в порядке»; включённая настройка или прошлый успех ≠
«подключено»; неполное чтение не выдаётся за полное — и не закрывает оповещений. Список, показанный частично, называет
«показано N из M»; поиск по загруженной странице так и подписан. Цвет важности всегда со словом.

**Устройство оповещения** (M10): связь с устройством — только однозначная; одинаковые имена у разных клиентов или у
двух машин одного клиента не склеиваются.

## Риски

- Оповещение нельзя закрыть по неполному чтению: закрывает только полный постраничный проход (так и сделано в C4).
- Ключи i18n, собранные во время выполнения, typecheck не ловит: нужны тест паритета, e2e и поиск по удалённым префиксам.
- ~~В NB/NN колокольчик уведомлений тоже называется «Varsler» / «Varsel»: одно слово для двух понятий.~~ Снято
  решением владельца: колокольчик остаётся «Varsler» / «Varsel», оповещения называются «Driftsvarsler» /
  «Driftsvarsel» (словарь выше); так пишут меню, очередь, вкладка «Drift», «Мой день» и UX-демо.
- Резервные копии Hostinger до M38 (с дампом PostgreSQL) новым инструментом не восстановить; в них только синтетика.
- Atera: поля v3, дата перехода на JWT и лимит запросов не подтверждены на аккаунте; webhooks заявок есть только в
  планах Enterprise/SuperPower; адрес страницы оповещения не подтверждён (`AlertUrlTemplate` пуст).
- Huntress: запись требует ключа, привязанного к пользователю (все действия пойдут от него); формат прямых ссылок не
  подтверждён; удаление агента — это удалённая деинсталляция.
- CloudAlly: проверить, что аккаунт партнёра может работать с методами `/v2/resellers`; вход API по e-mail и паролю без
  MFA — нужен отдельный API-пользователь; регион для норвежских клиентов (EU или EU_STOCKHOLM).
- Новые персональные данные (комментарии заявок, тексты инцидентов, пользователи копий): для каждого — правило удаления
  и строка в документе о персональных данных.
