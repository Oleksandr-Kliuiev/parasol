## Required findings

**R1. Fence increment for remote policy/admission mutations and runtime pause is not implementable as written.**
`docs/stage5/ask/remote/04_AUTHORITY_AND_BILLING.md` lines 16–18 and 107–108 require policy update, allowlist change, pause and revoke to take the workspace fence FOR UPDATE and "increment its version transactionally through new focused triggers", while lines 22–26 say the new NOLOGIN definer gets "only required table privileges" and existing definers gain no privilege. The accepted fence invariants, re-evaluated by every Ask phase (`packages/ask/authority.ts:120-121`), forbid each obvious route: the fence definer may own exactly one function and hold no privilege on any other relation (`packages/graph/fence-role.ts:105-119`, `prisma/roles.sql:310-320,381-386`), so a second fence-definer-owned trigger is a readiness violation; the fence table must carry exactly two policies (`fence-role.ts:128-134`), so a third role-specific `USING(true)` policy is a violation; the existing trigger function is hard-coded to four tables (`prisma/migrations/202610091000_stage3_action_fence/migration.sql:124-129`) and is owned by the fence definer after provisioning (`roles.sql:337`), so a later migration cannot `CREATE OR REPLACE` it. Nothing in the package states which role gets `UPDATE(version)` on `ActionAuthorityFence`, and the amendment-delta table in `01_SCOPE.md` lines 39–47 does not list any change to Stage 3 fence readiness.
Fix: choose and specify one mechanism. Recommended: the new remote definer (owner of reserve/settle/pause) is granted `SELECT("workspaceId",version), UPDATE(version)` on `ActionAuthorityFence`, increments the fence inside its own SECURITY DEFINER routines (or a new definer-owned trigger function on `RemoteAskPolicy`/`RemoteAskClientAdmission`) under the existing `ActionAuthorityFence_scope` policy with `app.workspace_id` set by the calling transaction, with no new fence policy. Add this grant to `roles.sql` §5 confinement checks and to a scoped readiness query, and list "remote definer may increment the fence" as an explicit amendment delta.

**R2. Privilege and readiness model for the new tables and routines is underspecified against existing defaults, and the gap fails closed on the whole Ask surface.**
`04_AUTHORITY_AND_BILLING.md` line 22 asserts "Runtime cannot INSERT/UPDATE policy, client admissions, counters or attempts directly", but `prisma/roles.sql:196` runs `ALTER DEFAULT PRIVILEGES … GRANT SELECT, INSERT, UPDATE ON TABLES TO <runtime>`, so every new table is writable by the runtime unless `roles.sql` revokes explicitly, and the runtime startup check only covers `PROTECTED_TABLES` (`packages/graph/runtime-role.ts:19-23`), so the grant would pass unnoticed. Separately, line 25 revokes PUBLIC EXECUTE only for the "reserve/settle/pause routines"; any new SECURITY INVOKER guard/trigger function left with default PUBLIC EXECUTE makes the fence definer able to execute an unlisted routine, which `actionFenceRoutineViolations` (`fence-role.ts:124-127`) counts as a violation, and every Ask phase then returns `ASK_RUNTIME_NOT_READY` (`authority.ts:120-121`). Stage 4 handled this by revoking PUBLIC on each new trigger function (`202610091210_stage4_poweroffice_guards/migration.sql:298-301`); the design does not require it.
Fix: in 04 state (a) every new routine, including trigger functions, revokes PUBLIC EXECUTE in its migration; (b) `roles.sql` explicitly `REVOKE INSERT, UPDATE` (and any DELETE) on the four new tables from the runtime after the default-privilege grant, extends the role count/loop for the eighth role, and asserts the new definer's exact privileges in §5; (c) the new tables join `PROTECTED_TABLES` or a remote allowlist in the runtime self-check; (d) the R-A matrix row "DB roles/upgrade" (`05_ACCEPTANCE.md` line 29) names these as independent negatives.

**R3. Policy row model contradicts itself: UNIQUE project per workspace policies versus revisions.**
`04_AUTHORITY_AND_BILLING.md` line 15 ("One project reference UNIQUE across workspace policies"), lines 10–12 (policy "binds a random admissionId, exact positive bigint policyVersion"), line 68 ("admissionId is metadata, never a new budget partition") and line 80 ("New admission revisions share the existing project's monthly/day spend totals") are consistent only if a revision is an in-place update of one row per (workspace, project) with `policyVersion` incrementing and `admissionId` stable. If a revision were a new row (new `admissionId`), the UNIQUE constraint would refuse it, and deleting the old row is excluded by immutable identities and attempt FKs. The 409 `ASK_REMOTE_POLICY_CHANGED` semantics in `02_CONTRACTS.md` lines 30–31 depend on this choice.
Fix: state explicitly that `RemoteAskPolicy` is one row per (workspaceId, projectIdentity), revised in place; `admissionId` is assigned once per row; `policyVersion` increments on every revision/pause/activation; and `RemoteAskAttempt` records (admissionId, policyVersion) as captured metadata with an FK to the policy row only.

**R4. "No remaining provider/publish budget" is unquantified, which turns ordinary DB latency into reservation drain.**
`04_AUTHORITY_AND_BILLING.md` lines 39–41 permit dispatch whenever any budget remains, and line 90 keeps the full 300000 µUSD reservation on timeout. After worst-case authenticate/admit/egress phases (3 × 2 s, `01_SCOPE.md` lines 49–51) a call can be committed and dispatched with a few hundred milliseconds left, guaranteeing an UNKNOWN outcome, and seven such outcomes exhaust the proposed US$2 day cap (`04` line 53). This is self-inflicted financial drain, not provider behavior.
Fix: define a minimum remaining original budget required *before* the egress INSERT (for example remaining ≥ 2000 ms provider + 500 ms publish floor); below it the request fails 504 with no attempt row and no reservation. Add the case to the "Deadline/ownership" and "Atomic billing" matrix rows in `05_ACCEPTANCE.md` lines 30–31.

## Nonblocking notes, residuals and limitations

1. **R-EVAL feasibility versus caps.** `05_ACCEPTANCE.md` lines 57–63 allow 5 % of ≥200 calls to miss the 2 s budget; ten UNKNOWN outcomes retain US$3.00, above the US$2/day cap, and upstream 429/5xx also retain the reserve. Not a design defect, but the owner should plan a multi-day run or a different eval-only day cap at admission.
2. **Settlement placement and run-terminal coupling.** `AskPhase.check()` throws `AskStopped` once the run is terminal (`packages/ask/phase.ts:29-32`) and `AskExchange.publish()` calls `run.end()` (`apps/api/src/ask-http.ts:69-76`). The drain-after-terminal delta (01 line 47) therefore needs a settlement phase bound to its own ≤2 s clock, not to the run. Also state the order explicitly: provider → settlement → phase 2, and that a failed/unknown settlement does not withhold an otherwise valid answer.
3. **Header allowlist** (`03_DATA_AND_PROVIDER.md` lines 36–37) omits Node's automatic `Connection` header; add `Connection: close` or the exact-headers integration test cannot pass.
4. **Usage validation bounds** (03 lines 60–62): the model page states max input 922,000 tokens and the payload is ≤16 KiB; a payload-derived upper bound (for example ≤32,768 prompt tokens) would catch gross anomalies. The official usage object also carries `cache_write_tokens` and `image_tokens`; positive values contradict the explicit-mode/no-image profile and should reject like audio/prediction counters.
5. **UTC period keys** (04 line 102): specify `(now() AT TIME ZONE 'UTC')::date` and the UTC month truncation, independent of session `TimeZone`.
6. **Price revision as data versus constants.** Settlement rates 275/825 (04 line 85), the DTO literal `reserveMicroUsd:300000` (02 line 17) and "future paid admission may lower them" (04 line 55) should be reconciled: either the reserve is profile-fixed and only day/month caps are policy-adjustable, or the DTO and settlement read the pinned price revision.
7. **Model identity residual.** If OpenAI later returns a dated snapshot in `model`, every call becomes `ASK_REMOTE_MODEL_MISMATCH` and trips the durable pause. Intended fail-closed; the runbook should say so.
8. **Upstream 401/403** (invalid key) retain US$0.30 each (02 line 46, 04 line 90). Consider tripping the circuit on 401/403 as a configuration fault to stop drain.
9. **Browser behavior change.** 02 lines 65–66 say a question edit invalidates pending work; accepted ASK-B clears input on submit and does not cancel a pending question on typing (`apps/operator/src/controller-ask.ts:113-124`). Confirm this is intended and list it as a delta.
10. **EU residency admission detail.** Official "Your data" guidance: Europe residency requires per-project region configuration plus approved abuse-monitoring/ZDR-class controls, and a Global-project key against `eu.api.openai.com` yields regional processing only. 06 lines 25–27 say this in substance; make project-level EU configuration an explicit R-EVAL checklist item.
11. **Pause increments the shared workspace fence**, so all in-flight Ask and Stage 3 admissions in that workspace see 409. Consistent with the authority-epoch model; worth a sentence in 04.
12. **Documentation verification results.** Confirmed against official pages on 2026-10-10: `gpt-6-luna` is the only published snapshot, supports `none` effort, Chat Completions and structured outputs, 1,050,000 context; `prompt_cache_options.mode: "explicit"` exists for GPT-5.6+ and "when no explicit breakpoints are placed, the request does not use prompt caching or create cache writes"; `prompt_cache_retention` is deprecated; `service_tier` accepts `default`; `store=true` is refused in non-US regions; Standard long-context cache-write US$0.25 and output US$0.75 per MTok with a 10 % regional uplift for models released after 2026-03-05, so the US$0.2891724 → 300000 µUSD reservation arithmetic is correct and conservative. The data-residency URL cited in 06 returned 404; the facts were taken from the "Your data" guide instead.

Limitations: documentation was read through a summarizing fetch, not raw HTML; the Chat Completions reference was read to its first 100 k characters; no provider telemetry, usage or account state was available or inferred. Lock-order analysis (fence → MONTH → DAY → attempt; settlement without fence; pause fence-first in its own transaction) found no cycle. Egress linearization at the committed attempt, non-reuse of requestId on unknown commit, consent reset rules, V1 byte-compatibility, question-only egress and the semantic-versus-schema separation are sound as written and were not found contradictory.
