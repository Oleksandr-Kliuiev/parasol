## Объём реализации

1. Свести результаты всех карточек и external gates; проверить traceability A01–A16 и дополнительные направления UX/security/migration/UAT.
2. Подготовить release notes для сотрудников, список известных ограничений, конфигурационный manifest, digest образов, миграции, rollback/cutback и критерии остановки rollout.
3. Заполнить GO_LIVE.md фактическими ссылками на evidence: деньги, доступ, data protection, тесты, нагрузка, backup/restore, supplier integrations, обучение и поддержка.
4. Назначить владельца продукта, Finance acceptance, on-call/L1/L2 и эскалацию; проверить доставку алертов и актуальность runbooks.
5. Запланировать ограниченный rollout и наблюдение; production-операции выполнять только в явно указанной пользователем среде с действующей авторизацией, сначала подготовив reviewable релиз.
6. Обновить README/CLAUDE/спецификации по фактической реализации; сохранить аудит как исторический документ с новой ссылкой на результаты, не переписывать старые свидетельства.

## Критерии приёмки

- **DEV-23-AC01** — Ни один P1 или обязательный external gate не замаскирован статусом done.
- **DEV-23-AC02** — Каждый пункт GO_LIVE имеет доказательство на конкретном релизе; mock/local pass не заменяет внешнее свидетельство.
- **DEV-23-AC03** — Promotion использует проверенный digest и миграции; откат совместим с данными.
- **DEV-23-AC04** — Finance/Product Owner зафиксировали go/no-go; при no-go сохраняется пилот и список следующих действий.
- **DEV-23-AC05** — Есть ответственный за инциденты и период стабилизации; приложение не остаётся без поддержки после передачи.
- **DEV-23-AC06** — Если направление исключено из релиза, есть явное решение владельца, выключенная функция и исправленные обещания продукта; полное выполнение пакета при этом не заявляется.

## Данные и обратимость

Не выполнять destructive down migrations или отключение старого процесса до приёмки. Для релиза подготовить снимок разрешённых настроек без секретов, параметры возврата и контрольные данные.

## Границы

Пакет разработки и локально проверенный код сами по себе не разрешают production rollout.

## Завершение задания

Для каждого AC записать способ проверки, фактический результат, ссылку на тест/протокол и commit или manifest в evidence/DEV-23.md по [шаблону](../evidence/TEMPLATE.md). Новые endpoints требуют permissions, record scope, CSRF для cookie mutation и concurrency control по применимости; новый UI — nb/en/ru и доступность. Не оставлять TODO вместо бизнес-инварианта.

Провести самопроверку diff и миграций; обновить backlog.json и PROGRESS.md. Если код проверен, но внешний gate не пройден, статус code_verified и точная причина. Не помечать accepted по существованию файлов, макетов или заглушек.
