## Объём реализации

1. Проверить Git, доступные инструкции, текущие изменения, версии SDK/Node и доступность Docker. Определить, используются ли реальные данные; не выводить содержимое секретов.
2. Сравнить текущие исходники с сохранённым manifest аудита. Зафиксировать отличия, не возвращать исходники к старой версии. При отсутствии истории подготовить и сохранить локальный baseline из явного списка исходников после проверки секретов; не включать сборки, реальные выгрузки и локальные настройки. Не делать push.
3. Воспроизвести A01 и три A02 через публичные доменные методы, а затем критические пути API. Для A03 создать новый тест закрытия месяца и повторного начисления.
4. Сохранить результаты с именами тестов и причинами падений. Регрессии допускаются красными только как доказательство дефекта на рабочей ветке; не маскировать skip и не включать красную версию в готовый релиз.
5. Составить инвентаризацию уже существующих BillingRuns/Bases, outbox, PDF и ролей на синтетической либо отдельно разрешённой копии; никакой автоматической правки данных.

- **DEV-00-AC01** — Baseline имеет проверяемый commit либо точный manifest и объяснение ограничения; пользовательские изменения сохранены.
- **DEV-00-AC02** — Тест 1000 → 900 → recollect обнаруживает 1900 на старой реализации и будет требовать 900 после DEV-01.
- **DEV-00-AC03** — Три теста A02 различают одинакового согласующего, устаревшее согласование и пересечение порога после ручной правки.
- **DEV-00-AC04** — Тест A03 проверяет экономический дубль через второй runId, а не только повтор одного outbound-запроса.
- **DEV-00-AC05** — Записан новый фактический результат базовых проверок; старые 252/54/80/29 не выданы за результат новой версии.
