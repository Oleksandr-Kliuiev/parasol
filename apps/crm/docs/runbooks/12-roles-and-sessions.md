# Runbook 12. Роли и сессии: синхронизация, срочный отзыв, недоступность Graph

Когда:
- первое развёртывание DEV-10;
- сотрудник уволен или аккаунт скомпрометирован;
- пользователи получают «Подтвердите права: выйдите и войдите снова» (`AUTH_REVERIFY_REQUIRED`);
- задача `entra-role-sync` падает;
- замер срока отзыва для EXT-02.

Модель — [ADR-019](../adr/ADR-019-sessions-and-privilege-freshness.md).

Роли: **администратор tenant** (Entra, PIM, разрешения Graph), **Admin CRM** («Интеграции», Hangfire `/admin/jobs`), DevOps (настройки окружения).

## 1. Первое включение
1. Управляемой идентичности crm-worker `id-crm-worker-<env>` выдать разрешения Microsoft Graph (Application):
   - `User.Read.All` — синхронизация пользователей, уже нужна;
   - `Application.Read.All` — чтение назначений ролей приложения CRM;
   - `GroupMember.Read.All` — члены назначенных групп.

   Это делает `infra/entra/register-app.sh <env> <url> <principalId worker>` (runbook 01, шаг 3), запускает Global или Privileged Role Administrator. Разрешения выдаются идентичности, а не регистрации приложения. crm-web их не получает.
2. `Integrations:MicrosoftGraph:CrmAppId` — client id регистрации «Vardahei CRM (<env>)». Bicep передаёт его worker из `entraClientId`, руками ничего не задаётся. Расписание — `Integrations:MicrosoftGraph:RoleSyncCron`, по умолчанию `*/2 * * * *`. Реже не ставить: срок отзыва ≈ интервал + 30 с.
3. После развёртывания: «Администрирование → Интеграции → последние запуски» (или `GET /api/v1/integrations/runs?system=microsoft-graph`) показывает `entra-role-sync` со статусом «Успешно» и текстом «N users with CRM roles in Entra ID; M CRM users confirmed, K changed». Задача работает каждые 2 минуты, но в журнал попадают каждая ошибка, каждое изменение ролей и раз в час — запуск без изменений, иначе журнал утонул бы. Ошибка 403 означает, что разрешения из п. 1 не выданы или ещё не применились (до ~30 мин после выдачи).
4. При первом входе после выпуска каждый пользователь один раз входит заново: cookie, выданные до DEV-10, не содержат серверной сессии. Это ожидаемо, данные не теряются.

## 1а. Полный доступ через одну группу
В Parasol у каждого сотрудника полный доступ ([ADR-030](../adr/ADR-030-full-access-group.md)): группа безопасности «Parasoll – full tilgang» назначена роли приложения `Crm.Admin`, а эта роль даёт все права CRM. Выполняет **администратор tenant** после регистрации приложения (runbook 01, шаг 3). Пример для окружения `test`; у другого окружения своя регистрация и своя группа.

1. Найти service principal приложения и id роли:
   ```bash
   APP_ID=<APP_ID регистрации «Vardahei CRM (test)»>
   SP_ID=$(az ad sp show --id "$APP_ID" --query id -o tsv)
   ROLE_ID=$(az ad sp show --id "$APP_ID" --query "appRoles[?value=='Crm.Admin'].id | [0]" -o tsv)
   ```
2. Создать группу и назначить её роли (нужен **Microsoft Entra ID P1**: без него назначение групп приложению недоступно — тогда п. 4):
   ```bash
   GROUP_ID=$(az ad group create --display-name "Parasoll – full tilgang (test)" --mail-nickname parasoll-full-test --query id -o tsv)
   az rest --method POST --url "https://graph.microsoft.com/v1.0/servicePrincipals/${SP_ID}/appRoleAssignedTo" \
     --headers "Content-Type=application/json" \
     --body "{\"principalId\":\"${GROUP_ID}\",\"resourceId\":\"${SP_ID}\",\"appRoleId\":\"${ROLE_ID}\"}"
   ```
3. Добавить трёх сотрудников **прямыми** членами: вложенные группы ролей не дают ([ADR-019](../adr/ADR-019-sessions-and-privilege-freshness.md)).
   ```bash
   az ad group member add --group "$GROUP_ID" --member-id <objectId сотрудника>   # для каждого из трёх
   ```
   Группы `CRM-<Role>-test` из скрипта регистрации оставить пустыми: при росте команды разделение ролей вернётся без изменения кода. PIM для этой группы не включать: доступ постоянный по решению владельца.
4. **Без Entra ID P1** — назначить `Crm.Admin` каждому из трёх пользователей напрямую (тот же вызов, `principalId` — objectId сотрудника):
   ```bash
   az rest --method POST --url "https://graph.microsoft.com/v1.0/servicePrincipals/${SP_ID}/appRoleAssignedTo" \
     --headers "Content-Type=application/json" \
     --body "{\"principalId\":\"<objectId сотрудника>\",\"resourceId\":\"${SP_ID}\",\"appRoleId\":\"${ROLE_ID}\"}"
   ```
   Синхронизация ролей читает прямые назначения так же, как групповые. Новый сотрудник в этом варианте получает роль тем же вызовом, а не членством в группе.
5. MFA обязательна: при P1 — политика Conditional Access для приложения (runbook 01, шаг 7), без P1 — security defaults tenant (запрашивают MFA не на каждом входе; проверить на tenant, EXT-02). Полный доступ означает, что одна украденная учётная запись открывает всё.
6. Сотрудник без назначения после входа видит «Нет доступа» с просьбой попросить администратора добавить его в группу «Parasoll – full tilgang»; страница «Пользователи» говорит, что доступ выдаётся через эту группу. Роли в интерфейсе не называются.
7. Проверка (не раньше чем через ~2,5 минуты): `GET https://graph.microsoft.com/v1.0/servicePrincipals/${SP_ID}/appRoleAssignedTo` показывает группу (или трёх пользователей) с ролью `Crm.Admin`; «Администрирование → Интеграции» — успешный `entra-role-sync`; у каждого сотрудника `/bff/user` возвращает `roles: ["Crm.Admin"]` и полный список `permissions`. Отзыв — §2.

## 2. Срочный отзыв (увольнение, компрометация)
1. В Entra в любом порядке:
   - удалить из группы «Parasoll – full tilgang» (или снять прямое назначение `Crm.Admin`), а также из групп `CRM-*`, если они использовались;
   - отключить аккаунт;
   - Revoke sessions.
2. CRM снимает роли не позже чем через ~2,5 минуты на всех репликах, без участия пользователя. Отключённый аккаунт теряет роли уже при следующем запуске `entra-role-sync`. Неактивным (401 на любой запрос) его делает `entra-user-sync` (ежечасно в :15). Чтобы не ждать, запустите её вручную в Hangfire (`/admin/jobs` → Recurring jobs → `entra-user-sync` → Trigger now).
3. Проверка: под ролью Admin откройте журнал аудита пользователя — запись об изменении `Roles` от системного пользователя. Сессия пользователя видит пустой набор ролей и страницу «Нет доступа».
4. Не используйте ротацию ключей Data Protection, чтобы кого-то «выкинуть»: она не завершает сессии (старые ключи остаются для расшифровки) и не для этого предназначена. Отдельной команды «завершить все сессии» нет. Отзыв идёт через каталог.

## 3. «Подтвердите права: выйдите и войдите снова» (`AUTH_REVERIFY_REQUIRED`)
Привилегированное действие (утверждение и выгрузка биллинга, разблокировка времени, согласование скидки, настройки интеграций и полей, удаление клиентов) или экспорт требует, чтобы каталог подтвердил роли не более 5 минут назад. Ответ означает, что подтверждения не было:
1. Посмотрите историю `entra-role-sync`. Если запуски падают — п. 4. Если задача на паузе (runbook 05) — снимите паузу, когда инцидент позволит.
2. Пользователь может продолжить сразу: в сообщении об ошибке (диалог) нажмите **«Подтвердить личность»**. Это вход в Entra с `prompt=login` и `max_age` 5 минут: Entra спросит пароль/MFA заново, приложение проверит `auth_time` и аккаунт и вернёт на ту же страницу, после чего действие можно повторить. Выход и вход вручную даёт тот же эффект. Если после подтверждения диалог снова просит его — см. п. 2а.
2а. **Регистрация приложения Entra должна отдавать claim `auth_time`** (Azure Portal → App registrations → Token configuration → Add optional claim → ID → `auth_time`; `infra/entra/register-app.sh` делает это при регистрации). Без него приложение не знает, когда пользователь аутентифицировался, и привилегированные действия закрыты для всех — это безопасный отказ, а не сбой синхронизации. Проверка: после «Подтвердить личность» в журнале нет `reverify_auth_time_missing`. Если Conditional Access требует конкретный контекст аутентификации, значение `acr` задаётся в `Auth:RequiredAcr` (по умолчанию пусто = проверка `acr` отключена; EXT-02). Перед выкладкой убедитесь, что claim настроен в `test` и `prod`.
3. В Development синхронизации нет: привилегированные действия требуют входа разработчика не старше 5 минут (вход разработчика ставит `auth_time` = сейчас). Это то же правило, а не ошибка.
4. Не увеличивайте `Auth:PrivilegedFreshness` в production, чтобы «починить» ошибку: значение — решение DEC-05, и бессрочное действие со старой ролью — то, что DEV-10 закрывает.

## 4. Graph недоступен или отвечает 403
- Через 5 минут без успешного запуска привилегированные действия и экспорт закрываются (fail-closed). Чтение продолжается, но не дольше 8 часов после последнего подтверждения (`Auth:RoleGrace`). Затем сессия требует входа, а вход проверяет роли заново.
- 403: проверьте разрешения идентичности (`az rest --method GET --url https://graph.microsoft.com/v1.0/servicePrincipals/<principalId>/appRoleAssignments`), что `CrmAppId` указывает на регистрацию этого окружения и что у неё есть service principal.
- 429 или 5xx: подождите. Задача повторяется каждые 2 минуты, отдельный повтор не нужен.
- Пауза интеграции `microsoft-graph` (runbook 05) останавливает и синхронизацию ролей: через 5 минут привилегированные действия возможны только после нового входа. Учитывайте это, ставя паузу.
- Если не отвечает сам вход Entra (`login.microsoftonline.com`), ежечасная проверка сессий откладывается на 5 минут: в журнале предупреждение «Session revalidation with Entra ID is unavailable», запросы обслуживаются. Ответ Entra «нужен вход» (отозванные сессии, сброс пароля, отключённый аккаунт) по-прежнему завершает сессию.

## 5. Замер срока отзыва (EXT-02)
Только в разрешённом tenant, с тестовыми пользователями, на окружении без режима разработчика. Для каждого случая записать время действия в Entra (T0), время, когда CRM перестала давать право (T1), и разницу:
1. **Прямое назначение.** Тестовый пользователь с `Crm.Finance` открыл «Биллинг». Снять назначение (T0). Каждые 10 с обновлять `/bff/user` или пробовать «Утвердить» на тестовом прогоне без реальных данных. T1 — роль исчезла или 403.
2. **Группа.** Удалить пользователя из `CRM-Finance-<env>` (в Parasol — тестового пользователя из группы полного доступа тестового окружения).
3. **PIM.** Активировать членство в `CRM-Admin-<env>` на минимальный срок и дождаться истечения. T0 — время окончания активации.
4. **Отключение аккаунта.** `accountEnabled = false`: роли пропадают по п. 1, 401 — после `entra-user-sync`.
5. **Две реплики.** Повторить п. 1 при двух и более репликах crm-web (`az containerapp replica list`) и убедиться, что обе отказывают. Скопированная cookie после выхода получает 401.
6. **Недоступность.** Временно отозвать `Application.Read.All` у идентичности worker (согласовать), через 5 минут проверить `AUTH_REVERIFY_REQUIRED` на привилегированном действии и 200 на чтении, вернуть разрешение.

Результат (цель ≤ 5 мин, DEC-05) записать в `docs/claude-opus/evidence/DEV-10.md` и `external-gates.json` (EXT-02) без идентификаторов реальных людей: только роли тестовых учёток и времена.

## 6. Что нельзя
- Давать идентичности worker разрешения шире `Application.Read.All`, `GroupMember.Read.All`, `User.Read.All` (например, `Directory.ReadWrite.All`): CRM ничего не пишет в каталог.
- Включать вход разработчика (`Auth:Mode=Development`) где-либо кроме Development: приложение не запустится, и это правильно.
- Запускать crm-web в production без `DataProtection:BlobUri` и `DataProtection:KeyVaultKeyUri`: приложение откажется стартовать — каждая реплика со своими ключами не читала бы cookie других.
