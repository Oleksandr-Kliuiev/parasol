# Runbook 05. Приостановить интеграцию во время инцидента

Когда: внешняя система отвечает мусором, удаляет данные, ушла в обслуживание или её ключ скомпрометирован, а ждать деплоя нельзя.

Роли: **Admin CRM** (право `integrations.manage`).

## 1. Пауза (без деплоя)
«Администрирование → Интеграции» → карточка системы → **«Приостановить»**; в диалоге укажите причину — она попадёт в журнал и в карточку.

Через API:
```bash
curl -X POST https://crm.<домен>.no/api/v1/integrations/atera/pause \
  -H "X-CSRF: 1" -H "Content-Type: application/json" \
  -d '{"paused":true,"reason":"Инцидент 2026-09-24: Atera отдаёт пустые тикеты"}'
```

Что происходит:
- задания синхронизации этой системы при наступлении расписания записывают прогон со статусом **Skipped** и причиной — видно, что задание сработало и было удержано;
- исходящие операции остаются в очереди (`Pending`) и **не** отправляются: очередь не растёт ошибками и ничего не теряет;
- CRM продолжает работать на уже синхронизированных данных.

## 2. Чего пауза не делает
- Не выключает интеграцию в конфигурации: флаги `Integrations:*:Enabled` меняются в переменных окружения Container Apps и требуют новой ревизии.
- Не отменяет уже выполняющееся задание — дождитесь его завершения (минуты).
- Не трогает другие системы: пауза всегда на одну.
- Не останавливает записи в CRM и отправки других систем. Для этого есть режим обслуживания ([runbook 03 § 2](03-database-restore.md#2-режим-обслуживания-t1)): только чтение для всех, ни одной отправки.
- Пауза хранится в базе. После восстановления из резервной копии действуют паузы копии; отчёт сверки (runbook 03 § 7) перечисляет приостановленные системы.

## 3. Снятие паузы
Та же кнопка — **«Возобновить»**. Очередь исходящих операций пойдёт со следующей минутой (`outbound-operations` — раз в минуту), задания — по своему расписанию; при необходимости запустите нужное вручную в Hangfire (`/admin/jobs`).

## 4. Проверка
```bash
curl -s https://crm.<домен>.no/health/integrations | jq '.systems[] | {system, paused, lastRunStatus, failedOutbound}'
```
`/health/integrations` — для мониторинга и дежурного: он **не** влияет на readiness, поэтому сулящая интеграция никогда не выводит CRM из балансировщика ([07 §4.3](../07-nfr-devops.md)).

## 5. После инцидента
- Снимите паузу и убедитесь, что первый прогон завершился со статусом `Succeeded`.
- Проверьте очередь: `GET /api/v1/integrations/runs?system=<система>` и счётчик «в очереди / с ошибками» на карточке.
- Запишите в журнал инцидента: когда поставили на паузу, почему, когда сняли, сколько операций ждало.
