# Runbook 16. Документы на VPS Hostinger

Модель: [ADR-026](../adr/ADR-026-vps-document-store.md). Роли: администратор VPS и Admin CRM.
Этот документ описывает будущую настройку; текущий PR не выполняет развёртывание,
подключение к рабочим системам или перенос реальных документов.

## Подготовка постоянного тома

1. Выделить приватную папку на постоянном локальном ext4/XFS, например
   `/srv/parasol/documents`. Проверить `findmnt -T /srv/parasol/documents` и свободные
   байты/inodes. Папка и родители не должны изменяться посторонними локальными пользователями.
2. Web и worker запускаются одним служебным UID. Права папки — `0700`, документов —
   `0600`. Путь не публикуется Caddy/Nginx/static middleware. У каждого окружения и БД
   своя папка: очистка сирот одной БД не должна видеть документы другой.
3. Один раз создать в папке `.parasol-volume` с UUID в формате `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`.
   Это идентификатор, не секрет. Сохранить его в резервной копии и конфигурации обоих
   процессов. При уже существующем томе маркер не генерировать заново.
4. Для контейнеров монтировать эту папку явно в web и worker; не использовать writable
   layer образа. Для systemd настроить зависимость от mount. Проверить поддержку hard
   link/fsync в файловой системе: приложение дополнительно проверит их при запуске.

Одинаковые параметры обоих хостов, пример пути внутри контейнера:

```text
Documents__Provider=FileSystem
Documents__RootPath=/var/lib/parasol/documents
Documents__VolumeId=<UUID из .parasol-volume>
```

`BlobContainerUri` и managed identity хранилища больше не используются. Конфигурация
`Provider=AzureBlob` останавливает запуск с понятной ошибкой. Development по-прежнему
поддерживает относительную папку; это не production-конфигурация.

Маркер защищает от пустого mountpoint и перепутанных томов. Он не заменяет проверку
типа диска, прав, свободного места и независимых резервных копий. Смена UID не должна
оставить файлы другого владельца: проверять владельца при планируемом переносе.

## Перенос существующих объектов

Если данных ещё нет, достаточно подготовить новый том. Если есть старое хранилище:

1. Снять резервную копию БД и полный инвентарь объектов: ключ, длина, SHA-256 самих байтов,
   время изменения. Для Ready-документов сверить инвентарь с `sales.QuoteDocuments`
   (`ObjectKey`, `ContentSha256`, `Length`). Хеш из Blob metadata не считается доказательством.
2. Включить maintenance, дождаться нулевого числа выполняющихся внешних операций и
   окна кэша (10 секунд); сохранить журнал внешних эффектов. Затем остановить оба
   хоста на период финального копирования, чтобы записи больше не менялись.
3. Экспортировать существующие объекты в отдельную приватную staging-папку, сохранив
   **исходные ключи, байты и время изменения**. Это операторский перенос данных;
   приложение не обращается к Azure и не содержит Azure-клиента хранилища.
   Нужны все префиксы: `quotes/`, `operations/`, privacy manifests, BI snapshots, месячные отчёты клиентов
   (`customers/documents/`, M43) и остальные.
   Нельзя ограничиваться PDF или пересоздавать их рендерером.
4. Сверить весь экспорт с инвентарём: количество, отсутствие лишних/пропущенных ключей,
   длины и SHA-256. Сверить Ready-документы с SQL. Проверить отсутствие symlink,
   специальных файлов и неканонических ключей. При расхождении не переключать приложение.
5. Поставить проверенную папку на постоянный том, задать права/владельца, создать маркер
   и прописать его UUID в конфигурации. Сохранить старое хранилище и БД до завершения
   проверки; исходные объекты не удалять и не переписывать.
6. Запустить web/worker в maintenance. Очистку `quote-document-orphans` держать отключённой
   до сверки. Выполнить dry run существующего restore reconciliation, проверить privacy
   replay и журналы эффектов, скачать выборку документов и сравнить SHA-256.
7. Открывать запись только после проверки. Если нужно отменить переключение до открытия
   записи, вернуть прежнюю пару приложения/БД/хранилища. После новых записей нельзя
   откатывать только папку или только БД: нужен повторный перенос и сверка эффектов.

## Резервная копия и восстановление

- Хранить зашифрованную копию вне этого VPS с отдельными правами и политикой удержания.
  Настроить уведомления об ошибках backup и исчерпании диска. Сам факт наличия backup
  Hostinger не подтверждает, что в него входят все bind mounts и что его можно восстановить.
- Для согласованной копии включить maintenance, дождаться завершения работы, остановить
  процессы и сделать резервную копию SQL Server плюс всего дерева документов с маркером
  и временами изменения. Ключи DataProtection и сертификаты из M05 сохраняются отдельно.
- Не откатывать актуальные privacy manifests, журнал внешних эффектов и maintenance
  вместе с бизнес-БД. Они нужны для replay удаления и предотвращения повторных отправок.
  При восстановлении старой БД сохранить актуальное дерево документов, остановить очистку
  и выполнить reconciliation; документы после точки восстановления могут стать сиротами,
  но всё ещё быть доказательством отправки.
- При потере диска восстановить полное дерево из последней проверенной копии в отдельную
  папку, сверить инвентарь и SQL-хеши/размеры, затем подключать её к хостам в maintenance.
  Если нет последних manifest/журналов, сохранять блокировку внешних действий до ручной
  сверки с провайдерами; неизвестные отправки автоматически не повторять.
- Пройти privacy replay, сверку SQL/документов и dry run/apply существующего
  `/api/v1/operations/restore/reconcile`. Очистку включать после решения по сиротам.
  Azure-команды из исторического runbook 03 и `tools/ops/restore.py` для VPS не применять.

## Неисправности

| Сигнал | Действие |
| --- | --- |
| Неверный/отсутствующий `.parasol-volume` | Проверить mount и конфигурацию; не создавать пустой новый том поверх пропавшего |
| Ошибка publish/fsync, ENOSPC/EROFS/permission denied | Проверить диск, inodes, mount и UID; не менять provider для обхода ошибки |
| `SAL_DOCUMENT_PREPARING` | После восстановления диска штатный job повторит сохранение и подхватит опубликованные байты |
| `SAL_DOCUMENT_UNAVAILABLE` | Сверить файл с SQL-хешем; восстановить точные байты из проверенной копии, не рендерить заново |
| `.stage-*.tmp` | Служебные незавершённые записи; скрыты от приложения, старше 7 дней удаляются при следующем запуске |

Резервное копирование, наблюдение за диском и учение восстановления на Hostinger ещё
нужно настроить при развёртывании. Численные RPO/RTO этим изменением не обещаются.
