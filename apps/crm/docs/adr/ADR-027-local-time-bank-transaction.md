# ADR-027 — одна локальная транзакция для Time и банка часов

Статус: M24 принят локально; 919 unit, 94 architecture, 118 affected SQL, 562 frontend, 73 browser и 9 composition проходят. Публикации и развёртывания нет.

## Доказанная проблема

У Time и Contracts отдельные DbContext на одной CRM SQL-базе. Прежний Consume/Reverse
сохранял движение банка до commit Time. Управляемый SQL-сбой перед Time SaveChanges
воспроизвёл три расхождения: bank used 1 / allocated 2; used 2 / allocated 1;
после неудачного withdrawal — used 0 / всё ещё allocated 2.

## Решение

Для команд approve/withdraw и импорта вводится явный scoped `TimeBankTransaction`.
Time владеет nonretrying SQL connection/transaction. Contracts через свой API создаёт
собственный временный DbContext с той же открытой connection и `UseTransaction`.
Модуль продолжает владеть своими таблицами, доменными методами, аудитом и outbox;
Time не ссылается на реализацию Contracts и не пишет SQL чужой схемы.
Единственный commit принадлежит Time. Движение банка, часы, allocations, оба аудита и
outbox фиксируются вместе или откатываются вместе. Никаких TransactionScope/MSDTC,
сети, другого хранилища, фоновой очереди восстановления или новых dependencies нет.

Read-your-writes важен: GetBillingTerms также присоединяется, иначе второй элемент
пакета мог бы заблокироваться на банке, изменённом собственной ещё не завершённой
транзакцией первой записи. Контексты используются последовательно; их disposal не
закрывает connection и не завершает транзакцию владельца.

## Ограничения и порядок

- Поддерживается только пара Time owner → Contracts participant в одной базе и под
  одинаковой SQL identity/configuration. Несовпадение отвергается до открытия foreign
  connection. Вспомогательный класс содержит техническую композицию, не бизнес-правила.
- Граница явная и scoped, без AsyncLocal или глобального process-state. Вложенный owner,
  завершённая транзакция и SQL execution strategy с повтором callback запрещены, включая
  уже активный внешний retry callback. Команда обязана владеть всей Time-транзакцией;
  произвольный внешний owner запрещён. Участник не повторяет SaveChanges самостоятельно.
- Порядок: все M23 month admissions → SQL application lock `time:bank-financial-work`
  → Time rows → bank work → единственный Time commit. Глобальный финансовый lock
  сериализует малое число банковских команд трёх сотрудников, включая разные месяцы,
  и предотвращает удержание нескольких банков в противоположном порядке.
- Метаданные inbox (BasisExported/TechnicianMapping) сохраняют M23 single-module
  ownership. ADR-016 не ослабляется: активный MessageHandlingContext не может включить
  эту command boundary. Другие модули не подключаются к ней автоматически.
- Внешние вызовы и файловые эффекты внутрь не входят. Atlas/PostgreSQL не участвует.
  Разделение Time/Contracts на разные БД потребует нового протокола; текущая реализация
  отказывает, а не создаёт ложную атомарность.

## Старая история

Транзакция предотвращает новые частичные сохранения и не переписывает старые движения.
Перед новой approval проверяются все source receipts следующего approval number, включая
закрытые, исчерпанные и удалённые записи банка. Неожиданный след требует Finance review;
новый случайный source key не маскирует его. Withdrawal сверяет исходные списания с
allocations и допускает уже полностью возвращённое подтверждённое списание: повтор
завершает Time без второго возврата. Несогласованные ledger facts отклоняются.

До финансового пилота требуется сверка исторических частичных операций. Отдельная
граница export → asynchronous invoiced этим решением не устраняется. Обновление всех
Web/Worker выполняется согласованно при остановленных писателях; старую и новую версии
нельзя смешивать. Схема и существующие source keys не меняются.
