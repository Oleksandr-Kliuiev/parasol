# ADR-026. Неизменяемые документы на VPS Hostinger

Дата: 2026-10-16. Принято для Parasol. Заменяет Azure Blob как способ хранения
из ADR-017; правила выпуска, проверки SHA-256, SQL-защиты и восстановления сохраняются.

## Решение

`IDocumentStore` использует `FileSystemDocumentStore` на постоянном локальном томе Linux.
Web и worker одного окружения работают с одной папкой от одного служебного UID.
Доступ к файлам — только через существующие авторизованные API. Новых production-пакетов нет.
`AzureBlob` остаётся лишь распознаваемым значением устаревшей конфигурации и вызывает
ошибку; автоматического переключения на пустую папку нет.

Production требует `Documents:RootPath` — существующий абсолютный путь вне `wwwroot` —
и `Documents:VolumeId`, UUID из файла `.parasol-volume` на этом томе. Проверка идентичности
выполняется при запуске и операциях. Конструктор проверяет запись, синхронизацию и
create-only hard link; hosted service инициирует его до приёма работы. Отсутствующий том,
чужой UUID, неподдерживаемые операции или недостаточные права приводят к ошибке.

## Протокол записи

1. Проверить канонический ключ и отсутствие символических ссылок в дереве объекта.
2. Создать приватные каталоги; синхронизировать их и родителей вплоть до корня тома.
3. Записать байты в уникальный `.stage-<uuid>.tmp` рядом с будущим объектом;
   `Flush(flushToDisk: true)`, закрыть файл.
4. `linkat(..., flags=0)` атомарно публикует имя. Существующее имя не заменяется;
   только `EEXIST` означает повторную запись. Другие ошибки не считаются успехом.
5. Синхронизировать каталог, в том числе при подхватывании существующего объекта:
   первый процесс мог остановиться между link и fsync. Прочитать сохранённые байты
   и вернуть их SHA-256/размер и признак первого автора.
6. Удалить временное имя и синхронизировать каталог. Ошибки синхронизации не скрываются.

Основание: [link(2)](https://man7.org/linux/man-pages/man2/link.2.html) запрещает замену
существующего имени; [fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html)
отдельно требует синхронизации каталога для сохранения его записи.

После остановки до link итогового объекта нет. После link опубликованы только полные
байты, а повторный выпуск подхватывает их. SQL-коммит не обязан совпадать с записью
файла: существующий `QuoteDocumentJob` завершает состояние `Preparing`.
PDF не пересоздаётся и renderer version не меняется.

## Чтение, удаление, границы гарантий

- SHA-256 всегда вычисляется из байтов, метаданные/sidecar не являются источником истины.
  Проверка хеша относительно SQL перед скачиванием/отправкой сохранена.
- Отсутствующий объект возвращает `null`. Потеря тома, ошибки доступа/чтения и неверный
  UUID вызывают ошибку. Ключи с пустыми, точечными или служебными сегментами запрещены.
- Новые staging-файлы не попадают в `ListAsync`, поэтому журналы maintenance/privacy
  не видят незавершённый JSON. При старте удаляются только зарезервированные staging-файлы
  старше 7 дней. Опубликованные документы этим проходом не удаляются.
- `DeleteAsync` остаётся для существующих проверяемых процедур privacy и очистки сирот.
  SQL-запрет изменения/удаления Ready-документов и защита ссылочных объектов сохранены.
- Поддерживаемая production-среда: приватная локальная ext4/XFS с рабочими hard link и
  fsync; macOS используется для разработки. NFS, SMB, FUSE и эфемерный слой контейнера
  не входят в контракт. Проба возможностей не подтверждает долговечность диска VPS.
- Это неизменность через приложение и протокол записи. Владелец ОС/диска может изменить
  файл напрямую; обнаружение такого изменения опирается на SQL-хеш и резервные копии.
  ОС и каталог доверенные: сторонние локальные процессы не должны менять дерево,
  создавать symlink/hard link или переставлять mount во время работы приложения.
  Это не аппаратное WORM-хранилище и не защита от неисправного диска/контроллера.
- Отдельная резервная копия вне VPS обязательна. Автоматического Blob versioning/soft
  delete больше нет; восстановление проверяется по ключам, хешам и размерам.

## Проверки и эксплуатация

Unit-набор запускает восемь независимых процессов, принудительно завершает автора
до link, между link/fsync и после fsync; проверяет повторный запуск, отмену, потерю
тома/UUID, symlink, ошибочные ключи и уборку staging. Те же проверки запускаются на Linux.
Интеграционные тесты используют реальный файловый store, SQL Server и WireMock:
выпуск → скачивание → вложение → новая версия → копирование/восстановление в другую папку.
Существующие тесты corruption, SQL immutable triggers, privacy, maintenance и restore остаются.

Настройка и перенос: [Hostinger document storage](../runbooks/16-vps-document-storage.md).
Локальные проверки остановки процесса не доказывают RPO/RTO и поведение физического диска
при отключении питания. Учение восстановления на целевом VPS — отдельный этап развёртывания.
