# ADR-030. Полный доступ каждого сотрудника через одну группу Entra

Дата: 21.10.2026. Статус: принято владельцем для Parasol в M38 ([M38](../../../../docs/migration/M38-OPERATIONS-IN-CRM.md)).
Реальный tenant, лицензия Entra ID и назначения сотрудников не проверялись (EXT-02).

## Контекст

- В Parasol работают три сотрудника (Oleksandr, Asbjørn, Bjarte), и каждый делает всю работу: технику, продажи,
  финансы и администрирование.
- CRM унаследовала семь ролей приложения (`Crm.Admin`, `Crm.Management`, `Crm.Sales`, `Crm.Technician`,
  `Crm.ServiceLead`, `Crm.Finance`, `Crm.ReadOnly`) и группы `CRM-<Role>-<env>` (ADR-010, ADR-019, runbook 01). Для
  троих это означало подбирать сочетания ролей, объяснять отказы словами «ваша роль…», а «Мой день» выбирал раскладку
  по роли.
- Прежний сервис интеграций добавлял второй уровень доступа — членство сотрудника по клиенту, которого роль CRM не
  давала. В M38 сервис удалён.
- Решение владельца (M38): все трое имеют полный доступ ко всем функциям, роли не настраиваются.

## Решение

1. В Entra одна группа безопасности **«Parasoll – full tilgang»** на регистрацию приложения; для отдельного
   тестового окружения — своя группа с суффиксом, например «Parasoll – full tilgang (test)».
2. Группа назначена роли приложения `Crm.Admin` в корпоративном приложении CRM. Эта роль — набор `Everything` в
   `Crm.Authorization/Permissions.cs`: все права, включая `finance.read`, `billing.approve`, `privacy.manage`,
   `operations.maintenance` и `integrations.manage`. Записевой охват (ADR-018) её не ограничивает: у неё есть
   `sales.quotes.all` и `projects.all`.
3. Сотрудники — прямые члены группы: вложенные группы ролей не дают (ADR-019). Добавление в группу выдаёт доступ,
   удаление отзывает его.
4. Назначение роли группе требует Microsoft Entra ID P1. Без него роль `Crm.Admin` назначается трём пользователям
   напрямую; `entra-role-sync` читает прямые назначения так же, как групповые.
5. Остальные роли и группы `CRM-<Role>-<env>` остаются в регистрации приложения пустыми. Код и тесты по-прежнему
   проверяют права по ролям, поэтому при росте команды разделение возвращается без изменения кода.
6. Проверки прав в коде остаются защитой: каждый эндпоинт требует своё право; войти может только назначенный
   пользователь (`appRoleAssignmentRequired: true`); снятые роли перестают действовать за ~2,5 минуты; привилегированное
   действие требует подтверждения ролей не старше 5 минут или повторного входа (`AUTH_REVERIFY_REQUIRED`).
7. Интерфейс ролей не показывает: экраны «Нет доступа», отказы и список пользователей говорят о доступе и группе
   «Parasoll – full tilgang», карточка учётной записи показывает e-mail вместо роли. Раскладку «Моего дня» каждый
   выбирает сам (`identity.Users.MyDayLayout`). Вход разработчика первым предлагает `Crm.Admin` — «Employee (full
   access)»; узкие роли остаются ниже, чтобы проверять права. Логика авторизации при этом не менялась.
8. Правило двух разных людей сохраняется: второе утверждение крупного прогона биллинга ставит другой активный
   сотрудник (BR-BIL-04, ADR-012). При полном доступе это может быть любой из двух других.

Настройка — [runbook 01 §7](../runbooks/01-first-deployment.md#7-домен-и-вход) и
[runbook 12 §1а](../runbooks/12-roles-and-sessions.md#1а-полный-доступ-через-одну-группу).

## Рассмотренные варианты

- **Оставить роли по обязанностям** (Technician, ServiceLead, Admin и Finance). Ограничивает ошибки, но трое делают
  всю работу, и отказы мешали ежедневной работе. Владелец отказался.
- **Всегда назначать `Crm.Admin` пользователям напрямую.** Работает без P1, но новый сотрудник получает доступ правкой
  приложения, а не группы. Оставлено запасным путём.
- **Использовать группу `CRM-Admin-<env>` из скрипта регистрации.** Роль та же, но имя говорит о ролях, а runbook 01
  предлагал вести её через PIM. Понятное имя «Parasoll – full tilgang» отражает решение.
- **PIM для группы** (доступ по запросу на срок). Требует Entra ID P2 или ID Governance и ежедневной активации, что
  противоречит решению «полный доступ всегда». Может вернуться позже для отдельных опасных действий.
- **Убрать проверки прав из кода.** Нет: они защищают от посторонних учётных записей tenant, от отозванных
  сотрудников и от устаревших сессий.

## Последствия

- Компрометация одной учётной записи открывает всё. Обязательны MFA (Conditional Access при Entra ID P1, без него —
  security defaults, которые запрашивают MFA не на каждом входе), повторный вход перед опасными действиями и журнал
  аудита. При подозрении — срочный отзыв по
  [runbook 12 §2](../runbooks/12-roles-and-sessions.md#2-срочный-отзыв-увольнение-компрометация).
- Аудит по-прежнему называет конкретного человека. Разделения обязанностей по ролям больше нет; остаётся правило двух
  разных людей для крупного биллинга.
- Новый сотрудник — добавить в группу (или, без P1, назначить роль напрямую). Уход — удалить из группы, отключить
  учётную запись и отозвать сессии.
- Документы 01 и 02 описывают семь ролей как общую целевую модель CRM; для Parasol действует это решение.
